# Целевая архитектура Raymondovich.ru

**Статус:** архитектурное предложение, подлежащее согласованию.  
**Базовая редакция для проектирования:** `afca990a72151174dd241ab701a451aae8d92b09`.  
**Область действия:** только репозиторий `raymondovich.ru`.

Документ определяет правила дальнейшего развития платформы. Он не означает немедленного переноса страниц, создания всех перечисленных каталогов или переписывания существующего кода. Новые модули появляются по мере возникновения реальной ответственности.

## 1. Архитектурная цель

Raymondovich.ru — развивающаяся платформа управления экосистемой проектов, а не только публичный сайт. Публичная презентация, аккаунт партнёра и закрытый Control Center должны опираться на согласованные предметные модели и общие технические механизмы, но не зависеть друг от друга на уровне реализации страниц.

Архитектура должна позволять добавлять новые направления без превращения страниц, сервисов или общих модулей в монолиты.

Базовые требования:

1. Clean Architecture и инверсия зависимостей.
2. DDD — разделение по предметным областям и бизнес-возможностям.
3. Один модуль — одна ясная ответственность.
4. Независимые точки входа и страницы.
5. Явные контракты между слоями и модулями.
6. Отсутствие дублирования общих компонентов и бизнес-правил.
7. Проверяемые изменения, тестируемые сценарии и документированные решения.
8. Без преждевременного создания абстракций и каталогов «на будущее».

## 2. Архитектурные слои и зависимости

### 2.1 Domain

Содержит предметную модель и правила бизнеса:

- сущности и идентификаторы;
- value objects;
- инварианты и доменные ограничения;
- доменные политики и события — когда они действительно нужны.

Domain не импортирует UI, Supabase, браузерные API, сетевые клиенты, файловую систему, инфраструктуру или слой хранения состояния.

Доменная логика не должна зависеть от конкретного способа сохранения данных.

### 2.2 Application

Содержит прикладные сценарии (use cases), координацию операций и порты, необходимые сценариям.

Примеры сценариев: создать идею, изменить её статус, запустить проект, назначить участника, получить портфель проектов.

Application:

- принимает входные данные сценария;
- проверяет прикладные предусловия;
- вызывает доменные правила;
- обращается к внешним возможностям только через интерфейсы/порты;
- возвращает результат, не зная о DOM и конкретном SDK.

Application не импортирует Supabase SDK и не строит HTML.

### 2.3 Infrastructure

Содержит реализации портов и интеграции:

- Supabase repositories / data adapters;
- Auth adapter;
- внешние API;
- браузерные и сетевые адаптеры;
- логирование и технические механизмы.

Именно здесь допустимы запросы к Supabase и преобразование формата хранения в прикладные модели. Инфраструктура реализует контракты, определённые внутренними слоями, а не диктует им бизнес-правила.

### 2.4 Presentation

Содержит страницы, UI-компоненты, обработчики пользовательского ввода и отображение состояния.

Presentation обращается к Application через публичные интерфейсы сценариев. Он не выполняет запросы к Supabase напрямую и не принимает на себя доменные решения.

Страница является точкой композиции конкретного пользовательского сценария, но не местом хранения всей логики продукта.

### 2.5 Core

Core — минимальный набор действительно общих технических контрактов и примитивов, которые нужны нескольким независимым модулям.

Запрещено превращать Core в свалку утилит, бизнес-логики или универсальных сервисов. Если понятие относится к конкретному домену, оно должно оставаться в этом домене.

### 2.6 Memory и состояние

Понятие Memory необходимо уточнить по мере проектирования. Оно не должно становиться параллельным Domain или универсальным хранилищем всего приложения.

Следует различать:
- долговременные бизнес-данные — через репозитории и инфраструктурные адаптеры;
- состояние конкретного UI-сеанса — рядом с соответствующим presentation-модулем;
- кэш и локальное техническое состояние — за явно определённым контрактом;
- пользовательские заметки/контекст, если они станут отдельной функцией продукта, — как самостоятельная предметная возможность.

До появления конкретных сценариев не создавать абстрактную систему Memory.

### 2.7 Design System

Содержит визуальные токены, типографику, базовые стили, компоненты и layout-паттерны.

Design System не импортирует Application или Domain и не содержит бизнес-правила. Компонент может принимать данные и callbacks, но не должен самостоятельно принимать решения о правах, статусах или бизнес-переходах.

## 3. Допустимое направление зависимостей

Основное правило:

`presentation → application → domain`

Application определяет необходимые порты. Infrastructure предоставляет их реализации. В точке композиции приложения связываются сценарии и адаптеры.

`infrastructure → contracts` — реализация внутренних контрактов; инфраструктура не должна становиться источником бизнес-правил.

Дополнительные ограничения:

- Domain не зависит от других внешних слоёв.
- Presentation не импортирует Infrastructure напрямую.
- Application не импортирует конкретный SDK или браузерный API.
- Design не зависит от бизнес-слоёв.
- Один bounded context не обращается к внутренним файлам другого контекста в обход его публичного интерфейса.
- Циклические зависимости запрещены.

Технически допустимая схема должна проверяться автоматизированно, а не оставаться только текстовым соглашением.

## 4. Предметные области и границы модулей

Ниже перечислены вероятные направления платформы, а не требование немедленно создать соответствующие папки:

- Identity & Access — учётная запись, аутентификация, роли и права.
- Ideas — фиксация, оценка и развитие идей.
- Projects — управление проектами и их жизненным циклом.
- Portfolio — портфельный обзор и приоритизация нескольких направлений.
- Partnerships — партнёры, участие и условия сотрудничества.
- Products — каталог собственных и внешних продуктов.
- Finance — финансовые показатели и коммерческие результаты.
- Knowledge / Strategy — документы, заметки, решения и стратегические материалы.
- Notifications — уведомления и события для пользователей.

Граница домена определяется бизнес-терминами, правилами, инвариантами и ответственностью, а не только названием экрана или таблицы.

Не следует заранее дробить домен на десятки микромодулей. Сначала фиксируется bounded context и его публичный контракт; внутреннее разбиение появляется по мере роста сложности.

## 5. Control Center

Control Center — отдельная пользовательская область, но не отдельная бизнес-модель и не один огромный модуль.

Рекомендуемое разделение:

- оболочка рабочего пространства: общая навигация, top bar, уведомления, account menu;
- функциональные области: Ideas, Projects, Portfolio и будущие разделы;
- общие UI-компоненты: диалоги, поля, состояния загрузки, пустые состояния;
- сценарии Application — вне UI-компонентов;
- доменные правила — в соответствующих bounded contexts.

Каждая функциональная область должна иметь собственную точку входа/инициализацию, собственные presentation-модули и явные зависимости. Общая оболочка не должна знать внутреннее устройство каждого раздела.

Не создавать единый `app-page.js`, содержащий все разделы. Не заменять его другим универсальным файлом с тем же набором обязанностей.

## 6. Страницы и маршрутизация

Текущая платформа использует многостраничную модель на GitHub Pages. Целевая схема сохраняет независимые страницы и не требует перехода на SPA.

Для чистых URL предпочтительна модель каталогов с `index.html`, например:

- `/products/`
- `/cooperation/`
- `/profile/`
- `/settings/`

Каждая страница должна иметь собственную HTML-точку входа и подключать только необходимые ей стили и модули.

Маршруты и ссылки должны быть описаны единообразно. Нельзя строить централизованный router-монолит или переносить бизнес-логику в маршрутизатор.

Перед миграцией необходимо отдельно проверить:
- все внутренние и внешние ссылки;
- redirect/callback URLs Supabase Auth;
- ссылки из писем и восстановление пароля;
- canonical URL, robots и метаданные;
- GitHub Pages fallback/404 поведение;
- обратную совместимость старых адресов и редиректы, если они доступны.

Перенос URL выполняется отдельным этапом после тестирования маршрутов.

## 7. Общие UI-компоненты

Повторяющиеся элементы, например боковая панель, должны иметь один источник реализации.

Выделение компонента означает единый контракт и единственное место изменения, а не механическое копирование HTML/CSS/JS в несколько страниц.

Общие компоненты не должны:
- знать о конкретных таблицах Supabase;
- выполнять прикладные сценарии самостоятельно;
- содержать правила доступа или бизнес-статусы;
- становиться универсальным контейнером всей страницы.

Необходимо выбрать способ доставки общих компонентов с учётом текущего статического хостинга и отсутствия подтверждённой build-системы. До такого решения не вводить runtime-загрузчик HTML-фрагментов или новый сборщик без обоснования и проверки на GitHub Pages.

## 8. Данные, репозитории и Supabase

Supabase — текущая инфраструктурная реализация, а не доменная модель платформы.

Правила:

1. Все обращения к Supabase SDK находятся в infrastructure.
2. Application работает через порты/контракты репозиториев и сервисов.
3. Запросы ограничиваются правами доступа и политиками RLS; клиентский интерфейс не является границей безопасности.
4. Схема БД, миграции, доменная модель и документация должны изменяться согласованно.
5. Критичные многошаговые операции должны быть атомарными на стороне БД — через транзакционную функцию/RPC или другой проверенный механизм, а не через последовательность клиентских запросов с попыткой компенсации.
6. Внешние DTO и строки БД преобразуются в модели, которые ожидают внутренние слои.
7. Нельзя доверять owner_id, role или иным критичным атрибутам только потому, что они пришли из UI.

### Нерешённый вопрос: жизненный цикл идеи и проекта

Текущая документация `overview.md` и `projects.md` описывает идею и проект как одну запись с изменением статуса. Фактическая реализация на базовой редакции содержит отдельные таблицы `ideas` и `projects`, связь `source_idea_id` и операцию создания проекта из идеи.

Целевая архитектура не выбирает один вариант молча. Это отдельное доменное решение, которое нужно принять до рефакторинга соответствующих сервисов и миграций.

При выборе оценить:
- нужна ли самостоятельная история идеи после запуска;
- какие данные могут изменяться независимо;
- нужна ли связь «одна идея — несколько проектов» или строго один к одному;
- как обрабатываются удаление, архивирование и повторный запуск;
- какие гарантии атомарности нужны;
- какие данные и связи уже существуют в production.

До решения запрещено выполнять миграцию, слияние таблиц или менять семантику существующих статусов.

## 9. Файлы и модульность

Правило «один файл — одна ответственность» означает:
- один модуль решает одну понятную задачу;
- публичный интерфейс модуля ограничен;
- внутренние детали не импортируются соседями;
- имя файла отражает назначение;
- размер файла сам по себе не единственный критерий, но смешение независимых причин изменения — сигнал к разделению.

Не дробить код на десятки микрофайлов только ради длины. Не создавать универсальные `utils.js`, `helpers.js`, `common.js` с несвязанными функциями.

Для каждого нового модуля должны быть понятны владелец ответственности, публичный интерфейс и допустимые зависимости.

## 10. Тестирование и архитектурные ограничения

Целевая стратегия тестирования:

- Domain — unit-тесты бизнес-правил и инвариантов.
- Application — тесты сценариев с подменяемыми портами.
- Infrastructure — интеграционные тесты адаптеров и запросов, где возможно.
- Presentation — проверки ключевых пользовательских сценариев и доступности.
- Маршруты — smoke-тесты всех публичных и закрытых точек входа.
- База данных — проверки миграций, RLS и критичных транзакционных операций.

Архитектурные проверки должны выявлять:
- импорт Infrastructure из Application/Domain/Presentation;
- импорт Presentation из Domain/Application;
- циклические зависимости;
- прямой Supabase SDK import вне Infrastructure;
- случайное включение бизнес-логики в Design System.

В репозитории на базовой редакции не обнаружен `package.json`; наличие полноценной автоматизированной тестовой и сборочной инфраструктуры пока не подтверждено. Поэтому сначала следует инвентаризировать доступные CI/workflow и выбрать минимальный проверяемый набор инструментов. Не добавлять тяжёлый build stack без необходимости.

## 11. Безопасность и доступ

- Авторизация и авторизация доступа — разные проверки: наличие сессии не означает право выполнять действие.
- UI скрывает недоступные действия для удобства, но окончательная проверка выполняется на доверенной стороне.
- RLS и серверные функции должны обеспечивать границы доступа к данным.
- Публичный publishable/anon key не является секретом; service-role ключи и другие привилегированные секреты не размещаются в клиентском коде.
- Redirect URLs и callback flow должны быть явными и тестируемыми.
- Любое изменение ролей, прав и владения данными рассматривается как изменение безопасности и требует отдельной проверки.

## 12. Документация и процесс изменений

Архитектурные решения, влияющие на несколько модулей, фиксируются отдельными ADR или разделами архитектурной документации.

Для изменения:
1. Проверить актуальную версию `main` и связанные модули.
2. Определить ответственность и границы изменения.
3. Проверить направление зависимостей.
4. Согласовать изменения схемы данных и миграции, если они нужны.
5. Добавить или обновить тесты.
6. Обновить документацию и журнал изменений.
7. Проверить GitHub Actions и фактический результат.
8. Не считать изменение опубликованным до успешного deployment workflow.

Рефакторинг выполняется небольшими обратимыми этапами. Не совмещать перенос маршрутов, изменение модели данных и крупную перестройку UI в одном изменении.

## 13. Рекомендуемая последовательность внедрения

1. Согласовать этот документ и отдельно принять решение по модели Ideas/Projects.
2. Зафиксировать фактическую карту зависимостей и определить composition root для текущих точек входа.
3. Ввести порты/адаптеры для одного вертикального сценария как эталон, не переписывая сразу все сервисы.
4. Разделить Control Center по функциональным областям и оболочке.
5. Устранить дублирование sidebar и других общих компонентов.
6. Выделить общие стили из HTML в Design System.
7. Ввести архитектурные и функциональные тесты.
8. Спроектировать и проверить чистые URL, callback и redirect flow.
9. Переносить остальные модули по одному, проверяя обратную совместимость.

## 14. Что этот документ не разрешает автоматически

Документ сам по себе не является разрешением:
- менять схему БД;
- объединять `ideas` и `projects`;
- переписывать существующие страницы;
- менять публичные URL;
- добавлять новый frontend framework или сборщик;
- менять визуальный дизайн;
- затрагивать репозиторий `raymondovich.online`.

Каждый такой шаг требует отдельного плана и проверки.

---
**Главное архитектурное правило:** платформа растёт через независимые предметные модули и сценарии с явными контрактами, а не через расширение универсальных файлов и прямое связывание страниц с инфраструктурой.
