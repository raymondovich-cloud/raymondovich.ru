# Спецификация UI-компонентов авторизованного пространства

> Версия: 1.4  
> Статус: Базовый компонентный слой реализован; полная спецификация остаётся проектной  
> Дата: 2026-11-11  
> Область: Welcome, Projects registry и последующие экраны авторизованного пространства  
> Основа: `authenticated-ui-standard.md`, `authenticated-ui-audit.md`, текущая реализация Profile и нижней навигации

## 1. Назначение и статус

Документ переводит направление единого интерфейса в измеримые контракты компонентов: геометрию, типографику, отступы, состояния, адаптивность и тематическое поведение.

Это целевая спецификация для последующей реализации, а не утверждение, что все значения уже внедрены. Статус остаётся проектным до отдельного подтверждения владельца. Значения, отмеченные как «эталон», измерены в текущем Profile или оболочке. Значения, отмеченные как «целевые», являются нормативным предложением для новых/унифицируемых компонентов.

Основной структурный и композиционный эталон — завершённый Profile и нижняя Liquid Glass навигация. Их удачная структура и поведение сохраняются, но допускается аккуратное усиление фирменной визуальной выразительности через токены Design System.

## 2. Неприкосновенные границы

1. Profile и нижняя навигация остаются структурным и композиционным эталоном. Их DOM, сценарии, размеры и поведение сохраняются; разрешена отдельная согласованная работа с акцентными цветами, градиентами, подсветками и поверхностями.
2. Унифицировать остальные экраны по качеству, иерархии и системе токенов, но не копировать структуру Profile буквально.
3. Не превращать каждую сущность в карточку. Тип поверхности определяется назначением данных и действием.
4. Не менять маршруты, бизнес-логику, права, RLS, схему БД, API, интеграции и пользовательские сценарии в рамках визуальной миграции.
5. Визуальные правила находятся только в `source/design-system/`. Запрещены inline CSS, CSS-in-JS, `element.style`, `setProperty()` и визуальные значения вне Design System.
6. Presentation отвечает за структуру и поведение; Application — за сценарии и преобразование данных; Infrastructure — за внешние источники. Presentation не обращается к Supabase напрямую.
7. Навигация выполняется через `RaymondovichNavigation`. Не создавать локальные механизмы переходов и собственные кнопки возврата в обход утверждённой навигационной архитектуры.
8. Светлая и тёмная темы равноправны. Ни одна реализация не считается готовой после проверки только одной темы.
9. Не вводить новые библиотеки, зависимости и токены без необходимости и проверки существующей системы.
10. Существующие данные, доступность действий и фактические статусы не подменять декоративными заглушками.

## 4. Базовая сетка и размеры контейнеров

Все размеры ниже — CSS px, если явно не указано иное.

### 4.1. Контейнеры

| Контракт | Ширина | Применение |
|---|---:|---|
| Narrow | max 700 | Профильные настройки, простые формы и узкие сценарии |
| Standard | max 1100 | Welcome после входа, реестры и основные рабочие экраны |
| Wide | max 1100 на текущем этапе | Не расширять текущую оболочку; отдельное увеличение допускается только после подтверждения необходимости и проверки |

- Контент центрируется в доступной ширине.
- `min-width: 0` обязателен для grid/flex-потомков с текстом.
- Горизонтальное переполнение недопустимо на ширинах от 320 px.
- На мобильном экране горизонтальные внутренние отступы рабочего содержимого — 0–12 px в зависимости от конкретного паттерна; оболочка уже использует собственные safe-area и padding.
- Не складывать повторно одинаковые боковые отступы оболочки, страницы и вложенного контейнера.
- Нижний контент должен иметь безопасный запас под фиксированную навигацию. Текущий shell уже резервирует 112 px плюс safe area; не добавлять второй такой же отступ на дочернем экране.

### 4.2. Шкала вертикальных интервалов

| Токен/значение | Назначение |
|---|---|
| 4 px | Минимальный интервал внутри компактной пары |
| 8 px | Связанные элементы, label/value |
| 12 px | Внутренние элементы строки/toolbar |
| 16 px | Основной интервал между группами и секциями |
| 20 px | Разделение крупных смысловых блоков |
| 24 px | Отступ перед самостоятельной обзорной областью |
| 28 px | Верхний/внутренний ритм на широких экранах, если требуется |

Предпочитать существующие spacing tokens. Не создавать новый токен для каждого единичного значения.

## 5. Типографическая шкала

Размеры — целевые значения. Текущие специальные значения Profile остаются без изменений.

| Роль | Размер / line-height | Вес | Использование |
|---|---|---|---|
| Screen title compact | 19 px / 1.2 | 700 | Компактный заголовок реестра, если он соответствует сценарию |
| Screen title standard | 22–30 px / 1.15 | 650–750 | Заголовок рабочего экрана |
| Section title | 16–19 px / 1.25 | 600–700 | Название группы/секции |
| Primary row title | 14 px / 1.3 | 550–600 | Основной текст строки |
| Body | 14–15 px / 1.5 | 400–500 | Описание и основной текст |
| Secondary | 12–13 px / 1.45 | 400–500 | Метаданные, пояснения |
| Eyebrow | 10–11 px / 1.4 | 600–750 | Короткая категория/надстрочный маркер |
| Numeric KPI | 22–28 px / 1.15 | 600–700 | Основной показатель, только если есть реальная сводка |

- Использовать `--font-body` и `--font-mono` из Design System.
- Не применять uppercase к длинным заголовкам и пользовательскому содержимому.
- Вторичный текст не уменьшать ради плотности ниже 11 px; в обычных рабочих сценариях целевой диапазон — 12–13 px.
- Все input/select/textarea должны иметь вычисленный размер шрифта не менее 16 px.

## 6. Контракты семантических компонентов

### 6.1. Screen Header

Назначение: идентифицировать текущий экран и, при необходимости, дать короткий контекст и действия.

Структура:
- один основной `h1`;
- необязательное описание;
- необязательная зона действий;
- eyebrow только при наличии смысловой категории, не автоматически.

Размеры:
- нижний отступ до первого содержательного блока: 16–20 px;
- заголовок: 22–30 px на стандартном экране; 19 px для компактного реестра;
- описание: 13–14 px, line-height не ниже 1.45;
- действия не должны вытеснять заголовок за viewport.

Поведение:
- один `h1` на экран;
- длинные заголовки переносятся;
- заголовок не должен повторять название в соседнем блоке без причины;
- вложенные экраны используют существующий навигационный контракт.

### 6.2. Content Container

Назначение: задаёт ширину и вертикальный ритм конкретного экрана.

- Использует один из контейнеров Narrow/Standard/Wide.
- Не имеет собственной визуальной рамки, если это не отдельная семантическая поверхность.
- Не задаёт цвета и шрифты напрямую.
- Не дублирует padding authenticated shell.
- Для списка задаёт интервалы между группами; для форм — интервалы между полями.

### 6.3. Group Container

Назначение: объединяет несколько связанных элементов в одну визуальную группу.

Эталонная геометрия Profile:
- радиус внешней группы: 22 px;
- тонкая граница из component token;
- поверхность из component token;
- внутреннее содержимое обрезается по радиусу через `overflow: hidden`;
- группа Profile имеет заголовок с padding 16px 17px 12px и строки высотой минимум 68 px.

Целевой контракт для новых групп:
- радиус 18–22 px; внутри одного экрана использовать один выбранный радиус;
- граница 1 px через семантический/component token;
- заголовок группы 12–13 px, вторичный цвет; отступы 14–16 px;
- расстояние между самостоятельными группами: 16 px;
- не помещать каждую строку в отдельную вложенную карточку;
- если строки разделены, использовать единый divider token.

### 6.4. Navigation Row

Назначение: переход на другой экран или в раздел.

Эталон Profile:
- минимальная высота строки: 68 px;
- сетка: 40 px icon slot / гибкий текст / необязательное значение / 15 px indicator;
- gap 12 px;
- горизонтальные padding 15 px;
- иконка 38×38 px, радиус 12 px;
- основной текст 14 px;
- вторичное значение 12 px;
- разделитель между соседними строками.

Целевой контракт:
- на ширине до 380 px разрешено уменьшение icon slot до 38 px, gap до 8 px и бокового padding до 10 px;
- зона нажатия — вся строка, не только иконка или chevron;
- наличие chevron определяется фактом перехода; информационная строка не должна выглядеть ссылкой;
- состояние focus-visible обязательно; hover только на устройствах с hover; pressed — на touch;
- текст и значение могут переноситься, если иначе возникнет переполнение.

### 6.5. Information Row

Назначение: показать подпись и значение без перехода.

- Не отображает chevron и не использует pointer cursor без отдельного действия.
- Базовая высота — та же, что у Navigation Row: 68 px. Отдельная компактная высота для информационных строк запрещена; при увеличении системного текста допускается рост строки без обрезания содержимого.
- Слева подпись/контекст, справа значение с выравниванием по правому краю.
- Значения чисел и денежных сумм не должны разъезжаться при обновлении.
- Пустое/неизвестное значение отображается единообразно, например «—»; не маскируется под ноль.
- Если значение устарело или введено вручную, это обозначается контекстной подписью.

### 6.6. Action Row

Назначение: выполнить действие, а не перейти в информационный экран.

- Действие формулируется глаголом.
- Опасное действие визуально использует semantic danger и требует подтверждения, если операция необратима или затрагивает данные.
- Loading блокирует повторный запуск и показывает понятную обратную связь.
- Disabled не должен выглядеть как доступное действие.
- Основное действие на одном экране — одно визуально доминирующее; вторичные действия не конкурируют с ним.

### 6.7. Summary / KPI

Назначение: быстро показать проверяемые показатели.

- Использовать только при наличии реальных данных и понятного источника.
- Значение — 22–28 px; подпись — 12–13 px.
- В одном ряду — не более 3 KPI на мобильном экране; desktop может расширять сетку после проверки.
- Для неизвестного значения показывать «—», для нулевого — «0».
- Цветовой акцент допустим только для смысла/статуса, а не для украшения каждого числа.
- Если показатель рассчитан по неполному набору данных, рядом должна быть подпись об ограничении.
- Не подменять пустую статистику фиктивными графиками или декоративными числами.

### 6.8. Search / Filter Toolbar

Назначение: поиск, фильтрация и основное действие реестра.

- Повторно использовать существующие `workspaceToolbar` и `workspaceFilters`, если их контракт покрывает сценарий.
- Не создавать параллельную toolbar только ради визуального отличия экрана.
- Поиск — гибкий элемент, не должен сжимать текст до нечитаемого состояния.
- Фильтры могут быть свернуты; состояние раскрытия отражается в `aria-expanded`.
- На узком экране toolbar переносится в вертикальную компоновку; действия сохраняют доступность.
- Поля ввода: минимум 16 px font-size, высота контролов от 44 px.
- Search/Filter не должен дублировать глобальный Pull Down Search.

### 6.9. Form Field

Назначение: ввод или редактирование значения.

- Видимая label обязательна; placeholder не заменяет label.
- Input/select/textarea: font-size не менее 16 px, min-height 44 px.
- Вертикальный gap label/control: 7–8 px.
- Поле ошибки располагается рядом с соответствующим полем, содержит текст и semantic danger.
- Состояния default/focus/invalid/disabled/saving/success определяются токенами.
- На мобильном экране поля в одну колонку; двухколоночная форма допускается только при достаточной ширине и логической парности полей.
- Виртуальная клавиатура не должна перекрывать активное поле и submit action.

### 6.10. State Panel

Общий контракт для loading, empty, error и success.

- Loading: короткое объяснение, без ложного обещания завершения; скелетон только если он реально улучшает восприятие структуры.
- Empty: что отсутствует + почему это ожидаемо/неожиданно + следующий доступный шаг. Не показывать действие, если у роли нет прав.
- Error: что не удалось сделать + безопасный следующий шаг. Технические детали и секреты не выводить.
- Success: подтверждает реально завершённую операцию; исчезновение сообщения не должно быть единственным подтверждением.
- Геометрия — одна спокойная поверхность, без вложенной рамки внутри рамки.
- Для пустого списка не использовать крупную иллюстрацию, если она не несёт смысловой нагрузки.

## 7. Welcome — целевой экран первого входа

Текущая реализация уже содержит:
- центрированную карточку шириной до 620 px;
- верхний eyebrow;
- фирменный mark 68×68 px;
- заголовок с градиентным акцентом;
- краткое описание;
- бейдж роли;
- основное действие высотой 48 px.

Целевой контракт:
1. Сохранить простой одноколоночный сценарий, без боковых панелей и дополнительных карточек.
2. Контент карточки — не шире 620 px; текст описания — не шире 440 px.
3. На мобильном устройстве внешний отступ по вертикали — 24 px; внутренний padding — 22 px по горизонтали, 28 px минимум по вертикали.
4. На широком экране вертикальный отступ может адаптивно увеличиваться; карточка остаётся визуально центрированной.
5. Заголовок 28–44 px с line-height около 1.08; не допускать переполнения.
6. Основная кнопка — минимум 48 px по высоте, с ясной глагольной формулировкой.
7. Роль — вспомогательный контекст, не конкурирующий с основным действием.
8. Не добавлять дублирующие блоки с перечнем всех модулей или маркетинговые обещания, не подтверждённые функциональностью.
9. Сохранить существующую логику завершения welcome и перехода через `RaymondovichNavigation`; визуальный срез не меняет её.

## 8. Projects registry — целевой экран первого вертикального среза

### 8.1. Информационная иерархия

Порядок:
1. Screen Header «Проекты».
2. Search / Filter Toolbar с поиском, фильтром и действием создания (только для роли с правом).
3. Краткая Summary область — только показатели, реально доступные из текущих источников.
4. Группа «В фокусе» — только если есть проекты, соответствующие действующему правилу приоритета.
5. Остальные проекты, сгруппированные по статусам.
6. Empty State, если список пуст или фильтр не дал результатов.

### 8.2. Представление проекта

- Проект — самостоятельная сущность, поэтому допускается компактная Content Card/Navigation Row, но не отдельная декоративная карточка вокруг каждого внутреннего значения.
- Название — основной текст, 17–19 px на широком экране, 15–17 px на узком.
- Описание — 12–13 px, максимум 2 строки в компактном представлении; полный текст не теряется в модели данных.
- Статус — отдельный компактный badge; цвет и текст статуса дублируют смысл, цвет не единственный индикатор.
- Приоритет и происхождение — вторичные метаданные, не равные по визуальному весу названию.
- Вся область записи доступна как единая цель перехода, если запись открывает проект.
- Не показывать фиктивные доходы, расходы, пользователей, прогресс или метрики. Для отсутствующих данных — «—»/описание отсутствия источника.

### 8.3. Геометрия реестра

- Расстояние между независимыми записями/группами: 10–16 px согласно выбранному паттерну.
- Радиус внешней поверхности: 16–20 px; в пределах одного экрана не смешивать более двух близких радиусов.
- Padding записи: 14–18 px на мобильном, 16–20 px на desktop.
- Высота определяется содержимым; не фиксировать высоту карточки, если описание может переноситься.
- На ширине до 700 px метаданные переносятся на следующую строку; статус остаётся видимым и не вытесняет название.
- На ширине 320 px запись не должна вызывать горизонтальный скролл.
- Hover не является единственным указанием на интерактивность; focus-visible и pressed обязательны.

### 8.4. Сводка и фильтры

- Сводка не должна занимать больше визуального веса, чем сам список.
- На мобильном максимум 2 KPI в одной строке; дополнительная сводка — компактная строка/группа ниже.
- Прогресс рассчитывается только по реальным данным и не округляется так, чтобы создавать ложную точность.
- Статусные группы раскрываются предсказуемо; раскрытие доступно с клавиатуры.
- Фильтр сохраняет выбранные значения при повторном рендеринге списка.
- При активных фильтрах empty state сообщает, что ничего не найдено, и предлагает очистить/изменить фильтр, если такая функция уже существует. Не добавлять новые бизнес-сценарии без согласования.

## 9. Темы: Light и Dark

Для каждого компонента и каждого состояния должны существовать корректные значения обеих тем.

Использовать семантические/component tokens:
- background/surface/surface-raised;
- text-primary/text-secondary/text-tertiary;
- border/divider;
- accent/accent-subtle/accent-foreground;
- success/warning/danger;
- focus-ring;
- component-specific surface/material tokens там, где они уже предусмотрены.

Правила:
1. Не инвертировать цвета механически.
2. Не использовать цвет как единственный способ передачи статуса.
3. Контраст текста проверяется на фактической поверхности, включая градиент/прозрачность.
4. Статусные цвета не заменяются фирменным оранжевым.
5. Liquid Glass остаётся характерной особенностью нижней навигации и отдельных контекстных поверхностей. Фирменные градиенты и акцентный цвет могут использоваться и в других компонентах, но дозированно: интерфейс должен оставаться рабочим, читаемым и визуально спокойным.
6. Структура Profile и нижней навигации остаётся эталоном. Их визуальное оформление можно точечно усилить в рамках отдельного согласованного изменения; нельзя ухудшать читаемость или перегружать интерфейс.

## 9.1. Фирменная выразительность: градиенты и акцентные цвета

Задача — убрать ощущение чрезмерно нейтрального и сухого интерфейса, не превращая рабочее пространство в набор ярких декоративных карточек. Базовая структура Profile и нижней навигации сохраняется; усиливается только визуальный характер.

### Принцип распределения акцентов

- Нейтральная поверхность остаётся основной площадью интерфейса.
- Фирменный оранжевый и его градиентные переходы — акцент, а не фон всего приложения.
- Градиенты применяются к ограниченному числу визуально значимых точек: главному CTA, активному элементу навигации, отдельным акцентным маркерам, выбранным состояниям и небольшим декоративным подсветкам.
- Не окрашивать каждую карточку, каждую строку и каждую иконку в оранжевый.
- Не использовать несколько конкурирующих градиентов в пределах одного экрана.
- Градиент не должен ухудшать контраст текста, границ, статусов и интерактивных состояний.

### Рекомендуемые уровни акцента

1. **Primary accent** — фирменный оранжевый/оранжевый градиент для одного главного действия или активного состояния на экране.
2. **Soft accent** — мягкий оранжевый оттенок/градиент низкой интенсивности для небольших поверхностей, иконок, выделения выбранной группы или локального свечения.
3. **Micro accent** — тонкая линия, небольшой индикатор, точка, маркер или деликатный glow; применяется для визуального ритма, а не для каждого элемента.
4. **Neutral** — основной режим для контента, строк, форм и информационных поверхностей.

### Применение по компонентам

| Компонент | Допустимый акцент | Чего избегать |
|---|---|---|
| Screen Header | Небольшой градиентный акцент в одном фрагменте заголовка или тонкий маркер | Полностью градиентный длинный заголовок на каждом экране |
| Group Container | Мягкая подсветка или акцентная деталь только у одной приоритетной группы | Яркая градиентная заливка всех групп |
| Navigation Row | Акцент иконки/индикатора у выбранной или важной строки | Оранжевая заливка каждой строки |
| Summary / KPI | Акцент на одном ключевом показателе, остальные нейтральны | Все числа и карточки в ярких градиентах |
| Action Row / CTA | Primary gradient допустим для главного действия | Несколько равносильных градиентных кнопок |
| State Panel | Цветовая семантика состояния; мягкий фирменный акцент только если он не конфликтует со статусом | Подмена success/warning/danger фирменным оранжевым |
| Bottom Navigation | Сохранить Liquid Glass; активный элемент может иметь тонкую фирменную подсветку/градиент | Яркий градиент на всей панели или постоянное свечение всех пунктов |
| Profile identity | Сохранить компактную композицию; допускается деликатный акцент аватара, границы или фонового свечения | Перекрашивание всей карточки в насыщенный оранжевый |

### 9.1.1. Утверждённая карта семантических акцентных токенов

> Статус: карта акцентных токенов утверждена владельцем 2026-11-11. Утверждение относится к этой карте и не означает автоматического утверждения всей спецификации UI-компонентов.

Существующие базовые цвета сохраняются. Новые семантические роли добавляются в общий слой Design System; существующие legacy-токены не удаляются и не переназначаются массово. Миграция потребителей выполняется отдельными вертикальными срезами после проверки совместимости.

| Токен | Dark | Light | Назначение |
|---|---|---|---|
| `--semantic-accent` | `#FF762F` | `#B94C19` | Основной фирменный акцент |
| `--semantic-accent-strong` | `#FF9A5B` | `#A94416` | Усиленный акцент |
| `--semantic-accent-gradient` | `#FF6A27 → #FFB078` | `#B94C19 → #D65B1F` | Фирменный градиент |
| `--semantic-accent-subtle` | `rgba(255,118,47,.14)` | `rgba(185,76,25,.10)` | Мягкая акцентная поверхность |
| `--semantic-accent-glow` | `rgba(255,118,47,.10)` | `rgba(185,76,25,.08)` | Локальное свечение |
| `--semantic-accent-border` | `rgba(255,118,47,.30)` | `rgba(185,76,25,.24)` | Акцентный контур |
| `--semantic-accent-foreground` | `#100D0C` | `#FFFFFF` | Текст на основном акцентном фоне |

Правила применения:
- Нейтральные поверхности остаются основой интерфейса.
- На одном экране допускается один главный градиентный акцент; вторичные акценты используются с низкой интенсивностью.
- Основные действия, выбранные состояния, заголовки и небольшие маркеры могут использовать акцентные токены по таблице применения выше.
- Не окрашивать все карточки, строки и иконки в фирменный цвет.
- Не заменять фирменным оранжевым семантические цвета success, warning, danger и info.
- Контраст градиентов, прозрачных границ и свечения проверяется на фактической поверхности после композиции.
- Значения Light и Dark самостоятельны; светлая тема не наследует тёмный градиент или glow.

В первой технической итерации токены добавляются без массового переключения существующих компонентов. Это позволяет проверить наличие и корректность общей карты без непреднамеренного изменения текущего интерфейса.

### 9.1.2. Визуальная редакция Profile и нижней навигации (2026-11-11)

- Утверждённые semantic tokens подключаются к существующим component tokens отдельно для Dark и Light.
- Profile: сохраняются нейтральная поверхность и существующая геометрия identity card; добавляется только локальный мягкий акцентный glow. Кольцо и halo аватара используют semantic border/glow tokens.
- Нижняя навигация: структура Liquid Glass, размеры, позиционирование, маршрутизация и логика active state не меняются. Акцент ограничен мягкой градиентной подложкой активной вкладки, semantic border и коротким градиентным индикатором.
- Нейтральные группы Profile, строки, иконки и неактивные вкладки не перекрашиваются. Статусные цвета остаются независимыми.
- Это первый ограниченный migration slice; остальные экраны и legacy consumers не затрагиваются.

### Light и Dark

- **Dark:** допустимы более заметные локальные оранжевые акценты и мягкое внешнее свечение, но основная поверхность остаётся тёмной и спокойной.
- **Light:** использовать более светлые и менее насыщенные оранжевые подложки; текст и границы должны сохранять достаточный контраст. Не переносить тёмную интенсивность свечения в светлую тему.
- Градиенты должны иметь отдельные проверенные значения для обеих тем, а не только прозрачность поверх одного и того же цвета.
- Фирменный акцент не заменяет статусные цвета success, warning и danger.

### Ограничение плотности

Для одного экрана по умолчанию:
- не более одного основного градиентного акцента;
- до двух-трёх вторичных мягких акцентов, если они выполняют разные функции;
- micro accents могут повторяться системно, но должны быть малоконтрастными;
- если взгляд не может сразу определить главное действие и главный блок, количество акцентов считается чрезмерным.

Это целевые визуальные правила, а не утверждённая палитра конкретных HEX-значений. Цветовые значения должны браться из текущих токенов или добавляться в Design System после проверки обеих тем.



Точные значения пяти новых токенов (отдельно для обеих тем):

| Токен | Dark | Light |
|---|---|---|
| `--gradient-accent-surface` | `linear-gradient(145deg, #25160F 0%, #1B110D 100%)` | `linear-gradient(145deg, rgba(214,91,31,.08) 0%, rgba(255,255,255,.96) 58%, rgba(241,243,246,.92) 100%)` |
| `--color-accent-line` | `#57301D` | `rgba(185,76,25,.30)` |
| `--color-accent-tint` | `rgba(255,118,47,.12)` | `rgba(185,76,25,.08)` |
| `--shadow-accent-glow` | `0 0 16px rgba(255,118,47,.10)` | `0 0 16px rgba(185,76,25,.07)` |
| `--color-nav-edge` | `rgba(255,255,255,.08)` | `rgba(255,255,255,.08)` |

Дополнительные правила реализации редакции 1.3:
- Для Profile identity card и единственной приоритетной строки Control Center применяется `--gradient-accent-surface` и `--color-accent-line`; для аватара допускается единственный локальный glow на экране через `--shadow-accent-glow`.
- Бейдж роли и плитка иконки проектов используют `--color-accent-tint`; плитка инструментов сохраняет бирюзовую категорийную идентичность. Другие строки остаются нейтральными.
- Email в identity card отображается одной строкой с ellipsis; счётчики строк «Мои проекты» и «Инструменты» оформляются нейтральными pill без изменения размеров строк.
- Пустое состояние «Избранное» получает декоративную звезду через CSS-псевдоэлемент, без изменения DOM.
- Нижняя навигация использует `--color-nav-edge`, сохранённый Liquid Glass material, мягкую верхнюю fade-поверхность и градиент активной вкладки. Активный аватар получает контур, но без дополнительного свечения.
- Нижний резерв контента остаётся `calc(112px + var(--safe-bottom))`: существующий контракт уже резервирует место под фиксированное меню и safe area; повторный отступ не добавляется.
- Разрешены только цветовые/рамочные переходы 0.18s; при `prefers-reduced-motion: reduce` переходы отключаются. Геометрия, DOM, данные, сценарии и навигационная логика не меняются.

## 10. Состояния и доступность

Обязательные состояния интерактивного компонента:
- default;
- hover — только для устройств с hover;
- pressed/active;
- focus-visible;
- disabled;
- loading;
- error/invalid;
- success — если операция предполагает подтверждение.

Общие требования:
- Интерактивные цели — не менее 44×44 CSS px, если это не нативно компактный inline control с альтернативной доступной областью.
- Видимый focus indicator обязателен.
- Семантический HTML и корректные роли/aria атрибуты.
- `aria-expanded`, `aria-current`, `aria-live` применяются по назначению, а не формально.
- Поддерживать reduced motion.
- Не отключать масштабирование страницы.
- Текст не должен обрезаться так, чтобы терялась важная информация или действие.

| Диапазон | Правила |

## 14. Реализованный базовый слой Design System

Этап 1 добавляет opt-in набор базовых компонентов авторизованной зоны. Компоненты доступны через классы `.app-ui-*`; существующая разметка экранов не переводится на них на этом этапе.

### Геометрия и типографика

- Системный стек шрифтов для нового слоя; моноширинный стек наследуется из `--font-mono`.
- Типографическая шкала от подписи до крупного заголовка с отдельными line-height и weight tokens.
- Единая spacing-шкала 4–40 px.
- Единая базовая высота всех типов строк — 68 px; Navigation, Information и Action Row не получают отдельные размеры. Иконка строки — 38 px.
- Touch target — минимум 44 px; основные поля и кнопки — 48 px.
- Единые радиусы control/group/card/sheet/pill.
- Единые длительности 160/220/320 ms, standard/enter easing и blur tokens для меню, листов и нижней навигации.
- Геометрические токены общие для тем; визуальные цвета, материалы, статусы и тени имеют отдельное dark/light mapping.

### Базовые компоненты и CSS-контракт

| Компонент | Классы |
|---|---|
| Большой и компактный заголовок экрана | `.app-ui-screen-header`, `.app-ui-screen-heading`, `.app-ui-screen-heading--compact` |
| Группированный список и строка | `.app-ui-group`, `.app-ui-group-heading`, `.app-ui-list`, `.app-ui-row` |

### Поведение и ограничения

- Новый слой использует только семантические и component tokens; собственные цвета в CSS-компонентах не задаются.
- Light и Dark имеют отдельные значения поверхностей, материалов, границ, теней, skeleton и статусных подложек.
- Bottom sheet и нижняя панель учитывают `--safe-bottom`; интерактивные строки, кнопки, меню и вкладки имеют зоны касания не менее 44 px.
- Поля ввода используют системный шрифт 16 px; существующее глобальное правило Foundation остаётся действующим.
- Focus-visible, hover-only для устройств с hover, pressed, disabled, expanded/open и error states оформлены централизованно.
- При `prefers-reduced-motion: reduce` перемещения и scale отключаются; остаётся только простое изменение opacity. Skeleton shimmer отключается.
- Контекстное меню позиционируется относительно anchor через CSS; координаты из JavaScript и динамическая запись визуальных свойств не требуются.
- Стили изолированы префиксом `.app-ui-*`; публичные селекторы и существующие классы экранов не затрагиваются.

Компоненты являются визуальными контрактами, а не новыми функциями. Разметка, сценарии, обработчики, маршруты, данные и доступность существующих действий не менялись.
