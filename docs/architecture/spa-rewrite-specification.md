**Статус:** консолидированная архитектурная спецификация, draft 2.0 — готова к комплексному рассмотрению владельцем; технологические ADR и production-проверки остаются отдельными контрольными воротами

## 1. Цель

Перевести Raymondovich.ru с MPA (набора независимых HTML-документов) на полноценное SPA с собственным маршрутизатором, сохранив существующие пользовательские сценарии, бизнес-правила, данные, безопасность и визуальную идентичность.

Задача не ограничивается созданием Router. Требуется переработать точки входа, маршрутизацию, жизненный цикл страниц, композицию интерфейса, загрузку модулей, управление состоянием, интеграционные границы, тестирование и документацию.

Новая архитектура должна стать устойчивой основой публичной платформы и закрытого Control Center.

## 2. Неизменяемые границы и правила работы

1. Вся разработка, рефакторинг, тестирование и исправления выполняются только в ветке architecture/spa-rewrite-2026-11-05 либо в согласованных вспомогательных ветках, созданных от неё.
2. main не изменяется в ходе разработки.
3. Merge, PR для интеграции, возврат на main и deployment выполняются только после прямого указания владельца.
4. Резервная ветка backup/pre-spa-rewrite-2026-11-05 сохраняется без изменений.
5. Репозиторий raymondovich.online не входит в область работ.
6. Production Supabase, Auth settings, таблицы, данные, RLS, grants, Edge Functions, DNS, Cloudflare, домены и hosting не изменяются без отдельного согласования.
7. Секреты, service-role keys, access tokens и иные учётные данные не добавляются в Git.
8. Нельзя удалять существующую функциональность только потому, что её неудобно переносить. До замены поведения необходимо описать его назначение, зависимости и пользовательский сценарий.
9. Если обнаружена неработающая или противоречивая функция, фиксируются факт, доказательства и варианты решения. Удаление не маскируется под рефакторинг.

Исполнитель имеет свободу выбирать архитектуру, структуру модулей, библиотеки и инструменты, если выбор обоснован, соответствует требованиям и не нарушает границы безопасности и production. Существенные решения фиксируются в ADR.

## 4. Целевая архитектура SPA

### 4.1. Application shell

Создать одну основную HTML-точку входа SPA — `index.html`. Shell отвечает за bootstrap, композицию приложения, подключение Router, корневой DOM-контейнер, общие стили и глобальную обработку ошибок. Отдельные HTML-файлы для внутренних страниц не являются частью целевой модели.

Публичная часть, Auth и Control Center могут иметь независимые layouts, но должны использовать согласованные общие механизмы.

### 4.2. Router

Реализовать единый Router на базе History API либо выбрать проверенную библиотеку по результатам ADR. Требования:
- централизованный реестр маршрутов;
- сопоставление статических и динамических сегментов пути;
- query string и hash;
- программная навигация;
- перехват только подходящих внутренних ссылок;
- поддержка popstate, Back и Forward;
- прямой вход по URL и refresh;
- 404 для неизвестного маршрута;
- обработка ошибок загрузки и рендеринга;
- защита от гонок при быстрой последовательной навигации;
- очистка обработчиков, подписок и ресурсов при уходе со страницы;
- корректное управление scroll и focus;
- сохранение стандартного поведения внешних ссылок, загрузок и специальных ссылок;
- безопасная обработка redirect target.

Router не содержит бизнес-логику, запросы Supabase, правила доступа к данным или разметку конкретных страниц.

### 4.3. Реестр маршрутов

Каждая запись маршрута должна явно определять:
- идентификатор и path/pattern;
- layout;
- lazy loader страницы, если применимо;
- требования доступа/guard;
- metadata: title, description, canonical, robots;
- политику scroll/focus при необходимости.

Нельзя распределять сопоставление URL по случайным обработчикам страниц.

### 4.4. Lifecycle и загрузка

Страница должна иметь определённые этапы mount, загрузки данных, отображения loading/empty/error/success, реакции на параметры URL и cleanup при уходе.

Code splitting применять по маршрутам или функциональным областям там, где это действительно уменьшает initial bundle. Не создавать абстракции без конкретной ответственности.

Состояние, которое должно переживать навигацию, хранить в URL, application/session state или backend согласно его семантике. Не полагаться на сохранение DOM предыдущей страницы.

### 4.5. Layouts

Минимально предусмотреть layouts:
- публичной части;
- аутентификации;
- закрытого Control Center.

Оболочка Control Center не должна знать внутреннюю реализацию каждого функционального раздела.

## 5. Целевая модель приложения и обязательный функциональный объём

### 5.1. Единая HTML-точка входа

Целевая архитектура использует одну основную HTML-точку входа — `index.html`. Она загружает SPA shell и bootstrap приложения. Все пользовательские страницы и разделы отображаются внутри приложения по маршрутам; отдельные HTML-документы для каждой страницы не создаются.

Маршруты являются адресуемыми состояниями одного приложения, а не самостоятельными HTML-точками входа. Их перечень и URL-контракт определяются централизованным реестром маршрутов.

### 5.2. Независимые функциональные модули

Функциональные области (например, публичная часть, Auth, Control Center, Ideas, Projects, Profile и Settings) проектируются как отдельные модули с чёткой ответственностью, публичными контрактами и контролируемыми зависимостями.

Требования:
- модуль не имеет права импортировать, вызывать или иным способом обращаться к внутренним файлам и внутренним реализациям другого модуля;
- межмодульное взаимодействие допускается только через публичный API целевого модуля либо через отдельно определённый общий application-контракт, если это предусмотрено архитектурой;
- наличие технической доступности файла или экспорта не означает разрешение обходить публичный контракт модуля;
- общие механизмы выносятся в соответствующие общие слои только при наличии реального повторного использования;
- не допускаются циклические зависимости, случайные глобальные переменные и взаимное управление DOM соседними страницами;
- lazy loading применяется по функциональным областям или маршрутам, если это даёт измеримую пользу.

### 5.3. Контролируемая координация и взаимодействие

Взаимодействие организуется через узкие точки координации с разделением ответственности:
- Router управляет URL, переходами и жизненным циклом маршрута;
- Application Layer координирует пользовательские и бизнес-сценарии через use cases и порты;
- отдельный функциональный модуль может иметь собственный controller/coordinator для координации своих компонентов и локального состояния;
- Infrastructure реализует интеграционные адаптеры и не управляет интерфейсом;
- Design System предоставляет визуальные компоненты и стили, не зависящие от бизнес-логики.

Не создавать один глобальный контроллер, который знает обо всех страницах, данных и функциях приложения. Такая точка стала бы монолитным узлом связности. Общие события или общее состояние вводятся только при обоснованной межмодульной потребности, с явно определённым контрактом и владельцем.

### 5.4. Инвентаризация существующей функциональности

Исходные HTML-файлы являются материалом для аудита и источником сведений о текущем поведении, контенте, сценариях, ссылках и интеграциях. Их количество и физическая структура не задают количество HTML-файлов или модулей новой архитектуры.

По результатам инвентаризации необходимо определить:
- какие пользовательские сценарии существуют фактически;
- какие функции должны быть сохранены без изменения поведения;
- какие страницы становятся маршрутами внутри SPA;
- какие элементы являются общими layouts или компонентами;
- какие старые URL требуют совместимости;
- какие функции дублируются, устарели, не работают или требуют отдельного решения владельца.

Нельзя автоматически переносить старую файловую структуру в новую. Структура целевого приложения определяется ответственностями и контрактами, а не расположением старых файлов.

### 5.5. Матрица функционального переноса

До удаления старых HTML и модулей составить матрицу:
- исходный файл/сценарий;
- целевой маршрут и функциональный модуль (если применимо);
- роль пользователя;
- действие;
- предусловия;
- ожидаемый результат;
- application use case и интеграции;
- ошибки и edge cases;
- подтверждающий тест.

Статусы: обнаружено, спроектировано, перенесено, проверено, заблокировано, исключено по согласованию.

### 5.6. Четыре пользовательских пространства платформы

Raymondovich.ru — единая платформа с четырьмя пользовательскими пространствами. Это не четыре отдельных приложения: пространства используют общую архитектурную основу, но имеют разные интерфейсы, маршруты, функции и правила доступа.

**Public — публичная презентация экосистемы.** Открытая часть предназначена для презентации Raymondovich, собственных продуктов, партнёрских и допущенных сторонних проектов, условий сотрудничества и привлечения участников. Просмотр публичной информации не требует авторизации и не предоставляет доступ к закрытым данным или инструментам проектов.

**Owner Control Center — административное пространство владельца.** Закрытая точка управления всей экосистемой. Владелец управляет идеями, проектами, пользователями, партнёрами, сторонними проектами, назначениями, полномочиями, подключаемыми модулями, инфраструктурой и общими показателями экосистемы. Создание, подключение и публикация проектов контролируются владельцем или явно уполномоченной административной стороной. Самостоятельное создание и публикация проектов обычными пользователями в текущей модели не предусматриваются; возможность пересмотра этого ограничения в будущем сохраняется.

**Partner Workspace — пространство партнёра.** Предназначено для участников, совместно с Raymondovich разрабатывающих или развивающих продукты. Для каждого подключённого проекта предусматриваются четыре базовые функциональные категории:
- **Accounting** — бухгалтерия и финансовые сведения проекта;
- **Services** — связанные сервисы и инфраструктура: домены, хостинг, серверы, репозитории и внешние платформы;
- **Analytics** — статистика и показатели проекта, включая доступные просмотры, посещения и другие метрики;
- **Marketing** — маркетинговые инструменты, продвижение и связанные показатели.

Наличие базовой категории не означает, что все её функции уже реализованы или доступны каждому участнику. Видимость данных и доступность операций определяются назначенными правами. Владелец платформы может дополнительно подключать индивидуальные рабочие модули под задачи конкретного проекта.

**External Project Workspace — пространство владельца стороннего проекта.** Предназначено для владельцев внешних продуктов, прошедших рассмотрение и подключённых к экосистеме на согласованных условиях. Начальный набор функций может включать управление реферальными ссылками, промокодами и статистикой привлечённого трафика. Архитектура должна позволять расширять пространство дополнительными модулями.

### 5.7. Единая учётная запись и множественные типы участия

Все пространства используют единую систему идентификации и авторизации. Один пользователь имеет одну учётную запись и может одновременно иметь несколько типов участия, например быть партнёром в одном проекте и владельцем подключённого стороннего проекта в другом.

Тип участия не является единственной взаимоисключающей глобальной ролью. Система поддерживает несколько независимых назначений и членств пользователя. Каждое назначение связано с конкретным пространством, проектом или областью платформы и имеет собственный набор полномочий.

### 5.8. Двухуровневая модель полномочий

Доступ определяется сочетанием глобальных полномочий пользователя (доступ к общим возможностям платформы и пространствам) и проектных полномочий (разрешённые действия и данные в контексте конкретного проекта).

Один пользователь может иметь разные права в разных проектах. Доступ к проекту не означает автоматический доступ ко всем его данным, финансам, сервисам или операциям. Полномочия определяются на уровне конкретных возможностей, а не только по названию роли.

Интерфейс может скрывать недоступные разделы и действия, но это не является границей безопасности. Проверки обязательны на application/use-case уровне и на серверной стороне. Для Supabase доступ к данным должен дополнительно обеспечиваться корректными RLS policies и другими серверными механизмами. Прямой URL или клиентский запрос не должен позволять обойти ограничения.

### 5.9. Общие и индивидуальные модули проектов

Project Control Center строится из двух типов модулей:
- **Платформенные модули** — общие функциональные возможности, которые могут подключаться к нескольким проектам; например, Accounting, Services, Analytics и Marketing.
- **Проектные модули** — функциональность для специфических процессов конкретного проекта, которая изначально может использоваться только им.

Проектная конфигурация определяет подключённые модули и их параметры, но не заменяет проверку полномочий. Перевод проектного модуля в платформенный статус возможен в будущем после появления реального повторного использования и отдельного архитектурного решения. Не создавать копии общих модулей для каждого проекта без обоснованной необходимости.

### 5.10. Переключение рабочих пространств

После единой авторизации система определяет пространства, доступные текущему пользователю. Если доступно одно пространство, оно может открываться непосредственно. Если доступно несколько, система открывает последнее использованное пространство либо предлагает выбрать доступное пространство при первом входе или отсутствии сохранённого выбора.

Пользователь переключается между разрешёнными пространствами без повторной авторизации. Последнее выбранное пространство может сохраняться как пользовательская настройка. Переключатель показывает только пространства, на которые у пользователя есть действующее назначение; смена пространства не расширяет полномочия и не отменяет повторную проверку доступа к проекту и операции.

Owner Control Center доступен только владельцу платформы и другим явно уполномоченным администраторам, если такая категория будет отдельно введена. Административный доступ не выводится из обычного партнёрского или внешнего проектного участия.

### 5.1. Control Center

Сохранить и перенести фактическое поведение:
- оболочка и навигация;
- Overview, Ideas и Projects;
- создание, просмотр, редактирование, архивирование и иные существующие операции;
- формы, валидация, подтверждения и уведомления;
- loading, empty, error и success states;
- переходы между связанными сущностями;
- профиль, настройки и выход.

Наличие нового экрана не доказывает перенос функциональности. Проверяются реальные операции и результат в данных.

### 5.2. Публичные страницы

Сохранить контент, ссылки, CTA, адаптивность, визуальные состояния и утверждённые бизнес-формулировки. Не менять позиционирование без отдельного согласования.

### 5.3. Матрица переноса

До удаления старых HTML и модулей составить матрицу:
- исходная страница/маршрут;
- роль пользователя;
- действие;
- предусловия;
- ожидаемый результат;
- application use case;
- интеграции;
- ошибки и edge cases;
- подтверждающий тест.

Статусы: обнаружено, перенесено, проверено, заблокировано, исключено по согласованию.

Это предварительный вариант. Окончательный контракт фиксируется после аудита внешних ссылок, Auth flows и SEO.

### 6.2. Совместимость старых URL

Для старых .html адресов выбрать и проверить стратегию: redirect, compatibility entry point или иной надёжный механизм. Нельзя удалять старые адреса без оценки внешних ссылок и обратной совместимости.

### 6.3. Hosting fallback

Исследовать фактическую цепочку DNS/CDN/hosting и проверить прямой запрос и refresh вложенного URL. Сравнить:
- GitHub Pages и его ограничения;
- 404.html fallback;
- Cloudflare Worker/Pages Functions или другой edge rewrite;
- иной static hosting с поддержкой SPA rewrites;
- гибридную стратегию с отдельными entry points.

Решение оформить ADR. Production DNS, Cloudflare и hosting не менять в рамках обычного rewrite.

### 6.4. SEO

Для публичных маршрутов определить уникальные title/description, canonical, robots, Open Graph metadata, sitemap и robots.txt. Проверить требования к индексации и social previews. Оценить ограничения client-side SPA; при необходимости рассмотреть prerendering, SSG, SSR или гибридную модель. Одного document.title недостаточно для полноценной SEO-стратегии.

## 7. Supabase Auth

Текущие URL, зафиксированные в snapshot:
- callback: https://raymondovich.ru/pages/auth/auth-callback.html
- recovery: https://raymondovich.ru/pages/auth/update-password.html

Не менять их в production без отдельного разрешения.

Сохранить сценарии:
- sign in и sign up;
- подтверждение email;
- callback/code exchange;
- password recovery и update;
- sign out;
- восстановление сессии после перезагрузки;
- истечение/обновление сессии;
- ошибки и повторный callback.

Callback должен обрабатываться до обычного protected-route redirect, чтобы не терять auth code и recovery parameters.

Route guards — UX-механизм, а не граница безопасности. Защита данных обеспечивается backend, RLS и grants.

Не использовать редактируемые user metadata для авторизации; учитывать обновление JWT claims после изменения app_metadata; не доверять role/owner_id из браузера; не раскрывать секретные ключи; не помещать токены в логи, аналитику или небезопасные URL.

## 8. Supabase Database и контракты данных

Supabase остаётся инфраструктурой, но не должен протекать в Domain/Application.

Требования:
1. SDK и сетевые запросы находятся в infrastructure adapters.
2. Application использует порты/контракты.
3. Presentation не обращается к Supabase напрямую.
4. Database DTO преобразуются во внутренние модели.
5. Сначала инвентаризировать миграции и data contracts.
6. Не утверждать, что миграции применены в production без проверки.
7. Не выполнять production migrations и не менять данные в рамках frontend rewrite.
8. Не менять таблицы Ideas/Projects, связи и статусы ради удобства новой архитектуры.

Расхождение документации Ideas/Projects с миграционной историей, указанное в snapshot, требует отдельного доменного решения и проверки фактической схемы.

Если возникнет необходимость DB change, подготовить отдельное предложение с причиной, схемой до/после, совместимостью, backfill, RLS/grants, тестами и rollback. Не применять автоматически.

## 9. Архитектура функциональных модулей

### 9.1. Базовая модель

Целевая модель приложения — **модульный монолит (Modular Monolith)** с принципами Clean Architecture и DDD.

Приложение остаётся единым развёртываемым продуктом, но его функциональные области имеют чёткие границы ответственности, собственные внутренние слои и контролируемые публичные контракты. Независимость модулей обеспечивается архитектурными правилами и проверками, а не отдельным deployment каждого модуля.

Структура строится в следующем порядке:
1. функциональные модули отражают предметные области и бизнес-ответственность;
2. внутри каждого модуля располагаются необходимые ему архитектурные слои;
3. общие механизмы размещаются в общих слоях только при наличии реальной общей ответственности;
4. приложение собирается в единое целое через App Composition Root.

### 9.2. Изоляция модулей и публичные API

Каждый функциональный модуль обязан предоставлять ограниченный публичный API — единственную разрешённую точку доступа к возможностям модуля со стороны других модулей.

**Обязательное правило:** один модуль не имеет права обращаться к внутренним файлам другого модуля. Запрещены прямые импорты внутренних путей, обращение к внутренним классам/функциям, чтение или изменение внутреннего состояния и обход публичного API через относительные пути или иные технические лазейки.

Требования:
- публичный API явно объявляется модулем, например через его `index.js` или иной согласованный entry point;
- экспортируются только те операции, типы и контракты, которые действительно нужны внешним потребителям;
- внутренние файлы, реализации, компоненты, репозитории и локальные координаторы остаются деталями реализации;
- изменение внутренней реализации не должно требовать изменений в других модулях, пока публичный контракт остаётся совместимым;
- модуль владеет своими внутренними правилами и состоянием; другой модуль не управляет ими напрямую;
- межмодульные сценарии координируются через Application Layer или явно определённые публичные контракты;
- циклические зависимости между модулями запрещены.

Публичный API — не формальность и не разрешение экспортировать всю внутреннюю структуру. Он должен быть минимальным и отражать реальные сценарии взаимодействия.

### 9.3. Внутренняя структура модуля

Внутри модуля используются слои Clean Architecture в объёме, оправданном его ответственностью:

- **domain** — сущности, value objects, инварианты и доменные правила;
- **application** — use cases, orchestration, порты и сценарии работы модуля;
- **infrastructure** — реализации портов и адаптеры к Supabase, browser APIs, network или storage, если они нужны модулю;
- **presentation** — страницы, компоненты и UI-координация, принадлежащие этому модулю;
- **index.js / public API** — публичная поверхность модуля для внешних потребителей.

Не каждый модуль обязан содержать все перечисленные каталоги. Не создавать пустые слои и файлы «на будущее». Размещение и глубина структуры определяются фактическими сценариями и ответственностью.

### 9.4. Композиция и взаимодействие

**App Composition Root** — место сборки приложения и связывания реализаций с контрактами. Он конфигурирует зависимости и передаёт модулям необходимые публичные интерфейсы. Он не должен превращаться в хранилище бизнес-логики.

Разделение ответственности:
- **Router** управляет URL, навигацией, сопоставлением маршрутов и lifecycle маршрута;
- **Application Layer** координирует сквозные пользовательские и бизнес-сценарии через use cases и порты;
- **Module Controller / Coordinator** координирует компоненты и локальное состояние внутри своего модуля;
- **Infrastructure** реализует технические адаптеры и не управляет пользовательским интерфейсом;
- **Design System** предоставляет визуальные токены и компоненты, не зависящие от бизнес-логики.

Запрещено создавать один глобальный контроллер, который знает внутреннее устройство всех модулей и напрямую управляет их состоянием или DOM. Общие события и общее состояние допускаются только при доказанной межмодульной необходимости; для каждого такого механизма должны быть определены контракт, владелец и правила жизненного цикла.

### 9.5. Общие слои и инфраструктура

Общая техническая инфраструктура не должна дублироваться без причины. Например, инициализация общего Supabase client может находиться в общей инфраструктуре, тогда как предметные repositories и преобразование DTO в модели принадлежат соответствующим модулям.

**Core** содержит только действительно общие технические типы, ошибки и контракты. Он не должен становиться зависимостью для хранения бизнес-логики всех модулей.

**Shared** допускается для небольших общих технических средств, если повторное использование подтверждено. Запрещено превращать его в универсальную свалку `utils`, `helpers`, `common` и несвязанных функций.

**Design System** изолирована от бизнес-слоёв. Бизнес-модули могут использовать её компоненты, но Design System не импортирует модули и не знает о предметных правилах.

### 9.6. Предварительная концептуальная структура

Следующая схема фиксирует направление организации, но не является окончательным деревом каталогов. Финальная структура будет уточнена после функциональной инвентаризации и проверки существующих исходников:

```text

├── app/
│   ├── bootstrap/
│   ├── composition/
│   ├── router/
│   └── layouts/
├── core/
│   ├── contracts/
│   ├── errors/
│   └── types/
├── modules/
│   ├── identity/
│   │   ├── domain/
│   │   ├── application/
│   │   ├── infrastructure/
│   │   ├── presentation/
│   │   └── index.js
│   ├── ideas/
│   ├── projects/
│   ├── partnerships/
│   ├── products/
│   ├── portfolio/
│   └── settings/
├── infrastructure/
│   ├── supabase/
│   ├── storage/
│   └── network/

Перечень модулей предварительный. Его нельзя считать решением о создании каждого из перечисленных модулей: границы и состав определяются аудитом существующей функциональности, доменных правил и реальных зависимостей. Структура не должна механически копировать старые каталоги или заранее создавать пустые модули.

### 9.7. Архитектурные ограничения и контроль

При реализации необходимо обеспечить проверяемое соблюдение границ:
- запрет импортов внутренних путей соседних модулей;
- отсутствие циклических зависимостей;
- соблюдение направления зависимостей Clean Architecture;
- отсутствие прямых обращений Presentation к Supabase;
- отсутствие зависимостей Domain от DOM, browser APIs и инфраструктуры;
- отсутствие зависимости Design System от бизнес-модулей.

Способ автоматической проверки (тесты архитектуры, lint rules или отдельный анализатор импортов) выбрать после определения фактического стека. До этого границы проверяются при code review и фиксируются в документации.

### 9.8. Принципы масштабирования

Новые функциональные модули выделяются тогда, когда существует самостоятельная предметная ответственность и реальная потребность в изоляции. Не дробить код на микромодули ради количества каталогов и не создавать универсальные абстракции без конкретных потребителей.

До рефакторинга Ideas/Projects отдельно разрешить доменное противоречие между описанием единой записи с жизненным циклом и фактической моделью отдельных таблиц `ideas` и `projects`, связанных через `source_idea_id`. Архитектурное решение по структуре модулей само по себе не разрешает менять эту модель данных.

Направление зависимостей внутри слоёв сохраняется: presentation → application → domain. Infrastructure реализует порты внутренних слоёв. Domain не импортирует внешние слои; Application не зависит от DOM, Supabase SDK и browser APIs. Циклические зависимости запрещены.


### 9.9. Целевая файловая структура репозитория и правила организации кода

Этот раздел определяет целевое размещение файлов и ответственность каталогов. Он конкретизирует архитектурную модель, не утверждая заранее frontend framework, bundler, state management library или конкретный способ deployment. Если после инвентаризации или ADR потребуется изменить дерево, изменение должно быть обосновано и отражено в архитектурной документации.

#### 9.9.1. Базовое дерево репозитория

Целевое дерево верхнего уровня:

```text

├── index.html
├── source/
│   ├── app/
│   │   ├── bootstrap/
│   │   ├── composition/
│   │   ├── router/
│   │   └── layouts/
│   ├── modules/
│   │   └── <functional-module>/
│   │       ├── domain/
│   │       ├── application/
│   │       ├── infrastructure/
│   │       ├── presentation/
│   │       └── index.js
│   ├── core/
│   │   ├── contracts/
│   │   ├── errors/
│   │   └── types/
│   ├── infrastructure/
│   │   ├── supabase/
│   │   ├── network/
│   │   └── storage/
│   ├── design/
│   │   ├── tokens/
│   │   ├── foundations/

Пустые директории, фиктивные модули и файлы-заглушки не создаются. Состав функциональных модулей определяется инвентаризацией и решениями по bounded contexts.

#### 9.9.2. Корневые файлы и каталоги

- **`index.html`** — единственная основная HTML-точка входа SPA. Содержит минимальную HTML-оболочку, корневой mount container и подключения, необходимые для запуска приложения. Бизнес-логика, реализация страниц и логика маршрутизации в него не помещаются.
- **`source/`** — исходный код приложения. Внутри находятся App Composition Root, Router, функциональные модули, общие технические слои и Design System.
- **`public/`** — только статические файлы, которые должны публиковаться или копироваться без прохождения через модульный исходный код: например, favicon, manifest, robots.txt, sitemap.xml и отдельные публичные ресурсы. Не размещать здесь исполняемую бизнес-логику или альтернативные HTML-точки входа. Фактический набор определяется hosting/SEO-решениями.
- **`tests/`** — сквозные, интеграционные и архитектурные тесты, которым нужна отдельная общая организация. Модульные unit-тесты могут располагаться рядом с тестируемым модулем, если выбранный тестовый стек и правила проекта это поддерживают. Не дублировать тесты в двух местах.
- **`docs/`** — архитектурные документы, ADR, функциональная инвентаризация, спецификации, инструкции и changelog. Документация не должна становиться местом хранения runtime-кода.
- **Конфигурационные файлы в корне** — только конфигурация реально выбранных и используемых инструментов: package manifest, lockfile, build/test/lint configuration и иные необходимые файлы. Они добавляются после технологического выбора и не должны заранее фиксировать неутверждённый стек.
- **`.github/`** — workflow и repository automation только после отдельной проверки текущего CI/CD и согласования целевого процесса. Наличие каталога не означает разрешение на deployment или изменение production pipeline.
- **Hosting-specific fallback/redirect files** — например, `404.html` или конфигурация rewrites — добавляются только после ADR по hosting и проверки реального поведения платформы. Они не заменяют Router и не считаются автоматически обязательными.

#### 9.9.3. Ответственность каталогов внутри source/

- **`app/bootstrap/`** — последовательность запуска приложения: подготовка runtime, инициализация необходимых общих механизмов и передача управления композиции приложения. Не содержит предметных бизнес-правил.
- **`app/composition/`** — Composition Root: создание экземпляров адаптеров и сервисов, связывание портов с реализациями, передача зависимостей публичным API модулей. Не становится глобальным хранилищем состояния или бизнес-логики.
- **`app/router/`** — Router, route registry, guards как UX-механизм, обработка навигации и lifecycle маршрутов. Не выполняет запросы к Supabase и не реализует доменные сценарии.
- **`app/layouts/`** — общие каркасы пользовательских пространств и компоновка верхнего уровня. Не содержит внутреннюю реализацию функциональных модулей.
- **`modules/<functional-module>/`** — отдельная предметная область с собственным внутренним устройством и публичным API. Внутренние файлы доступны только самому модулю; внешние потребители используют только публичный entry point.
- **`core/`** — минимальные общие технические контракты, базовые типы и ошибки, необходимые нескольким областям. Не размещать здесь бизнес-сущности конкретного модуля, универсальные сервисы без владельца или произвольные функции.
- **`infrastructure/`** — общие технические адаптеры и подключения к внешним системам, которые действительно используются несколькими модулями. Предметные repositories, mapping DTO и специфичные для домена адаптеры остаются внутри соответствующих модулей. Общий Supabase client может быть здесь; прямой доступ Presentation к нему запрещён.
- **`design/`** — Design System: токены, базовые визуальные foundations, переиспользуемые UI-компоненты и общие визуальные layout-паттерны. Не импортирует бизнес-модули и не содержит предметные правила.
- **`shared/`** — небольшие общие технические функции, для которых подтверждено повторное использование и не подходит более конкретный владелец. Не создавать свалочные каталоги `utils`, `helpers` или `common`; каждая функция должна иметь понятную ответственность.

#### 9.9.4. Правила размещения файлов

1. Каждый файл имеет одну основную ответственность и размещается рядом с кодом той области, которой он принадлежит.
2. Предметная логика принадлежит соответствующему функциональному модулю, а не Router, Design System или глобальному shared-каталогу.
3. Use cases и координация сценариев размещаются в Application Layer соответствующего модуля либо в отдельном application-уровне только для действительно сквозных сценариев.
4. UI-компоненты, страницы и локальные стили принадлежат модулю, который ими владеет. По-настоящему общие визуальные компоненты относятся к Design System.
5. Общие технические подключения не копируются по модулям; доменные адаптеры и преобразования данных не выносятся в общий слой только ради сокращения числа файлов.
6. Публичный API модуля объявляется явно. Запрещены импорты внутренних путей другого модуля, даже если они технически доступны.
7. Не создавать barrel-файлы, каталоги или абстракции без ясной цели. Публичный entry point модуля не должен автоматически экспортировать всю его внутреннюю структуру.
8. Не размещать секреты, локальные env-файлы с ключами, пользовательские данные, runtime-логи, временные выгрузки и артефакты сборки в репозитории.
9. Не хранить несколько конкурирующих реализаций одной функции после завершения миграции без документированной причины и срока удаления.
10. Имена каталогов и файлов должны быть последовательными и отражать назначение; соглашения о расширениях, именовании тестов и стиле импортов фиксируются после выбора toolchain.

#### 9.9.5. Что запрещено в целевой структуре

- возвращать отдельный HTML-файл для каждой внутренней страницы или пользовательского пространства;
- размещать бизнес-логику в `index.html`, Router, глобальных UI-компонентах или конфигурационных файлах;
- создавать один глобальный каталог, содержащий внутреннюю реализацию всех модулей;
- импортировать внутренние файлы соседних модулей или обходить их публичные контракты;
- дублировать общий infrastructure-код в каждом модуле без технической причины;
- превращать `core/` или `shared/` в универсальную зависимость для любого кода;
- заранее создавать пустые функциональные модули и слои;
- добавлять конфигурацию невыбранного framework/build tool или предполагать неподтверждённые возможности hosting.

#### 9.9.6. Порядок утверждения окончательного дерева

До создания новой структуры необходимо завершить инвентаризацию существующих файлов и функциональности. Затем:
1. сопоставить существующие исходники, сценарии и интеграции с целевыми областями ответственности;
2. определить фактические функциональные модули и их публичные контракты;
3. отделить код, который переносится, код, который заменяется, и код, требующий решения владельца;
4. уточнить hosting-specific файлы и toolchain после соответствующих ADR;
5. зафиксировать окончательное дерево и миграционную матрицу до массового переноса функциональности.

Утверждение этой целевой схемы не разрешает удалять старые файлы, менять production или начинать прикладную реализацию до выполнения согласованных этапов инвентаризации и архитектурных решений.

## 10. Design System

Создать единый источник:
- цветовых и типографических токенов;
- spacing scale;
- радиусов, теней и границ;
- кнопок, полей, карточек, диалогов;
- навигации;
- loading, empty, error и feedback states;
- адаптивных layout-паттернов.

Сохранить визуальную идентичность Raymondovich: тёмная основа, оранжевые акценты/градиенты, лаконичный премиальный интерфейс.

Не допускать необоснованного CSS-in-JS, дублирования компонентов, бизнес-логики в UI и случайного размножения inline CSS/JS. Проверять мобильные устройства и Safari.

## 11. Выбор стека и ADR

Не предписывать заранее конкретный framework или bundler. До реализации подготовить ADR по:
- vanilla ES modules против framework;
- собственный Router против библиотеки;
- build tool и code splitting;
- hosting/fallback;
- state management;
- CSS architecture;
- тестовому стеку;
- SEO/prerendering.

Критерии: поддерживаемость, безопасность, размер runtime/bundle, мобильная производительность, совместимость с hosting, тестируемость, простота сопровождения и отсутствие неоправданной сложности.

Если вводятся зависимости, фиксировать версии и lockfile.

### 11.1. Порядок выбора frontend-технологий

Конкретный frontend framework, bundler и сопутствующий технологический стек не выбираются до завершения архитектурного согласования, инвентаризации существующей функциональности и необходимой технической оценки.

Порядок принятия решения:
1. Завершить согласование целевой архитектуры и обязательных ограничений.
2. Провести инвентаризацию существующих страниц, сценариев, модулей, интеграций и текущего frontend-кода.
3. Проверить фактические ограничения hosting, URL routing/fallback, SEO, браузерной совместимости и доступной тестовой инфраструктуры.
4. Сформировать shortlist подходящих технологических вариантов.
5. Сравнить варианты по единым критериям: соответствие SPA и Modular Monolith, поддержка модульной изоляции и Clean Architecture, безопасность, производительность и размер клиентского bundle, совместимость с Supabase и hosting, тестируемость, доступность специалистов/документации и стоимость сопровождения.
6. Зафиксировать обоснованный выбор в отдельном ADR до начала реализации базовой SPA-платформы.

До принятия ADR запрещено считать какой-либо конкретный framework, bundler или state management library утверждённым решением. Инвентаризация должна быть технологически нейтральной и не подгоняться под заранее выбранный инструмент.

## 12. Управление состоянием и обработка ошибок

### 12.1. Модель управления состоянием

Состояние приложения разделяется по назначению и жизненному циклу. У каждого состояния должен быть один явно определённый владелец. Совместное использование данных несколькими областями не означает, что они должны копироваться в единое глобальное хранилище.

Категории состояния:

- **URL State** — маршрут и адресуемые параметры: query string, поиск, фильтры, сортировка, пагинация и другие состояния, которые должны восстанавливаться по ссылке и корректно работать с Back/Forward. URL является источником истины для таких значений; не следует дублировать их в независимом глобальном store.
- **Module State** — состояние, принадлежащее конкретному функциональному модулю: данные активного сценария, состояние редактора, локальные выборы и другие значения, необходимые только этому модулю. Внутреннее состояние недоступно другим модулям напрямую.
- **Application State** — минимальный набор действительно общих состояний, используемых несколькими областями приложения, например глобальные настройки интерфейса, состояние shell или глобальные уведомления, если их общая природа подтверждена. Общие данные должны иметь одного владельца и предоставляться через определённый контракт.
- **Session State** — состояние авторизации и текущей пользовательской сессии. Ответственность за него изолируется в Identity/Auth Module. Состояние клиента не является механизмом авторизации или контроля доступа: доступ к данным должен обеспечиваться серверной стороной и соответствующими политиками Supabase RLS.
- **Persistent State** — данные, которые должны переживать перезагрузку или быть доступны на разных устройствах. Постоянные бизнес-данные (идеи, проекты, партнёрства и другие записи) имеют серверное хранилище в качестве источника истины. Клиентский кэш и браузерные хранилища могут применяться для UX и производительности, но не подменяют серверный источник истины.

### 12.2. Владение и размещение состояния

- У каждого состояния есть один владелец: Router, функциональный модуль, UI-компонент, Identity/Auth Module либо явно определённый application-level сервис.
- Локальное временное UI-состояние (например, открытая модальная панель или несохранённый ввод) остаётся у компонента или модуля, которому оно принадлежит.
- Модули не читают и не изменяют внутреннее состояние друг друга. Межмодульный доступ возможен только через публичный API соответствующего модуля или отдельно определённый application-контракт.
- Application Layer координирует сквозные бизнес-сценарии, затрагивающие несколько модулей. Координация не переносит владение данными одного модуля к другому и не создаёт глобальный универсальный store.
- Supabase и другие серверные адаптеры относятся к Infrastructure. Предметные данные и правила остаются в соответствующих модулях.
- Выбор между localStorage, sessionStorage, IndexedDB и cookies делается по конкретной задаче, сроку жизни и чувствительности данных. Не сохранять чувствительные данные в браузерном хранилище без отдельного обоснования безопасности.
- При logout и завершении/смене сессии очищаются относящиеся к пользователю кэши и временные данные; данные предыдущего пользователя не должны оставаться доступными в интерфейсе следующей сессии.

### 12.3. Жизненный цикл и согласованность

Предусмотреть:
- очистку временного состояния при завершении соответствующего сценария или lifecycle маршрута;
- отмену запросов, ставших неактуальными после навигации или смены параметров;
- защиту от stale responses и гонок при быстрых действиях пользователя;
- согласованные правила кэширования и invalidation после мутаций;
- защиту от повторной отправки операций там, где дублирование может привести к некорректному результату;
- подтверждение серверного сохранения до отображения окончательного успешного результата;
- централизованную очистку пользовательских кэшей при logout.

### 12.4. Выбор State Management Library

Конкретная библиотека управления состоянием не предписывается заранее. Необходимость и выбор Redux, Zustand или альтернативы определяются отдельным ADR после функциональной инвентаризации, определения стека и анализа фактических межмодульных сценариев. Нельзя вводить библиотеку только по причине перехода на SPA. Архитектурные контракты и владение состоянием должны оставаться независимыми от выбранной библиотеки.

### 12.5. Обработка ошибок

Обработка ошибок должна локализовать отказ в минимально необходимой области и сохранять работу независимых частей платформы.

#### 12.5.1. Изоляция ошибок

Ошибки изолируются между четырьмя пространствами (Public, Owner Control Center, Partner Workspace, External Project Workspace), а также между проектами, модулями, маршрутами и независимыми бизнес-сценариями. Ошибка отдельного раздела Owner Control Center не отключает весь центр; ошибка одного проекта или его модуля не блокирует другие проекты партнёра; отказ одного внешнего проекта не нарушает работу остальных.

Отказ общего компонента оценивается по радиусу воздействия. Независимая функциональность продолжает работать, если это безопасно. Если нельзя надёжно проверить сессию или полномочия, закрытые пространства блокируются. Обход авторизации и небезопасный fallback запрещены.

#### 12.5.2. Уровни восстановления

Система выбирает наименьший достаточный уровень:
1. Автоматическое восстановление — повтор безопасно повторяемой операции при временном сбое.
2. Локальное восстановление — перезагрузка конкретного модуля, раздела, маршрута или проектного контекста без перезапуска всего приложения.
3. Полное восстановление — перезапуск SPA только если нарушена работоспособность application shell, Router или runtime и локального восстановления недостаточно.

Восстановление не должно создавать бесконечные циклы, дублировать записи или скрывать устойчивую ошибку. Результат фиксируется.

#### 12.5.3. Пользовательское сообщение и техническая диагностика

Пользователь получает понятное сообщение, безопасное объяснение и доступное действие. Отдельная техническая диагностика содержит тип и источник ошибки, пространство, проект, модуль, маршрут, время, correlation ID, затронутые зависимости, историю попыток и результат восстановления.

Пользовательский интерфейс не раскрывает приватные данные и опасные внутренние детали инфраструктуры. Логи не содержат пароли, токены, секреты или чувствительные пользовательские payload.

#### 12.5.4. Классификация

- INFO — информационное событие; регистрация без обязательного уведомления.
- WARNING — некритичная проблема/деградация при сохранении функциональности; регистрация и наблюдение.
- ERROR — отказ функции, модуля или бизнес-сценария; локальная обработка и восстановление.
- CRITICAL — отказ критического компонента либо угроза безопасности/целостности данных; приоритетная реакция и уведомление владельца.

Критичность определяет приоритет обработки, логирования и уведомлений с учётом фактического влияния.

#### 12.5.5. Политика автоматических повторов (Retry Policy)

Повторяются только безопасные операции. Число попыток ограничено; интервалы увеличиваются по exponential backoff (при необходимости с jitter). Ошибки авторизации, недостатка прав и валидации автоматически не повторяются. Операции записи защищаются idempotency keys или эквивалентным механизмом от дублирования, когда это применимо. Если неизвестно, была ли операция зафиксирована, повтор допускается только после проверки результата либо обеспечения идемпотентности. Точные лимиты и классификация ошибок определяются отдельным ADR/реализационным решением.

#### 12.5.6. Частичный отказ сквозных сценариев

Application Layer фиксирует успешные, неуспешные и неподтверждённые шаги сценария. Система не оставляет данные в неопределённом или противоречивом состоянии. Выполняется откат, если он технически и семантически безопасен; иначе сохраняется явно определённое согласованное промежуточное состояние. Сценарий должен поддерживать безопасное продолжение или повтор без дублирования эффектов. Транзакции и компенсационные действия (включая Saga Pattern) выбираются по характеру сценария; атомарный откат независимых систем без общей транзакции не предполагается.

#### 12.5.7. Общие критические компоненты

Отказы Identity/Auth, Router, Application Core и общей Infrastructure оцениваются по зависимостям и радиусу воздействия. Ошибка отдельного маршрута или необязательного инфраструктурного сервиса не должна блокировать независимые функции. Публичная презентация продолжает работать при отказе Auth-зависимого сценария, если сама от него не зависит. При невозможности безопасной проверки авторизации закрытый доступ блокируется.

#### 12.5.8. Мониторинг и уведомления

Owner Control Center предоставляет единый мониторинг ошибок и инцидентов по четырём пространствам: затронутые проекты/модули/зависимости, критичность, повторяемость, ход восстановления и история. Недоступность необязательного мониторинга не должна останавливать основные сценарии.

INFO регистрируется без уведомления по умолчанию; WARNING уведомляет при существенной деградации; ERROR — с учётом влияния и повторяемости; CRITICAL требует приоритетного уведомления. Повторяющиеся одинаковые события и уведомления группируются/подавляются по правилам, но история инцидента, изменения состояния и факт восстановления сохраняются.

### 12.6. Проверки работоспособности (Health Checks)

Health Checks определяют фактическое состояние компонентов и необходимых зависимостей. Доступность endpoint сама по себе не доказывает корректность всех функций сервиса.

#### 12.6.1. Статусы компонентов

- HEALTHY — компонент работает штатно.
- DEGRADED — компонент работает частично или с ограничениями.
- UNAVAILABLE — компонент недоступен либо не может безопасно выполнять основную функцию.
- RECOVERING — выполняется восстановление после подтверждённого сбоя.

#### 12.6.2. Способы запуска

Предусматриваются:
- плановые проверки по расписанию;
- событийные проверки после ошибки или признака существенной деградации;
- ручной запуск владельцем из Owner Control Center для компонента, группы компонентов или всей платформы.

Постоянный интенсивный опрос всех компонентов не допускается. При штатной работе без сигналов об ошибках достаточно планового графика; внеплановые углублённые проверки запускаются по событию или вручную. Событийные проверки ограничиваются cooldown/debounce и лимитами частоты, чтобы избежать шторма проверок.

#### 12.6.3. Периодичность и нагрузка

Периодичность централизованно настраивается по критичности: критические компоненты проверяются чаще, обычные — умеренно, некритичные — редко. Конкретные интервалы определяются после инвентаризации компонентов и оценки нагрузки. Проверки должны иметь таймауты, ограничение параллелизма, защиту от наложения одинаковых запусков и каскадного старта. Лёгкие проверки доступности отделяются от глубоких функциональных проверок; тяжёлые интеграционные/E2E проверки не запускаются чаще необходимого.

#### 12.6.4. Подтверждение сбоя

Первая неудачная проверка фиксирует подозрение, но обычно не переводит компонент сразу в UNAVAILABLE. Выполняется повторная проверка. Успешный повтор снимает подозрение, сохраняя запись о кратковременном сбое. Подтверждённый сбой переводит компонент в DEGRADED или UNAVAILABLE по фактическому влиянию. Критические угрозы безопасности и целостности данных требуют немедленных защитных действий без ожидания повторного подтверждения.

#### 12.6.5. Приоритет диагностики и восстановления

1. Безопасность и целостность данных.
2. Identity/Auth и критические системные компоненты.
3. Router и Application Core.
4. Общие инфраструктурные сервисы.
5. Отдельные функциональные модули.
6. Некритичные дополнительные сервисы.

Приоритет определяет очередность диагностики/восстановления, но не требует останавливать независимые компоненты.

#### 12.6.6. История и хранение

Owner Control Center хранит дату/время, компонент и пространство/проект, итоговый статус, проблемы и затронутые зависимости, длительность, способ запуска (плановый/событийный/ручной), correlation ID и результат восстановления. Подробные результаты хранятся 90 дней. Далее записи агрегируются в долгосрочный архив со сводной статистикой доступности, динамикой стабильности и историей серьёзных инцидентов.

#### 12.6.7. Уведомления о результатах

HEALTHY — запись в историю без уведомления по умолчанию; DEGRADED — уведомление при существенном ухудшении; UNAVAILABLE — обязательное уведомление владельца; RECOVERING — отображение в мониторинге и уведомление при значимом изменении/затяжном восстановлении; успешное восстановление после подтверждённого инцидента — уведомление. Повторяющиеся уведомления группируются/подавляются с сохранением истории.

#### 12.6.8. Безопасность проверок

Проверяющая подсистема не должна выполнять изменяющие бизнес-данные операции. Если проверке необходима запись/мутация, используется изолированный тестовый контур или специально предусмотренный безопасный механизм. Проверки имеют ограниченные полномочия и не должны становиться источником перегрузки.


### 12.7. Журнал ошибок и техническая диагностика

Система ведёт подробную историю ошибок и связанных технических событий, достаточную для расследования причин сбоев и восстановления последовательности выполнения.

Для диагностических событий, где применимо, фиксируются:
- дата и время;
- компонент, функциональный модуль, пространство и проект;
- тип, категория и критичность события;
- этап выполнения и безопасный технический контекст;
- stack trace и сведения о задействованных зависимостях;
- correlation ID и идентификаторы связанного инцидента;
- результат операции и известная причина сбоя.

Связанные события объединяются в историю инцидента. В ней отражаются первоначальное обнаружение, изменение статусов, затронутые компоненты, попытки восстановления и итог.

Журналы не должны содержать пароли, токены, ключи, секреты, платёжные реквизиты и иные чувствительные данные. Перед записью применяются фильтрация и редактирование чувствительных значений. Диагностический контекст должен быть достаточным для расследования, но не раскрывать содержимое пользовательских данных без необходимости.

Системные журналы и полная техническая диагностика доступны только владельцу платформы. Другие пользователи не получают доступ к глобальным журналам и могут видеть только специально разрешённую информацию, относящуюся к их рабочей области, если такая функция будет предусмотрена отдельно.

Конкретные сроки хранения подробных журналов ошибок, правила архивирования и очистки определяются отдельным решением с учётом требований безопасности, объёма данных и применимых ограничений. Срок 90 дней, установленный для подробной истории Health Checks, автоматически на журналы ошибок не распространяется.

### 12.8. Уведомления об ошибках и инцидентах

Предусматриваются два канала уведомлений владельца:
1. Owner Control Center — централизованный интерфейс уведомлений, инцидентов и их истории.
2. Telegram — оперативные уведомления о значимых ошибках, критических сбоях и существенных изменениях состояния, включая подтверждённое восстановление.

Email как канал системных уведомлений в текущую архитектуру не включается.

В Owner Control Center предусматриваются настройки:
- включение и отключение категорий уведомлений;
- минимальная критичность для отправки в Telegram;
- раздельное управление уведомлениями об ошибках и восстановлении;
- ограничение частоты повторных уведомлений;
- просмотр истории отправки и ошибок доставки.

Настройки уведомлений управляют доставкой сообщений, но не регистрацией и хранением самих событий. Повторяющиеся события могут группироваться и подавляться по правилам, при этом история инцидента, изменения состояния и факт восстановления сохраняются.

Недоступность Telegram не должна приводить к потере инцидента: событие сохраняется в системе и остаётся доступным в Owner Control Center. Доставка уведомлений должна быть отделена от компонента, отказ которого вызвал инцидент.

### 12.9. Независимость журналирования и мониторинга

Регистрация ошибок, аудит и накопление событий не должны зависеть от доступности интерфейса Owner Control Center. При недоступности Control Center система продолжает собирать события и, если доступен канал, отправлять критические уведомления через Telegram.

После восстановления Control Center накопленная история становится доступна владельцу. Предусматривается резервный механизм регистрации на случай отказа основного механизма журналирования — в пределах технических возможностей инфраструктуры.

Синхронизация накопленных событий после восстановления должна предотвращать потерю и дублирование записей. Доставка уведомлений и долговременное сохранение диагностических данных рассматриваются как независимые процессы.

### 12.10. Защита журналов и полномочия владельца

Raymondovich.ru имеет единственного владельца — пользователя, которому принадлежит платформа и который обладает исключительными глобальными полномочиями владельца, главного администратора и управляющего всей платформой.

Только владелец имеет полный доступ к управлению платформой и ко всей глобальной административной и системной информации, включая настройки, проекты и пространства, пользователей и назначения, системную инфраструктуру, общие показатели, журналы ошибок, историю инцидентов, аудит и техническую диагностику.

Полномочия остальных пользователей ограничиваются явно назначенными им правами и областью ответственности. Доступ к одному проекту или продукту не предоставляет доступ к другому проекту, его данным или управлению. Проектные полномочия не предоставляют глобального управления платформой. Полная изоляция должна обеспечиваться серверной авторизацией и политиками доступа к данным, а не только ограничениями интерфейса.

Системные журналы, глобальные инциденты и полная техническая диагностика доступны только владельцу. Записи аудита и системных журналов защищаются от незаметного изменения. Изменение или удаление записей не должно быть доступно обычными пользовательскими операциями; административные операции над журналами, архивированием и очисткой сами подлежат регистрации. Архивирование и очистка выполняются только по утверждённым правилам хранения.

### 12.11. Режимы работоспособности платформы

Состояние платформы и её интерфейсов учитывает три режима:
- NORMAL — штатная работа доступных компонентов и пространств.
- DEGRADED — ограниченная работоспособность: неисправные компоненты изолируются, независимые компоненты и пространства продолжают работу.
- PROTECTIVE — защитный режим при угрозе безопасности или целостности данных либо при невозможности безопасно подтвердить авторизацию.

Переход в режим определяется фактическим состоянием компонентов и риском. В PROTECTIVE блокируются опасные операции и ограничивается доступ к затронутым закрытым функциям. Публичная часть продолжает работу, если её собственные зависимости не затронуты. Выход из защитного режима допускается после подтверждения безопасности и восстановления необходимых компонентов.

Режимы платформы не отменяют локальную изоляцию: область ограничений должна соответствовать фактическому радиусу воздействия, если более широкая блокировка не требуется для безопасности.

### 12.12. Аудит действий пользователей и история изменений

Система регистрирует значимые действия безопасности и управления, в том числе:
- входы и выходы из системы, а также неудачные попытки доступа;
- создание, изменение и удаление проектов и иных значимых объектов;
- изменение настроек и полномочий;
- административные операции;
- доступ к чувствительным данным и попытки несанкционированного доступа.

Обычные действия интерфейса, не имеющие значения для безопасности или управления (например, каждое нажатие или перемещение по экрану), не должны создавать избыточный аудит.

Для значимых изменений сохраняются объект и операция, состояние до изменения и после него, исполнитель, дата и время, а также результат. История изменений связывается с Audit Log и, где применимо, с соответствующим инцидентом через идентификаторы корреляции.

Пароли, токены, секреты и иные чувствительные значения не записываются в историю изменений. Если объект содержит чувствительные поля, они исключаются или редактируются до сохранения снимка состояния.

Подробная история аудита действий и изменений хранится один год, после чего переносится в архив. Критические события безопасности и административные инциденты хранятся дольше; конкретный срок и правила архивирования для них определяются отдельно. Архивирование и очистка выполняются автоматически по утверждённым правилам с регистрацией соответствующих операций.

### 12.13. Резервное копирование и восстановление

Для критически важных данных предусматривается регулярное резервное копирование. Резервные копии хранятся отдельно от основной системы и защищаются от несанкционированного доступа, изменения и удаления.

Требования:
- шифрование резервных копий при хранении и передаче;
- ограничение доступа по принципу минимально необходимых полномочий;
- защита от незаметного изменения и удаления;
- проверка целостности после создания и перед восстановлением;
- раздельное хранение основной системы и резервных копий;
- регистрация операций создания, проверки, восстановления, архивирования и удаления копий.

Возможность восстановления на определённый момент времени (point-in-time recovery) предусматривается там, где её поддерживает выбранная инфраструктура и она обоснована требованиями к данным.

Создание резервной копии само по себе не считается подтверждением возможности восстановления. Необходимы регулярные проверки и тестовые восстановления в изолированной среде. Проверки не должны затрагивать production-данные.

Конкретные технологии, периодичность резервного копирования, сроки хранения и процедуры восстановления определяются после инвентаризации инфраструктуры.

### 12.14. Цели восстановления (RPO / RTO)

Для данных и компонентов определяются:
- RPO (Recovery Point Objective) — максимально допустимая потеря данных, выраженная временем;
- RTO (Recovery Time Objective) — целевое максимально допустимое время восстановления.

Для критически важных данных и системных компонентов устанавливаются более строгие целевые показатели, чем для обычных функциональных модулей. Показатели могут различаться для Public, Identity/Auth, Owner Control Center и проектных пространств с учётом их критичности и зависимостей.

Конкретные значения RPO и RTO устанавливаются после инвентаризации инфраструктуры, оценки рисков, технических возможностей и стоимости реализации. Фактическое соблюдение показателей проверяется тестовыми восстановлениями; результаты фиксируются.

### 12.15. Реагирование на инциденты безопасности

При обнаружении подозрительной активности или признаков компрометации предусматривается последовательность:
1. **Обнаружение** — регистрация сигнала и сбор безопасного диагностического контекста.
2. **Изоляция** — ограничение затронутого аккаунта, компонента, проекта или иной области.
3. **Защита** — блокировка потенциально опасных операций и применение необходимых защитных мер.
4. **Уведомление** — информирование владельца через Owner Control Center и Telegram в соответствии с критичностью.
5. **Расследование** — сохранение и анализ технических доказательств и последовательности событий.
6. **Восстановление** — возврат функций и доступа после проверки безопасности.
7. **Анализ** — фиксация причины, последствий и мер по предотвращению повторения.

Изоляция должна быть адресной и соответствовать радиусу воздействия. Независимые проекты и компоненты продолжают работу, если это безопасно. При угрозе общей инфраструктуре, безопасности или целостности данных допускаются более широкие защитные ограничения. Все существенные действия по реагированию и восстановлению регистрируются.



### 12.16. Производительность и масштабирование

Архитектура должна поддерживать постепенный рост числа пользователей, проектов, функциональных модулей и объёма операций без необходимости полной перестройки платформы.

Обязательные принципы:

- **Независимость модулей.** Рост нагрузки на отдельный функциональный модуль не должен требовать изменения архитектуры остальных модулей. Границы модулей и их публичные контракты должны позволять оптимизировать и при необходимости масштабировать отдельные области независимо в пределах возможностей выбранной инфраструктуры.
- **Изоляция нагрузки.** Тяжёлые операции одного проекта или функциональной области не должны без необходимости блокировать или существенно замедлять работу других проектов и независимых областей платформы. Следует учитывать ограничения параллелизма, очереди, лимиты внешних сервисов и ресурсы общих компонентов.
- **Оптимизация загрузки.** Клиент должен загружать только необходимые для текущего маршрута и сценария код, данные и ресурсы. Применять route-level или module-level code splitting, lazy loading, кэширование и другие оптимизации при наличии измеримой пользы и без нарушения безопасности или актуальности данных.
- **Асинхронное выполнение.** Длительные и ресурсоёмкие операции не должны блокировать основной пользовательский поток или критический путь интерфейса. Для таких операций предусматривать асинхронное выполнение, понятные статусы, обработку ошибок, отмену или безопасное завершение по правилам конкретного сценария.
- **Контроль ресурсов и производительности.** Предусмотреть сбор и анализ показателей производительности клиентской части, серверных операций и критичных интеграций. Мониторинг должен помогать выявлять узкие места, деградацию и аномальную нагрузку; сбор данных не должен раскрывать секреты или избыточные персональные данные.
- **Запас для роста.** Новые пользователи, проекты и функциональность должны подключаться через существующие архитектурные контракты и согласованные механизмы расширения, а не требовать переписывания всей платформы.

Конкретные целевые показатели (например, время загрузки, Core Web Vitals, latency критичных операций, допустимая конкурентная нагрузка, объём данных и время фоновых задач), пороги предупреждений и методы нагрузочного тестирования определяются после инвентаризации функциональности и технического аудита инфраструктуры. Значения должны быть измеримыми, привязанными к реальным пользовательским сценариям и проверяться в тестовой среде.

Независимое масштабирование на уровне модулей является архитектурным требованием к изоляции и оптимизации, но само по себе не означает обязательного перехода к микросервисам или отдельному развёртыванию каждого модуля. Платформа сохраняет согласованную модель модульного монолита, пока результаты измерений и реальные ограничения не обоснуют иное.

### 12.17. Политика кэширования и актуальности данных

Supabase и соответствующие серверные источники остаются источником истины для постоянных бизнес-данных. Клиентский кэш предназначен для ускорения интерфейса и снижения повторных запросов; он не становится самостоятельным источником истины и не должен подменять подтверждённое серверное состояние.

Обязательные правила:

- **Назначение кэша.** Кэшировать только данные, для которых определены владелец, область действия, допустимый срок актуальности и правила обновления. Стратегия выбирается по типу данных и пользовательскому сценарию; универсальный бессрочный кэш не допускается.
- **Обновление после мутаций.** После успешного создания, изменения или удаления записи кэш затронутых сущностей и связанных представлений должен быть обновлён либо инвалидирован. Интерфейс не должен продолжать показывать заведомо устаревшее значение как подтверждённое актуальное состояние.
- **Конкурирующие запросы.** При повторной загрузке, быстрой навигации, смене фильтров или параметров предотвращать применение устаревшего ответа поверх более нового состояния. Использовать отмену запросов, идентификаторы запросов, версии или эквивалентные механизмы по необходимости.
- **Смена пользователя и полномочий.** Кэш должен быть изолирован по пользователю, сессии и необходимому проектному контексту. При logout, смене аккаунта или изменении контекста доступа соответствующие записи очищаются или повторно проверяются; данные предыдущей сессии не должны отображаться следующему пользователю.
- **Потеря соединения и неопределённость.** Пользователь должен получать ясное сообщение, когда данные не удалось обновить или серверное сохранение не подтверждено. Кэшированные данные при необходимости могут быть показаны как последние известные, но их статус и время актуальности должны быть обозначены. Нельзя сообщать об успешном сохранении без подтверждения сервера.
- **Чувствительные данные.** Не сохранять чувствительные данные в localStorage, sessionStorage, IndexedDB, Cache API или иных долговременных браузерных хранилищах без отдельного обоснования, оценки угроз и согласованного решения по безопасности. Кэширование не должно обходить серверную авторизацию и RLS.
- **Срок жизни и очистка.** Для каждого вида кэшируемых данных определить TTL либо событийное условие инвалидирования, максимальный объём и поведение при ошибке обновления. При logout и завершении сессии очищать пользовательские кэши и временные данные в соответствии с их областью действия.
- **Проверка согласованности.** Критичные сценарии записи и последующего чтения должны проверяться на подтверждение серверного результата, отсутствие дублирования, корректную invalidation и защиту от stale responses.

Конкретная библиотека и техническая стратегия кэширования не выбираются заранее. Они определяются после инвентаризации сценариев и выбора frontend-стека, с учётом безопасности, сложности данных и измеримой пользы.

# Часть II. Полная инфраструктурная спецификация платформы

> Эта часть консолидирует инфраструктурные требования. Она описывает целевую модель и обязательные ограничения, но не означает, что перечисленные сервисы уже созданы или включены. Технологические продукты, тарифы, конкретные значения лимитов и production-конфигурация фиксируются только после соответствующих ADR и отдельного разрешения владельца.

## 13. Архитектурный контур всей платформы

### 13.1. Логические уровни

Платформа разделяется на логические уровни:

1. Client / Presentation — SPA shell, маршруты, layouts, UI-компоненты, формы, доступность и локальное UI-состояние.
2. Application — use cases, orchestration, проверка предусловий, координация транзакций, порты и защита от повторных операций.
3. Domain — сущности, value objects, инварианты, доменные политики и события.
4. Infrastructure adapters — Supabase client, repositories, storage adapters, network clients, telemetry, notification delivery и внешние интеграции.
5. Backend platform — Supabase Auth, PostgreSQL, RLS, database functions/RPC, Edge Functions при обоснованной необходимости, storage и фоновые задачи при наличии соответствующей потребности.
6. Delivery / Hosting — source control, build pipeline, immutable build artifacts, staging и production deployments, CDN/hosting, DNS/TLS.
7. Operations / Governance — monitoring, health checks, audit, incident response, backups, restore, access governance и change control.

Это логические границы, а не обязательное разбиение на отдельные физические серверы или микросервисы. Базовая модель — модульный монолит на клиенте и управляемая backend-инфраструктура. Выделение отдельных сервисов допускается только при измеримой необходимости.

### 13.2. Системные границы

- Browser UI не является доверенной средой.
- Клиент не является источником истины для прав, ролей, владельца записи и критических атрибутов.
- Application Layer обращается к внешним системам только через объявленные порты.
- Infrastructure не принимает доменные решения.
- Backend enforcement обязателен для операций с закрытыми данными.
- Публичные и закрытые данные имеют различимые политики доступа.
- Каждая внешняя интеграция имеет владельца, контракт, scope разрешений, таймаут, обработку ошибок, правила логирования и процедуру отключения.
- Отказ необязательной интеграции не останавливает независимые пространства.

## 14. Backend, API и серверные операции

### 14.1. Роль Supabase

Supabase является текущей backend-платформой Raymondovich.ru. Компоненты используются по назначению:

- Auth — идентификация и управление сессиями;
- PostgreSQL — постоянные бизнес-данные и транзакционная целостность;
- RLS — серверная авторизация на уровне строк;
- SQL functions/RPC — атомарные операции и серверные бизнес-переходы, когда это оправдано;
- Edge Functions — защищённые операции и интеграции, которые нельзя безопасно выполнять в браузере;
- Storage — только при подтверждённой потребности в хранении файлов;
- scheduled/background mechanisms — для фоновых задач, мониторинга, уведомлений и архивирования, если выбранная инфраструктура их поддерживает.

Наличие функции или сервиса в этой архитектуре не означает, что компонент уже создан, настроен или используется в production.

### 14.2. API contracts

Каждая операция Application Layer имеет контракт: назначение/use case ID, входная схема и валидация, пользовательский и проектный контекст, предусловия и permissions, результат, типизированные ошибки, идемпотентность, побочные эффекты, требования к транзакционности, correlation ID и тестовые сценарии.

Внешние ответы и строки БД не передаются напрямую в UI как универсальные объекты. Infrastructure mapping преобразует DTO в типизированные внутренние модели и обратно.

### 14.3. Серверная авторизация

UI guards нужны для навигации и UX, но не для защиты данных. Каждая закрытая операция проверяется сервером через RLS, безопасную database function или Edge Function с корректной проверкой пользователя и полномочий.

Запрещено:
- считать скрытую кнопку защитой;
- доверять переданному клиентом user_id, owner_id, role, project_id или permission без серверной проверки;
- помещать service-role key или иные секреты в браузерный bundle;
- использовать service-role key в клиентском коде;
- обходить RLS без отдельного security review и строго ограниченного server-side сценария.

### 14.4. Транзакции и согласованность

Операции, меняющие несколько связанных записей, имеют чёткую границу атомарности. Если действие является одной бизнес-операцией, предпочтительно выполнять его в одной транзакции PostgreSQL, например через контролируемую RPC/database function. Если задействованы внешние системы без общей транзакции, применяется спроектированная последовательность состояний, idempotency и compensating actions/Saga. Нельзя обещать атомарность между независимыми сервисами.

До реализации отдельно разрешаются и тестируются:
- запуск проекта из идеи;
- удаление проекта и поведение исходной идеи;
- архивирование/восстановление связанных сущностей;
- профильный source of truth;
- semantics of pin_order;
- наличие completion_criteria в фактической схеме;
- реальная связь ideas/projects и её cardinality.

До read-only сверки production schema нельзя выполнять destructive или corrective migrations по предположению.

### 14.5. Фоновые задачи

Длительные и повторяющиеся задачи не должны блокировать UI request. Если появляется реальная потребность, серверный job pattern определяет уникальный ID, queued/running/succeeded/failed/cancelled status, время создания/запуска/завершения, ограниченные попытки, idempotency, timeout/cancellation, diagnostics, correlation ID и безопасный повторный запуск.

Конкретный механизм очереди/планировщика выбирается после проверки возможностей Supabase и фактической потребности. Не вводить отдельную очередь без реальных фоновых задач.

## 15. Identity, account, permissions и security model

### 15.1. Identity и session lifecycle

Identity Module владеет получением и наблюдением сессии, login/logout, registration, email confirmation/callback, password recovery/update, обновлением токенов через SDK, обработкой истечения/отзыва сессии и очисткой session-scoped cache при logout/account switch.

Сессия считается подтверждённой только после успешной проверки Auth. Если Auth недоступен и невозможно подтвердить право доступа, закрытые пространства блокируются. Public остаётся доступным, если его функции не зависят от Auth.

Auth callback и recovery URL являются внешним контрактом, используемым письмами и Supabase Auth. Их нельзя менять без проверки allowlist, шаблонов писем, legacy compatibility и end-to-end тестов.

### 15.2. Модель участия и разрешений

Один аккаунт может иметь несколько типов участия. Тип участия не является глобальной ролью, автоматически дающей доступ ко всем проектам.

Модель различает:
- Account — идентичность пользователя;
- Participation Type — вид участия;
- Project Membership — участие в конкретном проекте;
- Assignment — назначенная область ответственности;
- Global Permission — глобальное полномочие;
- Project Permission — полномочие в конкретном проекте;
- Resource Scope — объект или набор объектов, на который распространяется разрешение.

Effective access вычисляется из допустимых global/project permissions с учётом scope, статуса назначения и ограничений. Доступ к проекту A не даёт доступа к проекту B. Owner Control Center доступен только владельцу; дополнительные административные полномочия не дают автоматически полный owner access.

### 15.3. Space switching

После подтверждения сессии система определяет доступные пространства. Если доступно одно — открывает его; если несколько — предлагает выбор либо открывает последнее использованное пространство согласно UX-политике. Переключение не требует повторной авторизации при действительной сессии. Последнее пространство может запоминаться как UI preference. Переключение не расширяет permissions и не меняет серверную авторизацию.

### 15.4. Security controls

Обязательны least privilege, RLS для закрытых таблиц и операций, deny-by-default для закрытых ресурсов, серверная проверка project scope, безопасное управление сессиями/logout, защита от open redirect, валидация входных данных на доверенной стороне, output encoding и защита от XSS, защита от CSRF там, где применима cookie-based схема, контроль CORS/origin allowlist, rate limiting для чувствительных операций, безопасная обработка ошибок, аудит зависимостей, защита секретов и security review для операций с повышенными полномочиями.

Конкретные CSP, cookie flags, headers, rate limits и retention policies определяются после выбора hosting/build stack и проверки фактической схемы Auth.

### 15.5. Secrets and environment configuration

- Публичный Supabase publishable/anon key может находиться в клиентской конфигурации только при корректной защите данных через RLS; он не является секретом.
- Service-role keys, API tokens, webhook secrets и private keys хранятся только в защищённом server-side secret storage.
- Секреты не коммитятся в Git, документацию, issue, telemetry или клиентские bundles.
- Development, staging и production имеют отдельные значения конфигурации и credentials, где поддерживается.
- Доступ к секретам предоставляется только нужным server-side компонентам.
- Rotation/revocation документируется и проверяется.
- .env.example содержит только имена переменных и безопасные placeholders.

## 16. Data architecture, storage and cache

### 16.1. Data ownership

Каждая сущность имеет один доменный модуль-владелец и определённый repository contract. Модуль-владелец определяет допустимые операции, invariants, lifecycle, visibility/access scope, mapping persistence schema, retention/archive policy и события значимых изменений.

Другие модули не изменяют таблицы напрямую в обход владельца доменной операции. Сквозные операции вызывают публичный use case владельца либо application orchestration с явными контрактами.

### 16.2. Database conventions

Для каждой таблицы/сущности определяются назначение и владелец, primary key, foreign keys/cardinality, nullability/defaults, unique/check constraints, обоснованные indexes, RLS policies/grants, audit/retention requirements, migration path/rollback strategy и тесты доступа/целостности.

Migrations последовательны и проверяемы в контролируемой среде. Не менять production schema автоматически из frontend deployment. Любая production migration — отдельная операция с backup/rollback plan и прямым разрешением.

### 16.3. Files and object storage

Storage не вводится «на будущее». Если потребуется хранение документов, изображений или файлов проектов, заранее определить private/public bucket policy, MIME types/size limits, naming strategy без утечки PII, upload/download authorization, signed URL expiry, content scanning при необходимости, lifecycle/retention/deletion, ownership/project scope и backup implications.

Публичные assets сайта не смешиваются с приватными пользовательскими файлами.

### 16.4. Cache consistency

Supabase/server остаётся source of truth. Client cache — оптимизация. Кэш scoped by user/session/project, обновляется или инвалидируется после успешных мутаций, защищён от stale responses/races, очищается или перепроверяется при logout/account switch/permission changes, ограничен TTL/size/cleanup policy. Нельзя показывать неподтверждённую запись как успешно сохранённую. Offline/stale data маркируются явно. Чувствительные данные не сохраняются в долговременном browser storage без security approval.

Конкретная cache library и policy выбираются в отдельном ADR.

### 16.5. Data lifecycle

Для каждой категории данных определяются create/update/archive/delete semantics, soft vs hard delete, retention, export, restoration and audit. Универсальное soft delete или физическое удаление не вводится без предметного обоснования. Удаление учитывает foreign keys, dependent records, external references and audit requirements.

## 17. External integrations and services

Каждая интеграция описывается паспортом: business purpose/owner, exchanged data and classification, authentication/scopes, API contract/version, timeout/retry, rate limits/quotas, error mapping, telemetry/redaction, outage behaviour/fallback, retention, credential rotation and disablement/rollback procedure.

Упоминание GitHub, Cloudflare, Telegram, payment providers, analytics или других платформ не означает, что интеграция уже существует. Credentials для административного управления платформой отделены от обычного членства в проекте. Доступ партнёра к проекту не даёт автоматический доступ к GitHub organization, Cloudflare account или secrets владельца.

## 18. Hosting, environments and delivery pipeline

### 18.1. Environment separation

Целевая модель предусматривает Local/Development, Staging и Production. Окружения максимально изолированы: разные deploy targets, credentials, Auth redirect configuration и backend resources, где возможно. Staging не должен случайно обращаться к production database или записывать production data. Production credentials не используются в локальных тестах.

### 18.2. Hosting and routing status

ADR-001 docs/architecture/decisions/adr-001-hosting-and-routing.md сравнивает GitHub Pages + Hash Router, GitHub Pages 404 fallback, Cloudflare Pages, Worker + GitHub Pages и альтернативный hosting. Cloudflare Pages рекомендован как кандидат для staging, но ADR остаётся PROPOSED. Это не утверждает, что Cloudflare Pages выбран или создан.

До решения текущий hosting не меняется; DNS, Cloudflare zone, Pages, Workers, SSL/TLS и GitHub Pages settings не меняются; production custom domain не переключается; Auth callback/recovery URLs не меняются.

После отдельного утверждения hosting ADR требуются staging build, direct URL/refresh tests, static asset 404 tests, TLS/headers/cache tests, Auth E2E, SEO review and rollback rehearsal.

### 18.3. Build and release pipeline

После выбора stack/build toolchain целевой pipeline включает dependency installation from lockfile, static analysis/lint, unit tests, architecture boundary checks, integration tests against isolated backend, production build, bundle/security checks, staging deployment, smoke/browser E2E tests, explicit release approval, production deployment only after owner authorization, post-deploy health checks and monitoring.

Автоматический production deployment не включается до отдельного решения. Build artifacts воспроизводимы и отделены от исходников. Source maps имеют осознанную политику доступа и не содержат секретов.

### 18.4. Release and rollback

Каждый релиз имеет commit/version identifier, changelog, build artifact reference, test evidence and deployment record. Rollback приложения должен учитывать совместимость с database schema; database rollback не всегда безопасен и проектируется отдельно. Предпочтительны backward-compatible expand/contract migrations.

Критерии rollback определяются для каждого релиза: Auth failure, data integrity issues, critical error rate, broken routes/assets, security incident.

## 19. Observability, audit, notifications and incident response

### 19.1. Observability

Разделять application logs, security/audit events, health-check history, performance metrics, deployment/release events и notification delivery history.

Значимые события связываются correlation ID/trace context. Логи структурированные: timestamp, environment, component, space/project context, severity, event type and outcome. Секреты и чувствительные payload redacted before persistence.

### 19.2. Error and incident history

Подробная история ошибок включает stack trace после redaction, stage/component/module/route, dependency context, correlation ID, sequence of related events, attempts/recovery result, affected spaces/projects, first seen/last seen/resolved time.

Retention error logs определяется отдельно и не приравнивается автоматически к 90-дневной Health Check history.

### 19.3. Notifications

Подтверждённые каналы уведомления владельца:
1. Owner Control Center.
2. Telegram.

Email не используется как канал системных уведомлений в текущей спецификации.

Централизованные настройки определяют event categories, minimum Telegram severity, отдельные error/recovery preferences, repeat suppression, delivery history and failures. Delivery асинхронна и не блокирует основные бизнес-операции. Event recording независимо от доступности Control Center UI. Если Telegram недоступен, событие остаётся записанным и доставка может быть безопасно повторена.

### 19.4. Audit and change history

Audit Log фиксирует значимые security/admin actions, а не каждый click: login/logout/failed access, permission/assignment changes, project lifecycle/publication changes, settings/integration changes, justified sensitive data access, backup/restore and incident actions.

Change History хранит before/after representation, actor, timestamp, object, action and result, исключая секреты и чувствительные значения. Подробная история аудита хранится один год, затем архивируется; для критических security/admin events устанавливается отдельный более длительный срок.

Журналы требуют ограниченного доступа на запись, tamper-evident или append-oriented storage там, где поддерживается, контролируемого retention и аудита доступа. Владелец — единственный глобальный администратор и полный владелец платформы. Scoped user roles не могут повышать свои права.

### 19.5. Health checks

Статусы: HEALTHY, DEGRADED, UNAVAILABLE, RECOVERING. Проверки плановые, событийные или ручные владельцем. Не использовать агрессивный polling; применять timeout, cooldown, debounce, bounded parallelism и deduplication. Первая неудачная проверка обычно означает подозрение, а не немедленное отключение, кроме security/data-integrity угроз. Подробная история Health Checks хранится 90 дней, затем агрегируется/архивируется с сохранением серьёзных инцидентов.

### 19.6. Platform operational modes

- NORMAL — штатная работа.
- DEGRADED — отдельные функции ограничены; независимые функции продолжают работу.
- PROTECTIVE — угроза безопасности, достоверности авторизации или целостности данных; опасные операции блокируются/ограничиваются до проверки.

Смена режима регистрируется и уведомляет владельца. Protective mode по возможности ограничивается затронутыми ресурсами.

### 19.7. Incident response

Обязательная последовательность: detect/classify → contain/isolate → protect credentials/data integrity → notify owner → investigate → restore after security/integrity checks → verify recovery → record root cause/timeline/prevention.

Destructive repair или production restore не выполняется без разрешения владельца, если только заранее утверждённый emergency runbook явно не разрешает такое действие.

## 20. Backup, disaster recovery and continuity

Критически важные бизнес-данные регулярно резервируются; копии хранятся отдельно от основного failure domain, где возможно. Scope и retention зависят от критичности и возможностей провайдера. Secrets не копируются в обычный backup archive.

Backup protection включает encryption at rest/in transit, least-privilege access, отделение от обычных application credentials, защиту от незаметного изменения/удаления или immutable retention там, где поддерживается, integrity verification после создания и перед restore, audit creation/access/export/restore и документированное восстановление ключей/credentials.

RPO и RTO определяются отдельно для критических и обычных данных, компонентов и пространств. Численные цели не выдумываются: они требуют infrastructure audit, provider limits, cost assessment и restore exercises. Backup не считается проверенным до успешного тестового восстановления.

Restore runbook определяет authorization/scope, target environment, backup/timestamp, integrity verification, dependency/configuration restoration, migration compatibility, access/RLS verification, post-restore functional checks, reconciliation of events after backup time, audit record and owner confirmation. Test restores выполняются в изолированной среде и не перезаписывают production.

## 21. Performance, scalability and availability objectives

Архитектура поддерживает route-level lazy loading, resource isolation, независимую оптимизацию модулей, bounded parallelism, async long-running work и workload isolation между проектами. Не загружать код/данные, не нужные текущему маршруту.

Измерять initial load/route transitions, JS/CSS bundle size and chunk failures, Core Web Vitals where applicable, API latency/error rate, database query latency/slow queries, background job duration/queue age, cache hit/miss/invalidation correctness, resource consumption/provider quotas.

SLO, concurrency, latency thresholds and alert thresholds определяются после baseline measurement и workload definition. В модульном монолите нельзя обещать независимое физическое масштабирование модулей; они изолируются логически и оптимизируются отдельно. Microservices не являются обязательной целью.

## 22. Testing and quality gates

### 22.1. Test layers

- Unit tests — domain invariants and pure application logic.
- Use-case tests — ports mocked/faked.
- Repository/adapter integration tests — isolated backend resources.
- RLS/authorization tests — owner, authorized partner, unauthorized user, other project member, anonymous.
- UI/component tests — validation, loading/empty/error, keyboard/focus.
- Router tests — direct URL, refresh, back/forward, query/hash, guards, redirects, unknown routes, cancellation.
- E2E — complete business journeys including Auth callback/recovery.
- Architecture tests — dependency direction, forbidden imports, module public APIs.
- Migration tests — fresh schema, upgrade path, constraints, forward/rollback compatibility.
- Performance/security tests — relevant critical paths.

### 22.2. Quality gates

Release candidate cannot pass if lint/static analysis fails; required tests fail; unauthorized access/RLS tests unexpectedly succeed; critical Auth journeys fail; routes/assets are broken; migrations risk existing data without reviewed plan; secrets appear in repository/build/logs; critical accessibility/mobile Safari regressions remain; rollback/recovery procedure is absent for a risky release.

Exact tools and thresholds фиксируются в ADR-004 after frontend stack selection. Evidence for manual tests is recorded.

## 23. Privacy, data classification and retention

Каждая категория данных классифицируется как public, internal, confidential или restricted/secret. Для неё определяются purpose, owner, access scope, storage location, retention, deletion/export rules, logging restrictions and backup handling. Собираются только необходимые данные. Не логируются credentials, full auth tokens, payment secrets, private keys и лишний персональный payload.

Privacy/legal requirements проверяются для реальных юрисдикций пользователей и коммерческой модели до публичного запуска. Этот документ не заменяет юридическую проверку.

### 24.2. Definition of architecture-document completion

Завершение архитектурного документа не означает, что все технологические ADR приняты или все production-факты проверены. Оно означает, что целевая инфраструктура и контрольные точки решений описаны для предметного рассмотрения владельцем.

## 26. Non-goals and prohibited assumptions

Документ не утверждает, что Cloudflare Pages, framework, bundler, state library или test runner выбраны; не разрешает production DNS/hosting/Supabase/Auth/database/RLS/grants/Edge Functions changes; не утверждает, что monitoring/backup/notifications/payments/storage/partner workspace runtime уже существует; не разрешает удалять текущие файлы/функции; не разрешает merge to main/deployment; не задаёт численные SLO/RPO/RTO/traffic/cost promises без измерений; не требует microservices; не переносит работу в raymondovich.online.

**Итоговый принцип:** сначала полностью определяем архитектуру и инфраструктурные контракты, проверяем факты и закрываем ADR; только после этого отдельно принимаем решение о реализации.
