# Raymondovich.ru — целевая архитектура платформы

- **Версия:** 1.0-draft
- **Дата:** 06.11.2026
- **Статус:** на рассмотрение и утверждение владельцем
- **Репозиторий:** `raymondovich-cloud/raymondovich.ru`
- **Базовая ветка:** `main` — минимальная точка входа
- **Рабочая ветка документа:** `architecture/foundation-2026-11-06`

> Этот документ фиксирует предлагаемую целевую архитектуру. Он не означает, что все перечисленные модули, технологии или инфраструктурные решения уже реализованы либо утверждены. До отдельного утверждения владельцем архитектура считается проектной спецификацией.

## 1. Назначение

Raymondovich.ru — единая SPA-платформа с публичной частью и закрытыми рабочими пространствами. Архитектура должна позволять развивать функциональные направления независимо, не связывая бизнес-логику с интерфейсом, маршрутизацией, хранилищем или конкретным backend-провайдером.

Цели:

1. Одна HTML-точка входа — корневой `index.html`.
2. Одна SPA-оболочка и централизованный Router.
3. Модульный монолит с изолированными бизнес-модулями.
4. Чёткие границы Domain, Application, Infrastructure и Presentation.
5. Управляемое взаимодействие модулей через публичные API и контракты.
6. Независимый Design System без бизнес-логики.
7. Возможность локализовать сбои и восстанавливать отдельные области приложения.
8. Возможность заменить инфраструктурные реализации без переписывания доменной логики.

## 3. Архитектурный стиль

Используется **модульный монолит** с принципами Clean Architecture и DDD там, где они оправданы предметной областью.

Это не набор независимых микросервисов. На первом этапе приложение собирается и разворачивается как единая SPA, но кодовые и бизнес-границы модулей должны быть строгими. Выделение отдельных сервисов возможно только после отдельного архитектурного решения (ADR), подтверждённого реальными требованиями.

### 3.1 Направление зависимостей

Допустимое направление:

```text
Presentation → Application → Domain
Infrastructure → Application/Domain contracts
App Composition → public module APIs
App Router → layouts and route-level module entry points
```

Правила:

- Domain не импортирует Application, Infrastructure, Presentation, Router, Design или Browser API.
- Application зависит от Domain и абстракций/контрактов, но не от конкретного Supabase SDK, DOM или UI-фреймворка.
- Infrastructure реализует порты и контракты, определённые внутренними слоями или Core.
- Presentation вызывает сценарии Application; она не содержит бизнес-правил и не обращается к Supabase напрямую.
- Один модуль не импортирует внутренние файлы другого модуля. Доступ разрешён только через его `index.js` и документированный публичный API.
- Core содержит нейтральные контракты, типы и примитивы ошибок. Core не становится складом бизнес-логики.
- Shared содержит только действительно общие технические функции. Бизнес-правила и модели конкретного модуля в Shared запрещены.
- Запрещены циклические зависимости.

## 4. Ответственность уровней

### 4.1 `source/app/`

Сборка приложения и управление его жизненным циклом.

- **bootstrap/** — запуск приложения: проверка обязательного окружения, инициализация минимальных системных служб, запуск композиции и монтирование SPA.
- **composition/** — Composition Root: создание реализаций зависимостей, связывание портов с адаптерами, регистрация модулей и системных сервисов. Здесь разрешено знать конкретные реализации Infrastructure.
- **router/** — единый Router, централизованный реестр маршрутов, guards, обработка навигации, lazy loading, 404 и переходы между пространствами.
- **layouts/** — общая оболочка и каркасы пользовательских пространств. Layout не реализует бизнес-сценарии.

Глобальный монолитный Controller запрещён. Сквозные сценарии координируются Application use cases; локальные контроллеры/презентеры допустимы внутри Presentation конкретного модуля.

### 4.2 `source/core/`

Общие архитектурные примитивы, не принадлежащие конкретному бизнес-модулю.

- **contracts/** — интерфейсы портов, событий и системных сервисов: логирование, часы, идентификаторы, навигационные или интеграционные контракты, если они действительно общие.
- **errors/** — базовая модель ошибок, категории, безопасные сообщения и правила преобразования ошибок.
- **types/** — общие типы и структурные определения без бизнес-семантики конкретного модуля.

Core не должен зависеть от модулей.

### 4.3 `source/modules/`

Изолированные бизнес-области. Внутри каждого модуля действуют одинаковые правила слоёв.

- **domain/** — сущности, value objects, инварианты, доменные политики и доменные события. Никакого UI, сетевых вызовов, SDK или хранения.
- **application/** — use cases, команды/запросы, orchestration, DTO, валидация прикладных сценариев, транзакционные границы и обработка результатов. Зависимости от внешнего мира выражаются через порты.
- **infrastructure/** — адаптеры конкретного модуля: репозитории, мапперы, реализации портов и интеграции. Общие клиенты Supabase/сети предоставляет системный Infrastructure Layer.
- **presentation/** — страницы/экраны, компоненты модуля, представление состояния, формы, контроллеры и преобразование результатов use case в UI.
- **index.js** — публичный API модуля: регистрация, разрешённые маршруты/точки входа, публичные use cases, контракты и события. Внутренние реализации наружу не экспортируются.

#### Назначение модулей

| Модуль | Ответственность |
|---|---|
| identity | Идентичность пользователя, регистрация/вход/выход, восстановление доступа, жизненный цикл сессии, роли и получение авторизационного контекста. Не владеет бизнес-данными остальных модулей. |
| ideas | Идеи владельца: фиксация, классификация, статусы, заметки, приоритеты и связь с проектами. Идеи не становятся публичными автоматически. |
| projects | Реестр проектов, жизненный цикл проекта, категории OWN / PARTNER / EXTERNAL, статусы допуска и проектные метаданные. |
| partnerships | Партнёрские отношения, заявки, рассмотрение, условия участия, соглашения и состояние сотрудничества. |
| products | Каталог продуктов экосистемы, их публичное представление, статусы готовности и коммерческие предложения. |
| portfolio | Портфель проектов/продуктов, сводное представление, показатели и связи между объектами. Не дублирует источник истины других модулей. |
| settings | Пользовательские и системные настройки, предпочтения интерфейса и настройки доступных функций. Секреты и сессионные токены не хранятся в пользовательских настройках. |

Модули не получают право на самостоятельную публикацию стороннего проекта. Для EXTERNAL PROJECTS сохраняется обязательный процесс допуска: прямое обсуждение, проверка целей, согласование коммерческих условий и оформление договорённостей до публикации.

### 4.4 `source/infrastructure/`

Общие технические адаптеры и клиенты, не содержащие бизнес-правил.

- **supabase/** — инициализация клиента и низкоуровневые адаптеры Supabase Auth/Database/Storage/Functions по мере реальной необходимости. Доступ к ним идёт только через Infrastructure конкретного модуля или Composition Root.
- **storage/** — абстракции и адаптеры локального/сессионного/браузерного хранения. Выбор места хранения определяется классификацией данных и моделью угроз.
- **network/** — HTTP-клиент, сетевые политики, таймауты, отмена запросов, сериализация, обработка сетевых ошибок и общие interceptors, если они нужны.

Ни один экран или Domain/Application use case не импортирует Supabase SDK напрямую. Клиентские ключи, доступные браузеру, не считаются секретами. Доступ к данным обязательно защищается серверными политиками и проверками прав.

### 4.5 `source/design/`

Изолированная дизайн-система.

- **tokens/** — цвета, типографика, интервалы, размеры, радиусы, тени, motion и другие дизайн-токены.
- **foundations/** — базовые правила оформления, reset, доступность, типографическая и пространственная шкалы.
- **components/** — переиспользуемые визуальные компоненты без бизнес-зависимостей.
- **layouts/** — визуальные паттерны и композиционные примитивы интерфейса.

Design System не импортирует бизнес-модули, не выполняет запросы, не управляет сессией и не содержит продуктовых правил. Бизнес-модули используют Design System, но Design System не знает о них.

### 4.6 `source/shared/`

Небольшой слой технических общих средств.

- **utilities/** — чистые функции общего назначения, форматирование и небольшие технические помощники.
- **browser/** — изолированные адаптеры Browser API: document/window, visibility, clipboard, media queries и т. п.

Shared не должен становиться общей свалкой компонентов, моделей и бизнес-функций. Если функция имеет смысл только для одного модуля, она остаётся внутри этого модуля.

## 5. Пользовательские пространства и маршрутизация

Приложение имеет одну SPA-оболочку и четыре логических пользовательских пространства:

1. **Public** — открытая презентация Raymondovich и публичный каталог допущенных проектов/продуктов.
2. **Owner Control Center** — закрытая рабочая среда владельца: идеи, проекты, портфель, партнёрства и управление экосистемой.
3. **Partner Workspace** — закрытая среда партнёра для доступных ему проектов, продуктов, условий и рабочих материалов.
4. **External Project Workspace** — изолированная среда стороннего проекта с доступом только к разрешённым проектным данным и функциям.

Пространства — это не отдельные приложения и не копии бизнес-модулей. Они формируются маршрутами, layouts, политиками доступа и разрешёнными возможностями модулей.

Требования к Router:

- один централизованный реестр маршрутов;
- проверка доступа до показа защищённого экрана;
- lazy loading модулей/маршрутных областей;
- единая обработка неизвестных маршрутов;
- сохранение корректного состояния при back/forward;
- отсутствие отдельных HTML-страниц для внутренних разделов;
- старые URL сохраняются или перенаправляются только после инвентаризации и принятия решения о совместимости.

**Открытый архитектурный вопрос:** стратегия URL для SPA на GitHub Pages. До выбора и проверки нельзя считать, что произвольные path-маршруты автоматически будут открываться при прямом переходе или обновлении страницы. Нужно отдельное ADR: hash routing, fallback через `404.html` или иной проверенный вариант с учётом домена и хостинга.

## 6. Composition и жизненный цикл

Порядок запуска:

1. Загрузить корневой `index.html`.
2. Запустить bootstrap.
3. Проверить минимальную конфигурацию и наличие DOM-точки монтирования.
4. Создать общие инфраструктурные клиенты и системные сервисы через Composition Root.
5. Зарегистрировать публичные API модулей.
6. Создать Router и передать ему реестр маршрутов и layouts.
7. Определить текущий маршрут и необходимую область доступа.
8. Загрузить только необходимые модули/экраны.
9. Смонтировать приложение и включить обработчики глобальных ошибок.

Bootstrap не содержит бизнес-логики. Composition Root — единственное место, где связываются конкретные реализации зависимостей.

## 7. Состояние и владение данными

Состояние разделяется по владельцу и времени жизни:

- **URL state** — маршрут, query-параметры и навигационное состояние.
- **Module state** — временное состояние конкретного модуля.
- **Application state** — состояние выполнения сквозного use case.
- **Session state** — только Identity; сессия не размазывается по модулям.
- **Persistent business data** — серверный источник истины, доступный через репозитории и Application сценарии.
- **Presentation state** — раскрытие панелей, активные вкладки, локальные формы и прочее состояние интерфейса.

Правила:

- у каждого состояния один определённый владелец;
- модуль не читает и не изменяет внутреннее состояние другого модуля;
- межмодульные данные запрашиваются через публичные API/контракты;
- глобальное хранилище не вводится без доказанной необходимости и ADR;
- конкретная state-management библиотека пока не выбрана.

## 8. Межмодульное взаимодействие

Предпочтительный порядок:

1. Публичный use case/API другого модуля — для синхронного запроса бизнес-операции.
2. Контрактное событие — для уведомления о факте, не требующем прямого вызова.
3. Application orchestration — для сценария, который затрагивает несколько модулей.

Запрещено:

- импортировать внутренние файлы соседнего модуля;
- напрямую менять чужие таблицы/состояния в обход владельца;
- строить скрытые зависимости через DOM или глобальные переменные;
- создавать циклы вызовов между модулями.

События должны иметь явную схему, версию при необходимости и определённого владельца. Событийная шина не вводится ради абстракции — только при наличии реального сценария.

## 9. Ошибки, изоляция и восстановление

Сбои локализуются на минимально возможном уровне:

1. локальный компонент/секция;
2. модуль;
3. прикладной сценарий;
4. пользовательское пространство;
5. всё приложение — только при системной неисправности.

Требования:

- ошибка одного модуля не должна автоматически обрушать всё приложение;
- сбои Public, Owner Control Center, Partner Workspace и External Project Workspace изолируются;
- безопасные fallback-состояния и понятные сообщения;
- автоматические повторные попытки — только для временных и безопасно повторяемых операций;
- защита от повторной отправки команд и дублирования операций;
- локальный перезапуск секции/модуля предпочтительнее перезапуска SPA;
- полный перезапуск приложения — крайняя мера;
- истечение сессии обрабатывается Identity и приводит к контролируемому переходу в безопасное состояние.

Глобальная система логирования получает ошибки через контракт. Логи не должны содержать пароли, токены, секреты, полные платёжные реквизиты и иные чувствительные данные. Пользовательские сообщения отделены от технической диагностики.

## 10. Безопасность и границы доверия

- Клиентский интерфейс не является границей безопасности.
- Любая проверка прав на клиенте нужна для UX, но не заменяет серверную авторизацию.
- Все операции с данными проверяются на стороне backend.
- Для Supabase доступ к строкам и операциям должен быть закрыт по умолчанию и разрешаться политиками RLS с проверкой владельца, роли, членства и контекста проекта.
- Секретные service-role ключи и приватные ключи никогда не попадают в браузер, репозиторий или публичные сборки.
- Доступ к Owner Control Center, Partner Workspace и External Project Workspace проверяется независимо от факта успешного входа.
- Принцип минимальных привилегий применяется к пользователям, модулям, интеграциям и серверным функциям.
- Чувствительные операции должны иметь серверную проверку полномочий и, где требуется, аудит.
- Не хранить сессионные токены в произвольном localStorage без отдельного анализа угроз и утверждённого решения.

Схема ролей, разрешений, таблиц, RLS и модель угроз оформляются отдельными спецификациями до реализации авторизации и подключения production-данных.

## 11. Design System и интерфейс

- Все визуальные параметры задаются через tokens.
- Компоненты не хранят бизнес-логику и не знают о конкретных backend-таблицах.
- Стили не генерируются из JavaScript.
- Общие компоненты не дублируются в модулях.
- Компонент включается в общий Design System только если он действительно переиспользуемый и не содержит предметной логики.
- Layout отвечает за структуру пространства, а не за права доступа или бизнес-операции.
- Доступность, клавиатурная навигация, reduced motion и адаптивность являются требованиями качества, а не дополнительными улучшениями.

Конкретный UI-фреймворк, CSS-методология и сборщик не фиксируются этим документом: для них нужны отдельные ADR и проверка совместимости с текущим минимальным репозиторием.

## 12. Тестирование и контроль качества

Обязательные уровни:

- **Domain unit tests** — инварианты, сущности, value objects и доменные политики.
- **Application tests** — use cases с подменёнными портами, включая ошибки, повторные вызовы и компенсационные сценарии.
- **Module contract tests** — проверка публичного API и запрет доступа к внутренним файлам.
- **Architecture tests** — направление зависимостей, отсутствие циклов, запрет прямого доступа Presentation к Supabase и изоляция модулей.
- **Infrastructure integration tests** — адаптеры и реальные внешние контракты в безопасной тестовой среде.
- **Router/layout tests** — доступность маршрутов, guards, неизвестные маршруты и переходы.
- **E2E tests** — ключевые пользовательские пути для каждого пространства.
- **Build checks** — воспроизводимая сборка и проверка итогового артефакта.

Проверка считается пройденной только при наличии фактического результата выполнения в CI или локальном окружении с зафиксированными версиями. Наличие workflow-файла или тестового скрипта само по себе не доказывает прохождение проверки.

## 13. Документация и изменения

- Архитектурные решения фиксируются в `docs/architecture/`.
- Существенные изменения сопровождаются записью в `docs/changes/YYYY-MM-DD-<topic>.md`.
- Изменение границ модулей, контрактов, хранения данных, маршрутизации, безопасности или инфраструктуры требует обновления спецификации и/или отдельного ADR.
- Перед изменением существующего файла необходимо получить его актуальную версию и сверить SHA.
- Изменения вносятся последовательно и проверяются после записи.
- Не создавать пустые каталоги и фиктивные реализации.
- Неподтверждённые решения помечаются как открытые вопросы, а не выдаются за утверждённые.

## 14. Что намеренно не создаётся сейчас

На этапе утверждения архитектуры не создаются:

- система авторизации и регистрации;
- таблицы и миграции базы данных;
- Supabase Auth/Database конфигурация;
- RLS-политики и серверные функции;
- бизнес-экраны и UI-модули;
- глобальный state manager;
- конкретный UI-фреймворк или сборщик;
- платежи, уведомления и интеграции;
- production-конфигурация и deployment-изменения.

Сначала утверждаются границы, ответственность и контракты. Реализация начинается отдельными контролируемыми этапами.

## 15. Открытые решения (ADR)

Следующие решения нельзя считать утверждёнными этой спецификацией:

1. **ADR-001 — Build/runtime:** сборщик, формат модулей, целевые браузеры и стратегия production-сборки.
2. **ADR-002 — SPA URL strategy:** маршруты и прямые переходы на GitHub Pages с собственным доменом.
3. **ADR-003 — UI technology:** UI-фреймворк или решение без фреймворка.
4. **ADR-004 — Styling:** организация CSS, импорт токенов и стратегия компонентных стилей.
5. **ADR-005 — State management:** нужна ли отдельная библиотека состояния.
6. **ADR-006 — Identity/security:** модель идентичности, роли, разрешения, сессии, threat model.
7. **ADR-007 — Data architecture:** схема данных, владение таблицами, миграции, RLS и серверные операции.
8. **ADR-008 — Testing/toolchain:** тестовый стек, CI gates и стратегия E2E.
9. **ADR-009 — Observability:** сбор ошибок, аудит, метрики и политика хранения логов.

Каждый ADR должен содержать контекст, варианты, критерии выбора, принятое решение, последствия и статус. ADR со статусом Proposed не является утверждённым решением.

## 16. Критерии утверждения архитектуры

Архитектура может быть утверждена после подтверждения владельцем следующих положений:

- [ ] корневой `index.html` — единственная HTML-точка входа;
- [ ] SPA с единым Router и централизованным реестром маршрутов;
- [ ] модульный монолит, а не преждевременная микросервисная система;
- [ ] структура каталогов и ответственность каждого слоя;
- [ ] семь перечисленных бизнес-модулей и их границы;
- [ ] четыре пользовательских пространства;
- [ ] направление зависимостей и запрет прямого доступа Presentation к Supabase;
- [ ] владение состоянием и правила межмодульного взаимодействия;
- [ ] изоляция ошибок и безопасное восстановление;
- [ ] требования к безопасности, тестированию и документации;
- [ ] перечень открытых ADR, которые будут решаться до соответствующих этапов реализации.

**До явного подтверждения владельцем документ остаётся Draft 1.0 и не является разрешением на реализацию всех перечисленных решений.**
