# Raymondovich.ru — архитектурный каркас

**Версия:** 1.0  
**Дата:** 2026-11-06  
**Статус:** архитектурная основа, реализация требует отдельных решений владельца.

## 1. Базовая модель

Raymondovich.ru — одно веб-приложение (SPA) с четырьмя изолированными пользовательскими пространствами. Это не четыре отдельных сайта и не четыре независимых приложения.

1. **Public** — публичная презентация экосистемы и проектов.
2. **Owner Control Center (OCC)** — закрытая система управления всей экосистемой, доступная только владельцу.
3. **Partner Project Management (PPM)** — рабочая среда совместных проектов Raymondovich и допущенных к ним партнёров.
4. **External Project Workspace (EPW)** — изолированная среда для владельцев и представителей сторонних проектов, прошедших отбор и заключивших соглашение.

Третье и четвёртое пространства имеют разные бизнес-модели, наборы данных и полномочия. Их нельзя объединять в одну универсальную «панель партнёра».

## 2. Принципы приложения

- Одна точка входа и единый жизненный цикл приложения.
- Модульный монолит: единое приложение, внутренние модули с чёткими границами.
- Clean Architecture: зависимости направлены к доменной логике; UI не обращается к инфраструктуре напрямую.
- Каждый модуль владеет своими данными и публичным API.
- Межмодульное взаимодействие — через контракты и сценарии Application Layer.
- Права проверяются сервером при каждой защищённой операции; скрытие UI не является защитой.
- Изоляция данных по пространствам, проектам и участникам обязательна.
- Публичная часть не получает административных полномочий.
- Никакая регистрация или публикация стороннего проекта не происходит автоматически.

## 3. Логическая схема

```text
Raymondovich Application (SPA)
├── Public
├── Owner Control Center
├── Partner Project Management
└── External Project Workspace

Shared platform capabilities
├── Identity & Access
├── Routing & Navigation
├── Design System
├── Notifications
├── Audit & Error Logging
└── Infrastructure Adapters
```

Shared capabilities не являются пятым пользовательским пространством. Они предоставляют общие технические функции четырём пространствам.

## 4. Предлагаемая структура исходного кода

```text
source/
├── app/
│   ├── bootstrap/          # запуск приложения
│   ├── composition/        # сборка зависимостей и модулей
│   ├── router/             # маршруты, guards, разрешение пространства
│   └── layouts/            # оболочки четырёх пространств
├── core/
│   ├── contracts/          # общие интерфейсы и межмодульные контракты
│   ├── errors/              # типы и классификация ошибок
│   └── types/               # общие примитивы типов
├── modules/
│   ├── identity/            # аутентификация, сессия, роли и разрешения
│   ├── public/              # публичная презентация и каталог
│   ├── owner/               # сценарии владельца и OCC
│   ├── partner-projects/    # совместные проекты Raymondovich
│   ├── external-projects/   # допущенные сторонние проекты
│   ├── projects/            # общие доменные сущности проектов, если применимо
│   ├── products/            # продукты и предложения
│   ├── portfolio/           # портфель и сводное представление
│   └── settings/            # настройки платформы
├── infrastructure/
│   ├── supabase/            # адаптеры доступа к Supabase
│   ├── storage/             # файловое хранилище
│   └── network/             # HTTP и сетевые адаптеры
├── design/
│   ├── tokens/
│   ├── foundations/
│   ├── components/
│   └── layouts/
└── shared/
    ├── utilities/
    └── browser/
```

Каждый бизнес-модуль при реализации получает внутренние слои `domain/`, `application/`, `infrastructure/`, `presentation/` и публичный `index.js`. Не создавать дублирующие слои заранее, пока в них нет содержимого.

## 5. Четыре пользовательских пространства

### Public
- Доступен без входа.
- Показывает Raymondovich, собственные, партнёрские и сторонние проекты, условия участия и контактные сценарии.
- Не предоставляет самостоятельную публикацию сторонних проектов.
- Не содержит административных операций.

### Owner Control Center
- Единственный пользователь с ролью Owner.
- Полный административный контроль над экосистемой.
- Идеи, стратегии, проекты, продукты, партнёрства, сторонние проекты, настройки, аналитика и аудит.
- Критические действия требуют серверной проверки полномочий и журналирования.

### Partner Project Management
- Доступ владельца и явно назначенных участников конкретных партнёрских проектов.
- Роли и разрешения ограничены назначенными проектами и задачами.
- Партнёр не получает глобальный доступ к OCC или другим проектам.
- Raymondovich сохраняет управление проектом и его допуском.

### External Project Workspace
- Доступ владельца Raymondovich и уполномоченных представителей конкретного внешнего проекта.
- Доступ возникает только после ручного допуска и оформления согласованных условий.
- Представитель видит только свой проект и разрешённые ему материалы/операции.
- Никакой регистрации, публикации или расширения доступа без решения владельца.

## 6. Матрица доступа (логический минимум)

| Ресурс / действие | Public | Owner | Partner | External representative |
|---|---:|---:|---:|---:|
| Читать публичный каталог | Да | Да | Да | Да |
| Управлять платформой | Нет | Да | Нет | Нет |
| Читать внутренние идеи и стратегии | Нет | Да | Нет | Нет |
| Управлять партнёрским проектом | Нет | Да | По назначению | Нет |
| Читать внешний проект | Только публичные сведения | Да | Нет, если отдельно не назначен | Только свой проект |
| Допускать внешний проект | Нет | Да | Нет | Нет |
| Управлять условиями договора | Нет | Да | Только в рамках полномочий | Только согласованные действия |

Это стартовая матрица. Детальные permissions должны быть определены для каждого use case и проверяться на сервере.

## 7. Identity и безопасность

- Аутентификация отвечает на вопрос «кто пользователь»; авторизация — «что ему разрешено».
- Роль сама по себе недостаточна: необходимы resource-level permissions и проверка членства в конкретном проекте.
- Owner — отдельный защищённый субъект; нельзя выдавать роль Owner через публичный интерфейс или клиентские данные.
- Partner и External Representative — разные типы доступа, не взаимозаменяемые.
- Все защищённые операции проверяются на серверной стороне.
- Для Supabase политики RLS должны обеспечивать изоляцию строк по пользователю, роли, проекту и членству.
- Секреты и service-role credentials никогда не попадают в браузер.
- В аудит не записываются пароли, токены и секреты.

## 8. Направление зависимостей

```text
Presentation → Application → Domain
Infrastructure → Application/Domain contracts
Composition Root → связывает реализации и контракты
```

- Presentation не вызывает Supabase напрямую.
- Domain не зависит от UI, роутера, Supabase или browser APIs.
- Application координирует use cases и проверяет бизнес-правила.
- Infrastructure реализует порты/контракты.
- Модули не импортируют внутренние файлы друг друга; только публичные API или общие контракты.

## 9. Router и изоляция пространств

Router разрешает маршрут, определяет требуемое пространство и запускает соответствующий guard. Guard проверяет сессию и клиентские claims только для UX; окончательное решение всегда принимает сервер при обращении к данным и выполнении команды.

Предлагаемые группы маршрутов (конкретная URL-стратегия пока не выбрана):

- Public: `/`, `/projects`, `/products`, `/partnership`
- Owner: `/owner/*`
- Partner: `/partner/*`
- External: `/external/*`

Прямое открытие URL, обновление страницы, fallback GitHub Pages и стратегия hash/history должны быть проверены отдельным ADR до реализации маршрутизатора.

## 10. Отказоустойчивость

- Ошибка локального модуля не должна автоматически перезапускать всё приложение.
- Ошибки разделяются на module, application и global.
- Для каждого пространства предусматривается собственный безопасный fallback.
- Повторять автоматически можно только безопасные идемпотентные запросы.
- Критические действия не повторяются без проверки результата.
- Error logging централизован, но не содержит секретов и чувствительных данных.

## 11. Что не фиксируется этим документом

Пока не утверждены: UI framework, bundler, state library, CSS strategy, URL routing strategy, конкретная схема БД, провайдеры авторизации, модель уведомлений и интеграции. Их нельзя выбирать случайно — нужны отдельные ADR с оценкой последствий.

## 12. Порядок реализации

1. Утвердить эту модель и границы четырёх пространств.
2. Принять ADR по технологическому стеку и маршрутизации.
3. Спроектировать Identity, роли, permissions и серверную модель изоляции.
4. Создать app bootstrap, composition root и router.
5. Реализовать оболочки четырёх пространств без бизнес-функций.
6. Подключать бизнес-модули по одному, начиная с согласованного приоритета.
7. Добавить тесты доступа: запрет по умолчанию, межпроектная изоляция и отсутствие повышения привилегий.

**Важно:** этот документ задаёт архитектурный каркас. Он сам по себе не включает аутентификацию, БД, RLS, реальные рабочие процессы или production deployment.
