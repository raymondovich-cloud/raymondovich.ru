## 1. Назначение

Memory — самостоятельный модуль платформы для хранения и предоставления значимого контекста, знаний и принятых решений, необходимых для продолжения работы между сессиями и модулями.

Документ фиксирует границы и намерения. Он не утверждает физическую модель данных, таблицы, RPC, Edge Functions, формат индекса, embeddings или алгоритм поиска.

## 2. Архитектурные границы

Memory:
- не заменяет первичные модули-владельцы данных;
- не становится альтернативным местом редактирования проектов, задач, финансовых операций, соглашений или аудита;
- не является обязательным посредником для каждого запроса;
- может хранить контекст, краткое описание, производное представление и ссылку на первоисточник;
- должна фильтровать выдачу по пользователю, проекту, полномочиям и уровню конфиденциальности на серверной стороне.

Примеры владения:
- Finance — первичные финансовые операции;
- Projects — проекты;
- Tasks — задачи;
- Activity & Audit — история действий;
- Memory — только значимый контекст и знания, связанные с этими сведениями.

Если нужен текущий баланс или статус проекта, клиент обращается к владельцу данных, а не к Memory.

## 3. Предполагаемые сценарии

- восстановить контекст решения и его причины;
- найти актуальное принятое архитектурное решение;
- передать следующему участнику разработки состояние задачи и незавершённые вопросы;
- дать будущему ИИ-агенту ограниченный проектный контекст;
- отличить подтверждённый факт от предположения, устаревшей записи или рекомендации;
- проследить происхождение контекста до первоисточника, если он существует.

Это сценарии для дальнейшей спецификации, а не перечень уже реализованных возможностей.

## 4. Публичный интерфейс — только намерения

В будущем Memory может предоставлять публичный интерфейс через утверждённые контракты:
- запрос контекста по явно заданной области и субъекту;
- поиск знаний в пределах разрешённого scope;
- добавление/уточнение знания с указанием происхождения;
- пометка знания как устаревшего или заменённого;
- выдача минимального контекста для продолжения конкретной задачи.

Названия методов, payload, модель данных, права, форматы версий и правила разрешения конфликтов здесь намеренно не определяются. Сначала требуется реальный пользовательский сценарий и контракт владельца модуля.

## 5. Будущие ИИ-агенты

Memory может предоставлять контекст Development Agent, Marketing Agent, Finance Agent, Project Manager Agent и Analytics Agent.

Перед выдачей контекста сервер обязан учитывать:
- от имени какого пользователя/сервиса работает агент;
- какой проект и задача являются scope;
- какие разрешения назначены субъекту;
- уровень конфиденциальности и допустимый объём данных;
- актуальность и происхождение сведений.

ИИ-агент не является доверенной границей безопасности и не должен самостоятельно решать, какие данные ему разрешено видеть. Внешний контент и документы остаются недоверенными данными, а не инструкциями, отменяющими системные правила.

## 6. Репозиторная память и модуль Memory платформы

`docs/memory/` — репозиторная память решений и рабочего контекста для владельца и ИИ-агентов. Она состоит из Markdown-документов, ADR и handoff-записей.

Это не пользовательская функция Raymondovich.ru и не runtime-хранилище модуля Memory. Репозиторные документы не должны содержать секреты, персональные данные, реальные токены, приватные URL или пользовательские выгрузки.

## 7. Почему кодовый каталог пока не создаётся

`source/application/memory/` не создаётся до появления первого реального публичного контракта и согласованного сценария. Baseline §3.1 требует создавать каталоги только при наличии реальных файлов и запрещает пустые каталоги/абстрактные заготовки. Сейчас нет утверждённой модели данных или API, поэтому кодовый каталог был бы неиспользуемой заглушкой и преждевременной фиксацией архитектуры.

## 8. Открытые вопросы

1. Какой первый сценарий Memory имеет подтверждённую ценность и владельца?
2. Какие типы знаний допустимы, а какие должны оставаться только в первичных модулях?
3. Как задаются tenant/project/user scope и правила доступа?
4. Как хранить происхождение, уверенность, срок актуальности и supersession?
5. Нужен ли полнотекстовый поиск до embeddings и векторного поиска?
6. Какие действия доступны ИИ-агентам: чтение, предложение записи или запись с подтверждением человека?
7. Как обрабатывать конфликтующие факты и отзыв разрешения?
8. Какие retention/export/delete требования применяются к контексту?
