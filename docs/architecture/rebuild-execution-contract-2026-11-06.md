# Контракт пересборки Raymondovich.ru

**Дата:** 06.11.2026  
**Статус:** APPROVED EXECUTION BASELINE  
**Репозиторий:** `raymondovich-cloud/raymondovich.ru`  
**Рабочая ветка:** `rebuild/foundation-2026-11-06`  
**База ветки:** `613e572b13d2d01fd700ca81abfa399ec3daefbd`  
**Область:** пересборка сайта и интерфейсов с сохранением проверенной архитектуры и утверждённых пользовательских сценариев.

## 1. Принятое направление

Работа продолжается не с нуля на уровне архитектуры. Проверенные технические решения, модули, use cases, адаптеры, маршрутизация, авторизация, документация и тесты из архитектурной ветки являются базой для дальнейшей разработки.

Публичный сайт и пользовательские интерфейсы пересобираются заново. Существующая реализация не считается неприкосновенной: каждый переносимый модуль проходит проверку на соответствие архитектурным границам и подтверждённому поведению.

Не допускается:
- повторно изобретать уже согласованные связи между блоками;
- переносить монолитные DOM-сценарии целиком;
- смешивать UI, бизнес-правила, хранение данных и интеграции;
- менять утверждённые пользовательские сценарии без отдельного решения;
- создавать абстракции, каталоги или функциональность «на будущее» без реальной ответственности.

## 2. Архитектурные слои и зависимости

Сохраняется действующая архитектурная модель проекта:

- `core` — только действительно общие технические типы и контракты;
- `domain` — предметные сущности, инварианты и бизнес-правила;
- `application` — use cases, orchestration и порты внешних зависимостей;
- `infrastructure` — реализации портов, Supabase и другие внешние адаптеры;
- `presentation` — маршруты, layouts, экраны и пользовательские взаимодействия;
- `memory` — только конкретное состояние/хранилище с явно определённым владельцем; не параллельный Domain и не универсальный контейнер;
- `design` — отдельная визуальная система, не содержащая бизнес-логики.

Допустимые зависимости:

```text
Presentation ───────> Application ───────> Domain
Infrastructure ─────> Application ports
Presentation runtime = composition root:
  связывает Application use cases с Infrastructure adapters

Presentation ───────> Design System (только визуальные контракты)
Design System ──────X Domain / Application / Infrastructure
Domain ─────────────X Presentation / Infrastructure / Memory
Application ────────X конкретный Supabase SDK / DOM / Router / UI framework
```

Конкретные Infrastructure adapters подключаются только в composition root. Presentation-страницы и компоненты не обращаются к Supabase напрямую. Межмодульные вызовы выполняются только через публичный API модуля или согласованный application contract. Циклические зависимости запрещены.

Наличие физического файла или экспорта не является разрешением обходить публичный контракт модуля.

## 3. Design System — самостоятельная система

`source/design/` является самостоятельным владельцем визуальных правил Raymondovich. Система должна развиваться независимо от бизнес-модулей и не превращаться в набор случайных CSS-файлов конкретных страниц.

Ответственность Design System:
- design tokens: цвета, типографика, размеры, интервалы, радиусы, границы, тени и слои;
- foundations: базовые правила оформления и доступности;
- общие визуальные компоненты;
- layout и responsive patterns;
- состояния компонентов: focus, hover, active, disabled, loading, error;
- правила композиции и визуальной иерархии.

Границы:
1. Design System не импортирует Domain, Application или Infrastructure.
2. В Design System нет бизнес-решений, авторизации, проверки ролей, запросов или работы с данными.
3. Компоненты получают данные и callbacks через явный интерфейс; бизнес-переходы остаются в Application.
4. Presentation использует Design System, но не дублирует и не переопределяет глобальные токены локальными стилями без обоснованного исключения.
5. Страничные композиции принадлежат Presentation; повторно используемые визуальные примитивы — Design System.
6. Не создавать пустые подпапки. Структура появляется вместе с реальными файлами и ответственностью.

Текущие CSS-файлы в `source/design/` считаются существующим материалом для аудита, а не автоматически готовой законченной Design System. Их содержимое будет классифицировано: токены/foundations, общие компоненты, layout patterns или локальные стили конкретного экрана.

## 4. Утверждённые пространства и их границы

Единое SPA содержит четыре пользовательских пространства:

1. **Public** — публичная презентация Raymondovich и её проектов, информация о форматах участия и публичные пользовательские страницы.
2. **Owner Control Center** — закрытое пространство владельца для Capture, Focus и Portfolio; управления идеями, проектами, направлениями и экосистемой.
3. **Partner Workspace** — рабочее пространство партнёров, сотрудничающих над проектами Raymondovich.
4. **External Project Workspace** — отдельное пространство для сторонних проектов, принятых в экосистему после обсуждения, проверки целей, согласования коммерческих условий и договора.

Это отдельные пользовательские пространства с согласованными общими механизмами, а не четыре независимых приложения и не четыре набора несвязанных страниц.

### 4.1. Категории проектов в публичной части

Публичная классификация сохраняет три утверждённых направления:
- **OWN PROJECTS / Собственные проекты**;
- **PARTNER PROJECTS / Партнёрские проекты**;
- **EXTERNAL PROJECTS / Сторонние проекты**.

Сторонние проекты не публикуются через свободную саморегистрацию. Публикация возможна только после прямого обсуждения с владельцем, проверки целей, согласования коммерческих условий и заключения договора.

### 4.2. Доступ и безопасность

- Public доступен посетителям в пределах публичного контента.
- Owner Control Center доступен только владельцу с подтверждённой административной ролью.
- Partner Workspace не открывает данные по факту регистрации: требуются подтверждённое участие и проектная авторизация.
- External Project Workspace не открывает данные по факту наличия публичной карточки проекта: требуется отдельное право доступа к соответствующему проекту.
- Route guards обеспечивают корректную навигацию, но не являются границей безопасности. Серверная авторизация и RLS обязательны для защищённых данных.
- Текущие Partner и External views являются placeholders. До появления модели membership и server-side project authorization они не считаются рабочими кабинетами и не должны показывать защищённые данные.

## 5. Существующие сценарии — сохранять, не переизобретать

Пересборка интерфейсов обязана учитывать утверждённые функциональные карты и проверенные сценарии текущей ветки. В частности:

- централизованный route registry, layouts, guards, direct URL, refresh и browser history;
- Auth: вход, регистрация, подтверждение email, callback, восстановление/смена пароля, восстановление сессии и выход;
- Owner Control Center: Overview, Ideas, Projects;
- режимы Control Center: Capture, Focus, Portfolio;
- идеи со статусами `new`, `review`, `launched`, `archived`;
- проекты со статусами `active`, `paused`, `completed`, `archived`;
- различие между бизнес-приоритетом и ручным pinning;
- связь проекта с исходной идеей через `source_idea_id`;
- действия создания, редактирования, приоритизации, архивации/восстановления и удаления в пределах существующих правил;
- мобильные и клавиатурные взаимодействия, включая открытие деталей обычным нажатием и контекстных действий долгим нажатием/контекстным меню;
- responsive navigation, account popover, Escape/backdrop, loading/empty/error/success и подтверждения необратимых действий;
- обратная совместимость существующих URL и Auth redirect bridges, пока не доказана безопасная замена.

Список является контрольным перечнем для аудита паритета, а не разрешением объявить все сценарии уже проверенными в production. Источники деталей: `docs/architecture/spa-rewrite-specification.md`, `docs/architecture/owner-control-center-functional-map-2026-11-05.md`, `docs/architecture/deep-functional-and-data-migration-map-2026-11-05.md`, `docs/architecture/final-repository-structure.md` и соответствующие тесты.

## 6. Правило переиспользования

Перед изменением каждого модуля:
1. Получить актуальный файл из целевой ветки и проверить его SHA.
2. Установить ответственность файла и его публичные контракты.
3. Проверить входящие и исходящие зависимости.
4. Сопоставить его поведение с функциональной картой и тестами.
5. Определить: reuse без изменений, refactor внутри границ, замена с parity tests или блокировка до отдельного решения.
6. Изменять один файл за раз; после изменения повторно получить файл и проверить результат.
7. Обновить changelog и тесты соответствующего уровня.

Не удалять функцию или legacy bridge только из-за неудобства переноса. Сначала фиксировать заменяющий сценарий, совместимость и доказательства паритета.

## 7. Порядок пересборки

1. **Architecture baseline:** подтвердить реальные связи, публичные API модулей, точки композиции и архитектурные ограничения.
2. **Design System foundation:** провести аудит текущих стилей, выделить tokens/foundations и базовые компоненты без привязки к бизнес-логике.
3. **Presentation foundation:** определить shell, layouts, route composition и правила подключения Design System.
4. **Public experience:** пересобрать публичные страницы на утверждённых текстах и направлениях.
5. **Authentication and Owner:** переносить только проверенные сценарии, сохраняя текущие контракты и ограничения безопасности.
6. **Partner / External:** реализовывать только после отдельной проверки моделей участия и проектных разрешений; до этого сохранять безопасные placeholders.
7. **Parity and quality gates:** unit, architecture, integration, E2E, build и ручная проверка на реальном iPhone Safari.
8. **Release decision:** отдельное согласование PR/main/hosting. Никакого автоматического merge или production deployment.

## 8. Технологические решения и нерешённые вопросы

- Текущая реализация использует Vue 3, Vue Router 5 и Vite 8; эти версии зафиксированы в package manifest.
- TypeScript не считается утверждённым решением.
- ADR-003 (state management) и ADR-004 (testing strategy) остаются отдельными решениями; не объявлять их принятыми сверх фактически реализованного.
- Node.js `node:test` является текущей базой unit/architecture tests; Playwright используется для browser E2E.
- Вопрос production hosting / Pages cutover остаётся вне scope этой пересборки и требует отдельного решения.
- Никакие production Supabase, Auth settings, schema, RLS, grants, Edge Functions, DNS, Cloudflare или hosting settings не меняются в рамках этой работы.

## 9. Границы репозитория и безопасности

Работа ведётся только в `raymondovich-cloud/raymondovich.ru` и только в ветке `rebuild/foundation-2026-11-06`.

Не изменять:
- `main`, резервные ветки и существующий PR #3;
- `raymondovich-cloud/raymondovich.online`;
- production deployment, Pages publishing source, DNS, Cloudflare и домены;
- production Supabase/Auth/database/RLS/grants/Edge Functions;
- секреты и credentials.

Любое изменение этих границ требует отдельного прямого разрешения владельца.

## 10. Критерий готовности каждого этапа

Этап считается завершённым только при наличии:
- изменённых файлов и их SHA;
- объяснённой ответственности и зависимости каждого изменённого модуля;
- тестов, соответствующих изменённому поведению;
- результата запуска проверок или честной отметки, что проверка не выполнялась/недоступна;
- changelog;
- отсутствия незаявленных изменений в защищённых областях.

Документация не заменяет runtime-проверку, а успешная сборка не доказывает корректность бизнес-сценариев или production security.
