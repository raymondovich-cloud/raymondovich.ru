## 1. Назначение документа

Документ определяет единые архитектурные правила взаимодействия между функциональными модулями Raymondovich.ru.

Его задача — заложить фундамент, который позволит развивать платформу как единую систему, не превращая её в набор тесно связанных компонентов.

Архитектура должна обеспечить:

- независимость бизнес-логики модулей;
- контролируемое взаимодействие между модулями;
- отсутствие прямых зависимостей от внутренних реализаций других модулей;
- единые правила передачи команд, запросов и событий;
- централизованный механизм контроля межмодульного взаимодействия;
- безопасную передачу пользовательского и проектного контекста;
- возможность добавлять новые модули без перестройки существующих;
- возможность в будущем выделять отдельные модули в самостоятельные сервисы.

**Главное требование:** модуль должен оставаться самостоятельной функциональной единицей, даже если физически все модули работают внутри одного приложения.

Этот документ является основой для последующих спецификаций:

1. Module Contract Specification V1.0.
2. Event System Specification V1.0.
3. Memory System Architecture V1.0.

## 2. Область действия

Архитектура распространяется на все пространства и функциональные модули платформы.

### 2.1. Пользовательские пространства

| Пространство | Назначение |
|---|---|
| Public Space | Публичная презентация Raymondovich и продуктов |
| Owner Control Center | Полное управление экосистемой владельцем |
| Partner Workspace | Совместная работа партнёров над проектами |
| External Project Workspace | Работа владельцев сторонних проектов и их участников |

### 2.2. Основные функциональные модули

Предполагаемый состав модулей:

- Identity & Access;
- People;
- Projects;
- Products;
- Ideas;
- Tasks;
- Partnerships;
- Agreements;
- Finance;
- Marketing;
- Analytics;
- Content Management;
- Intake;
- Services & Integrations;
- Notifications;
- Activity & Audit;
- Memory.

Это предварительный архитектурный перечень. Окончательное разделение ответственности и состав модулей должны быть закреплены в отдельной спецификации модульной структуры.

### 2.3. Границы действия

Документ регулирует:

- зависимости между модулями;
- передачу данных между модулями;
- вызов функциональности других модулей;
- обработку событий;
- выполнение межмодульных процессов;
- передачу контекста пользователя и проекта;
- обработку ошибок и повторных операций.

Документ не определяет:

- конкретную структуру всех таблиц базы данных;
- окончательный технологический стек;
- дизайн пользовательского интерфейса;
- бизнес-правила каждого модуля;
- полную модель разрешений;
- конкретные форматы всех событий, команд и запросов.

Эти вопросы должны регулироваться отдельными документами.

## 3. Основные архитектурные принципы

Все модули Raymondovich.ru обязаны соблюдать следующие принципы.

### 3.1. Modular Monolith

На первом этапе платформа разрабатывается как модульный монолит.

Это означает:

- одно приложение;
- единая точка развёртывания;
- общая инфраструктура;
- возможность использовать одну базу данных;
- логически изолированные модули;
- формализованные интерфейсы взаимодействия.

Модульный монолит выбран потому, что на начальном этапе микросервисная архитектура создаст дополнительную инфраструктурную и операционную сложность.

При этом модульный монолит не должен превращаться в монолитную архитектуру, где любой компонент может обращаться к любому другому.

### 3.2. Независимость модулей

Каждый модуль отвечает за собственную предметную область.

Он самостоятельно определяет:

- бизнес-правила;
- внутреннюю структуру;
- обработку операций;
- хранение собственных данных;
- проверку бизнес-ограничений;
- внутренние процессы.

Другие модули не должны знать, как именно реализована эта логика.

### 3.3. Единая система взаимодействия

Модули взаимодействуют через формализованные механизмы Core Interaction System.

Запрещается создавать произвольные связи между модулями.

Любое межмодульное взаимодействие должно иметь понятную причину, определённый контракт и контролируемый результат.

### 3.4. Явное владение данными

У каждого набора первичных данных должен быть определён модуль-владелец.

Другие модули могут получать необходимые сведения через публичные интерфейсы, но не должны самостоятельно изменять чужие данные.

### 3.5. Безопасность по умолчанию

Любой запрос к данным или выполнение команды должны учитывать:

- пользователя;
- его активную роль;
- проектный контекст;
- полномочия;
- уровень конфиденциальности данных;
- допустимость конкретной операции.

Отсутствие информации о полномочиях не означает разрешение на выполнение операции.

### 3.6. Минимальная необходимая сложность

Архитектура должна обеспечивать расширяемость, но не должна включать инфраструктуру, которая пока не нужна.

Не следует преждевременно внедрять:

- микросервисы;
- распределённые брокеры сообщений;
- отдельные серверы обнаружения сервисов;
- распределённые транзакции;
- сложную оркестрацию;
- векторные базы данных без реальной необходимости.

## 4. Понятие функционального модуля

Функциональный модуль — самостоятельная часть платформы, отвечающая за конкретную область бизнес-логики.

Каждый модуль имеет следующие составляющие:

| Компонент | Назначение |
|---|---|
| Domain | Бизнес-сущности, правила и ограничения |
| Application | Сценарии выполнения операций |
| Public Interface | Публичные возможности модуля |
| Infrastructure | Технические реализации и работа с внешними ресурсами |
| Data Ownership | Ответственность за собственные данные |
| Event Handlers | Реакция на разрешённые события |
| Tests | Проверка логики и контрактов |

Конкретная внутренняя структура может отличаться в зависимости от сложности модуля.

Однако модуль обязан сохранять принцип: его внутренние компоненты не являются публичным интерфейсом для остальных модулей.

### 4.1. Пример владения данными

| Данные | Владелец |
|---|---|
| Пользователи и идентификация | Identity / People |
| Роли и полномочия | Access |
| Проекты | Projects |
| Продукты | Products |
| Задачи | Tasks |
| Финансовые операции | Finance |
| Договорённости и договоры | Agreements |
| Маркетинговые данные | Marketing |
| Аналитические результаты | Analytics |
| История действий | Activity & Audit |
| Системные знания и контекст | Memory |

Таблица является предварительным распределением ответственности. В частности, окончательное разделение Identity, People и Access будет уточняться при проектировании модулей.

### 4.2. Запрет на двойное владение

Один и тот же первичный объект не должен независимо редактироваться несколькими модулями.

Например:

- Finance владеет финансовыми операциями.
- Analytics может получать сведения о финансовых результатах.
- Analytics может рассчитывать показатели.
- Analytics не может самостоятельно изменять первичные финансовые операции.

Если другому модулю нужны данные, он получает их через интерфейс владельца.

## 5. Запрещённые зависимости между модулями

Следующие действия запрещены.

### 5.1. Прямой импорт внутренних компонентов

Модуль A не должен импортировать внутренние классы, функции, репозитории и сервисы модуля B.

Исключение — официально опубликованные интерфейсы и контракты.

### 5.2. Прямое обращение к чужим таблицам

Модуль не должен самостоятельно выполнять запросы к внутренним таблицам другого модуля.

Например, Analytics не должен напрямую читать внутренние таблицы Finance.

Он должен получать необходимые данные через разрешённый интерфейс Finance или через специально определённый механизм передачи аналитических данных.

### 5.3. Обход бизнес-логики владельца

Запрещается изменять данные другого модуля в обход его бизнес-правил.

Например, создание финансовой операции должно проходить через Finance, а не через прямую запись в его таблицу со стороны Projects.

### 5.4. Зависимость от внутренней реализации

Модуль не должен зависеть от:

- названий внутренних функций другого модуля;
- структуры его таблиц;
- внутренних типов данных;
- порядка выполнения его внутренних операций;
- особенностей его инфраструктуры.

### 5.5. Циклические зависимости

Недопустима ситуация, при которой:

- модуль A зависит от B;
- модуль B зависит от A.

Если бизнес-сценарий требует участия нескольких модулей, взаимодействие должно организовываться через публичные контракты и Process Manager.

## 6. Core Interaction System

**Core Interaction System (CIS)** — системный механизм, обеспечивающий контролируемое взаимодействие модулей.

Его задача — предоставлять инфраструктуру коммуникации, а не управлять бизнес-логикой всей платформы.

CIS не является универсальным сервисом, в котором сосредоточены правила работы всех модулей.

### 6.1. Основные компоненты

| Компонент | Ответственность |
|---|---|
| Module Contracts | Формализация публичных интерфейсов |
| Command Bus | Передача команд |
| Query Bus | Выполнение запросов |
| Event Bus | Передача событий |
| Event Handlers | Обработка событий |
| Process Manager | Координация длительных процессов |
| Access Context | Передача контекста полномочий |
| Module Registry | Учёт зарегистрированных модулей |
| Contract Registry | Учёт доступных контрактов |
| Interaction Logger | Техническая регистрация взаимодействий |
| Outbox | Надёжная публикация событий |

Не все компоненты обязаны быть самостоятельными сервисами или отдельными инфраструктурными системами.

На первом этапе это могут быть логические компоненты одного приложения.

### 6.2. Принцип работы

Упрощённая схема:

```text
                  APPLICATION
                       |
                       v
              CORE INTERACTION
                       |
          +------------+------------+
          |            |            |
          v            v            v
      COMMAND        QUERY        EVENT
        BUS           BUS          BUS
          |            |            |
          v            v            v
      MODULE A     MODULE B     EVENT HANDLERS
                                     |
                                     v
                                  MODULE C
```

Это логическая схема, а не требование к физическому размещению компонентов.

## 7. Module Contracts

Каждый модуль предоставляет другим модулям только те возможности, которые официально опубликованы через его публичный контракт.

Контракт определяет:

- название операции;
- назначение;
- входные данные;
- выходные данные;
- требования к полномочиям;
- возможные ошибки;
- гарантии выполнения;
- правила совместимости версий.

### 7.1. Публичный и внутренний интерфейсы

Необходимо разделять:

**Public Interface** — интерфейс, доступный другим модулям.

**Internal Interface** — внутренние компоненты, доступные только самому модулю.

Другие модули могут использовать только Public Interface.

### 7.2. Стабильность контрактов

Изменение контракта не должно неожиданно ломать существующих потребителей.

Несовместимые изменения требуют:

- изменения версии контракта;
- анализа зависимых модулей;
- согласованного перехода;
- тестирования совместимости.

Подробные правила будут закреплены в Module Contract Specification V1.0.

## 8. Command Bus

Command Bus предназначен для передачи команд модулям.

**Команда — это намерение выполнить конкретное действие.**

Примеры:

- создать проект;
- изменить статус задачи;
- зарегистрировать финансовую операцию;
- добавить участника проекта;
- опубликовать продукт;
- создать уведомление.

### 8.1. Правила команд

1. Команда направляется конкретному обработчику.
2. Команда должна иметь определённую структуру.
3. Команда должна проходить проверку полномочий.
4. Бизнес-правила проверяются модулем-владельцем.
5. Результат выполнения должен быть определён.
6. Ошибки должны возвращаться в стандартизированном формате.

### 8.2. Пример

Пользователь добавляет расход в Partner Workspace.

```text
PARTNER WORKSPACE
        |
        v
COMMAND BUS
        |
        v
FINANCE MODULE
        |
        v
VALIDATION
        |
        v
SAVE EXPENSE
        |
        v
RESULT
```

Partner Workspace не должен самостоятельно создавать запись во внутренних таблицах Finance.

Он передаёт команду, а Finance самостоятельно выполняет операцию.

### 8.3. Синхронное выполнение

На первом этапе Command Bus может работать внутри одного приложения.

Команда передаётся обработчику, результат возвращается вызывающему сценарию.

Отдельная инфраструктура сообщений для этого не требуется.

## 9. Query Bus

Query Bus предназначен для получения данных без изменения состояния системы.

**Query — это запрос информации.**

Примеры:

- получить список проектов пользователя;
- получить финансовую сводку проекта;
- получить состояние подписок;
- получить список задач;
- получить сведения о доступных продуктах.

### 9.1. Правила запросов

1. Запрос должен направляться через публичный интерфейс владельца данных.
2. Query не должен изменять состояние системы.
3. Ответ должен содержать только разрешённые сведения.
4. Должна выполняться проверка полномочий.
5. Формат ответа должен определяться контрактом.
6. Внутренняя структура данных владельца не должна раскрываться потребителю.

### 9.2. Пример

Partner Workspace формирует общую страницу состояния проекта.

```text
PARTNER WORKSPACE
        |
        +------> PROJECTS QUERY
        |
        +------> TASKS QUERY
        |
        +------> FINANCE QUERY
        |
        +------> SERVICES QUERY
        |
        +------> ANALYTICS QUERY
        |
        v
PROJECT OVERVIEW
```

Каждый модуль предоставляет только те данные, которыми он владеет.

Partner Workspace объединяет полученные результаты для отображения пользователю.

**Важно:** Query Bus не должен превращаться в механизм произвольного доступа к базе данных.

## 10. Event Bus

Event Bus предназначен для передачи информации о факте произошедшего изменения.

**Событие сообщает, что определённое действие уже произошло.**

Примеры:

- ProjectCreated;
- ProjectStatusChanged;
- TaskCompleted;
- ExpenseRecorded;
- PartnerAdded;
- ProductPublished;
- AgreementSigned.

### 10.1. Основное назначение

События позволяют другим модулям реагировать на изменения без прямой зависимости от внутренней реализации источника.

Пример:

```text
PROJECTS MODULE
       |
       v
PROJECT CREATED
       |
       v
EVENT BUS
       |
       +------> MEMORY
       |
       +------> NOTIFICATIONS
       |
       +------> ANALYTICS
```

После создания проекта другие модули могут выполнить собственные действия.

Projects не должен знать, как именно Notifications отправляет уведомления или как Analytics рассчитывает показатели.

### 10.2. События не заменяют команды и запросы

Это принципиальное разграничение.

| Механизм | Назначение |
|---|---|
| Command Bus | Попросить выполнить действие |
| Query Bus | Получить информацию |
| Event Bus | Сообщить о произошедшем факте |

Неправильно использовать Event Bus для абсолютно всех операций.

Например, если интерфейсу нужно немедленно получить список проектов, необходимо использовать Query, а не создавать событие с ожиданием ответа.

### 10.3. Обработка событий

Обработчик события должен:

- знать, какие события он принимает;
- проверять корректность входных данных;
- выполнять только свою ответственность;
- корректно обрабатывать повторную доставку;
- фиксировать результат обработки;
- не изменять чужие данные напрямую.

Подробная архитектура событий будет описана в Event System Specification V1.0.

## 11. Process Manager

Некоторые операции требуют участия нескольких модулей.

Для таких процессов используется Process Manager.

Он координирует последовательность действий, но не забирает бизнес-логику у участвующих модулей.

### 11.1. Пример: подключение нового партнёра

Предположим, владелец одобряет заявку партнёра.

Процесс может выглядеть так:

1. Intake подтверждает принятие заявки.
2. People & Access создаёт или связывает пользователя.
3. Partnerships фиксирует партнёрские отношения.
4. Projects назначает партнёра на проект.
5. Access выдаёт необходимые полномочия.
6. Notifications отправляет уведомление.
7. Activity & Audit фиксирует действия.

Process Manager управляет последовательностью и состоянием процесса.

Каждый модуль самостоятельно отвечает за собственные операции.

### 11.2. Ошибки и частичное выполнение

Нельзя предполагать, что многоэтапная операция всегда выполняется полностью.

Например:

- партнёрская запись создана;
- проект создан;
- выдача доступа завершилась ошибкой.

Система должна знать, на каком этапе остановился процесс.

Для этого Process Manager должен поддерживать:

- состояние процесса;
- завершённые шаги;
- текущий шаг;
- ошибки;
- возможность повторного выполнения;
- предусмотренные компенсационные действия.

### 11.3. Компенсационные действия

Если процесс не может завершиться, система должна определить, что делать с уже выполненными шагами.

Например:

- отменить назначение участника;
- отозвать выданные полномочия;
- перевести процесс в состояние ожидания ручного вмешательства.

При этом компенсация не всегда означает физическое удаление ранее созданных данных.

Финансовые операции, подписанные документы и юридически значимые действия требуют особого подхода.

**Важно:** компенсационные действия должны быть определены бизнес-правилами соответствующих модулей. Process Manager не имеет права самостоятельно отменять операции в обход владельцев данных.

## 12. Access Context

Access Context — единый контекст пользователя и полномочий, сопровождающий межмодульное взаимодействие.

Он необходим, чтобы модули не принимали решения о доступе на основании непроверенных данных из пользовательского интерфейса.

### 12.1. Состав контекста

Предварительно контекст должен включать:

- идентификатор пользователя;
- идентификатор сессии или аутентифицированного субъекта;
- активное пространство;
- идентификатор проекта, если операция проектная;
- назначенную роль;
- необходимые разрешения;
- тип инициатора операции;
- идентификатор запроса;
- сведения, необходимые для аудита.

Это логическая модель. Окончательный состав и формат будут определены в документации безопасности и спецификации доступа.

### 12.2. Серверная проверка

Все критические операции должны проверяться на серверной стороне.

Нельзя доверять:

- скрытым элементам интерфейса;
- переданному клиентом названию роли;
- переданному клиентом идентификатору проекта без проверки;
- локальным настройкам пользователя;
- значениям, которые можно изменить через браузер.

### 12.3. Изоляция проектов

Если пользователь имеет доступ к проекту A, это не означает, что он автоматически получает доступ к проекту B.

Проверка должна учитывать одновременно:

- личность пользователя;
- конкретный проект;
- назначение пользователя в проекте;
- разрешённую операцию;
- тип данных.

### 12.4. Принцип минимальных полномочий

Модуль должен получать только тот контекст и те сведения, которые необходимы для выполнения конкретной операции.

Не следует передавать всем модулям полный профиль пользователя и все его разрешения.

## 13. Взаимодействие с Memory System

Raymondovich Memory System (RMS) является самостоятельным модулем платформы.

Он предоставляет другим модулям доступ к знаниям, контексту, принятым решениям и информации, необходимой для продолжения работы.

### 13.1. Memory Interface

Взаимодействие с памятью осуществляется через публичный Memory Interface.

Другие модули не должны напрямую обращаться к внутреннему хранилищу Memory.

### 13.2. Принцип ответственности

Memory не заменяет первичные модули-владельцы данных.

Пример:

- Finance хранит финансовые операции.
- Projects хранит проекты.
- Tasks хранит задачи.
- Activity & Audit хранит историю действий.
- Memory хранит значимый контекст и знания, связанные с этими сведениями.

Memory может хранить ссылку на первоисточник, контекст, краткое описание или производное представление.

Однако она не становится альтернативным местом редактирования первичных данных.

### 13.3. Memory не является обязательным посредником

Не каждый запрос должен проходить через Memory.

Если Partner Workspace запрашивает текущую сумму расходов, он должен обращаться к Finance.

Не нужно сначала запрашивать Memory, а затем получать через неё финансовые сведения.

Memory используется тогда, когда действительно нужен сохранённый контекст или знания.

### 13.4. Контекст для будущих ИИ-агентов

В дальнейшем Memory может предоставлять информацию агентам:

- Development Agent;
- Marketing Agent;
- Finance Agent;
- Project Manager Agent;
- Analytics Agent.

Перед передачей контекста необходимо проверять:

- пользователя, от имени которого работает агент;
- проект;
- полномочия;
- уровень конфиденциальности;
- допустимый объём информации.

Фильтрация должна выполняться серверной частью.

Нельзя рассчитывать на то, что ИИ-агент самостоятельно правильно ограничит доступ к информации.

### 13.5. Ограничение первой версии

Векторный поиск, embeddings и дополнительные поисковые механизмы не являются обязательными условиями запуска первой версии.

Их внедрение должно зависеть от реальных сценариев использования Memory.

## 14. Outbox и надёжность событий

При передаче событий необходимо исключить ситуацию, когда данные успешно сохранены, но соответствующее событие потеряно.

Для этого архитектура должна предусматривать механизм Outbox.

### 14.1. Проблема

Предположим:

1. Finance сохраняет финансовую операцию.
2. Finance должен отправить событие ExpenseRecorded.
3. Происходит сбой между сохранением данных и отправкой события.

В результате операция существует, но Analytics и другие подписчики не получают информацию о ней.

Это приводит к рассинхронизации.

### 14.2. Решение

При использовании Outbox информация о событии сохраняется согласованно с изменением данных в рамках транзакции владельца.

Упрощённая схема:

```text
FINANCE MODULE
      |
      v
DATABASE TRANSACTION
      |
      +------> SAVE EXPENSE
      |
      +------> SAVE OUTBOX EVENT
      |
      v
TRANSACTION COMMIT
      |
      v
OUTBOX PROCESSOR
      |
      v
EVENT BUS
      |
      v
EVENT HANDLERS
```

Таким образом, система получает возможность повторно отправить событие после сбоя.

### 14.3. Обязательные требования

Механизм должен предусматривать:

- сохранение события до публикации;
- повторную отправку;
- регистрацию статуса публикации;
- обработку ошибок;
- защиту от потери событий;
- идемпотентную обработку получателями.

Техническая реализация будет определена в Event System Specification V1.0.

## 15. Interaction Logger и Activity & Audit

Эти два механизма нельзя смешивать.

Они выполняют разные задачи.

### 15.1. Interaction Logger

Interaction Logger предназначен для технической регистрации взаимодействий между модулями.

Он может фиксировать:

- инициатора;
- вызывающий модуль;
- целевой модуль;
- тип взаимодействия;
- идентификатор контракта;
- идентификатор запроса;
- время выполнения;
- результат;
- техническую ошибку;
- длительность обработки.

Его задача — диагностика, наблюдаемость и поиск технических проблем.

### 15.2. Activity & Audit

Activity & Audit отвечает за регистрацию значимых действий в системе.

Примеры:

- пользователь вошёл в Owner Control Center;
- владелец изменил права партнёра;
- партнёр добавил финансовую операцию;
- проект изменил статус;
- договор был подписан;
- владелец удалил участника.

Это не просто технический журнал вызовов, а история значимых действий.

### 15.3. Принцип разделения

| Interaction Logger | Activity & Audit |
|---|---|
| Технические взаимодействия | Значимые действия |
| Ошибки вызовов | Изменения состояния |
| Время выполнения | Кто и что сделал |
| Трассировка | История и контроль |
| Диагностика | Аудит |

В дальнейшем эти механизмы могут использовать общую инфраструктуру логирования, но их назначение и правила хранения должны оставаться разделёнными.

## 16. Обработка ошибок

Все межмодульные взаимодействия должны иметь предсказуемую обработку ошибок.

Необходимо различать как минимум следующие категории.

| Категория | Пример |
|---|---|
| Validation Error | Некорректные входные данные |
| Authorization Error | Недостаточно полномочий |
| Not Found | Объект не найден |
| Conflict | Операция конфликтует с текущим состоянием |
| Business Rule Error | Нарушено бизнес-ограничение |
| Dependency Error | Недоступен другой модуль |
| Timeout | Истекло время ожидания |
| Internal Error | Внутренняя техническая ошибка |

### 16.1. Требования

- Ошибки не должны содержать секретные данные.
- Внутренние технические подробности не должны передаваться пользователю без необходимости.
- Ошибки должны иметь идентификатор для диагностики.
- Повторные операции должны учитывать идемпотентность.
- Система должна различать временные и постоянные ошибки.

### 16.2. Повторные операции

Автоматический повтор допустим не для всех операций.

Например, повторное получение списка проектов безопаснее, чем повторное создание финансовой операции.

Для изменяющих состояние команд должны предусматриваться механизмы защиты от дублирования.

## 17. Идемпотентность

Идемпотентность означает, что повторное выполнение одной и той же операции не приводит к нежелательному повторному эффекту.

Это особенно важно для:

- финансовых операций;
- создания пользователей;
- регистрации партнёров;
- обработки событий;
- оплаты;
- изменения полномочий;
- интеграций с внешними сервисами.

### 17.1. Требование

Для операций, где повтор может привести к дублированию или финансовому ущербу, должен использоваться механизм идентификации операции.

Например, повторная отправка одной команды регистрации расхода не должна автоматически создавать второй расход.

Конкретные правила ключей идемпотентности будут определены в соответствующих контрактах и спецификации событий.

## 18. Трассировка взаимодействий

Каждое межмодульное взаимодействие должно иметь идентификатор корреляции.

Это позволяет связать действия нескольких модулей в рамках одного пользовательского сценария.

Пример:

```text
REQUEST: RQ-1001

PARTNER WORKSPACE
       |
       v
FINANCE
       |
       v
EVENT BUS
       |
       +------> ANALYTICS
       |
       +------> MEMORY
       |
       +------> NOTIFICATIONS
```

Все связанные действия должны позволять восстановить цепочку выполнения.

Это необходимо для:

- поиска ошибок;
- расследования проблем;
- анализа задержек;
- проверки корректности процессов;
- технической поддержки.

Идентификаторы трассировки не должны использоваться вместо проверки полномочий.

## 19. Синхронное и асинхронное взаимодействие

Необходимо разделять операции по характеру выполнения.

### 19.1. Синхронное взаимодействие

Используется, когда вызывающему сценарию нужен немедленный результат.

Примеры:

- получение списка проектов;
- проверка полномочий;
- получение финансовой сводки;
- создание задачи;
- изменение статуса проекта.

Для этого используются Command Bus и Query Bus.

### 19.2. Асинхронное взаимодействие

Используется, когда операция может выполняться независимо от первоначального пользовательского запроса.

Примеры:

- отправка уведомлений;
- обновление аналитических показателей;
- сохранение контекста в Memory;
- обработка интеграционных событий;
- выполнение длительного процесса подключения партнёра.

Для этого используются Event Bus и Process Manager.

### 19.3. Общий принцип

Пользовательский интерфейс не должен ожидать завершения всех вторичных процессов, если для выполнения основной операции это не требуется.

Например, после успешного создания проекта система может сразу сообщить об успехе, а уведомления и обновление аналитики выполнить отдельно.

При этом состояние дополнительных процессов должно быть контролируемым.

## 20. Module Registry и Contract Registry

Эти компоненты должны обеспечивать учёт доступных модулей и их публичных интерфейсов.

### 20.1. Module Registry

Содержит сведения о зарегистрированных модулях:

- идентификатор;
- название;
- назначение;
- версия;
- статус;
- доступные возможности;
- технические зависимости.

На первом этапе достаточно статической регистрации модулей в приложении или конфигурации.

Динамическая система обнаружения сервисов не требуется.

### 20.2. Contract Registry

Содержит сведения о публичных контрактах:

- идентификатор;
- владелец;
- версия;
- назначение;
- тип взаимодействия;
- статус;
- совместимость.

Это позволит контролировать, какие возможности доступны другим модулям.

### 20.3. Важное ограничение

Наличие модуля в реестре не означает автоматическое предоставление ему доступа ко всем остальным модулям.

Доступ определяется контрактами и правилами полномочий.

## 21. Практические архитектурные сценарии

Для проверки архитектуры необходимо рассмотреть реальные сценарии платформы.

### 21.1. Public Space: отправка заявки

Посетитель отправляет заявку на участие в партнёрском проекте.

```text
PUBLIC SPACE
     |
     v
INTAKE
     |
     v
VALIDATION
     |
     v
SAVE APPLICATION
     |
     v
APPLICATION RECEIVED
     |
     +------> EVENT BUS
                  |
                  +------> NOTIFICATIONS
                  |
                  +------> ACTIVITY & AUDIT
```

Требования:

- публичный пользователь не получает доступ к Owner Control Center;
- заявка сохраняется в Intake;
- уведомление владельцу отправляется отдельно;
- публичный интерфейс не обращается напрямую к внутренним таблицам Intake;
- заявка становится доступной владельцу через его закрытое пространство.

### 21.2. Owner Control Center: создание проекта

Владелец создаёт новый проект.

```text
OWNER CONTROL CENTER
          |
          v
     COMMAND BUS
          |
          v
       PROJECTS
          |
          v
    VALIDATION
          |
          v
    SAVE PROJECT
          |
          v
   PROJECT CREATED
          |
          v
      EVENT BUS
          |
          +------> MEMORY
          |
          +------> NOTIFICATIONS
          |
          +------> ACTIVITY & AUDIT
```

Требования:

- Projects отвечает за создание проекта;
- владелец имеет необходимые полномочия;
- событие публикуется после успешного сохранения;
- другие модули не изменяют данные Projects напрямую.

### 21.3. Partner Workspace: финансовая сводка

Партнёр открывает финансовую панель проекта.

```text
PARTNER WORKSPACE
         |
         v
    ACCESS CHECK
         |
         v
      QUERY BUS
         |
         v
       FINANCE
         |
         v
   FINANCIAL SUMMARY
         |
         v
   PARTNER INTERFACE
```

Требования:

- Finance проверяет полномочия на предоставление данных;
- данные ограничены конкретным проектом;
- партнёр видит только разрешённые финансовые сведения;
- финансовые операции не изменяются;
- интерфейс не получает внутренние данные Finance.

### 21.4. External Project Workspace: добавление участника

Владелец стороннего проекта приглашает участника.

Процесс должен проходить через:

1. People & Access;
2. Projects или соответствующий модуль управления участниками проекта;
3. Access;
4. Notifications;
5. Activity & Audit.

Проверяется принадлежность проекта и право приглашать новых участников.

Участник не получает доступа к другим внешним проектам или внутренней информации Raymondovich.

Этот сценарий дополнительно проверяет, что архитектура поддерживает изоляцию разных типов проектов.

## 22. Ограничения первой версии

Первая версия архитектуры должна быть достаточно простой для реализации, но не должна нарушать установленные границы.

### 22.1. Разрешается

- один backend;
- единое приложение;
- общая инфраструктура;
- единая база данных;
- логическое разделение модулей;
- внутрипроцессный Command Bus;
- внутрипроцессный Query Bus;
- внутрипроцессный Event Bus;
- базовый Process Manager;
- Outbox;
- единый Access Context;
- централизованная регистрация модулей и контрактов.

### 22.2. Не требуется на старте

- микросервисная инфраструктура;
- отдельный брокер сообщений;
- динамическое обнаружение сервисов;
- распределённые транзакции;
- сложная система оркестрации;
- отдельный сервер для каждого модуля;
- векторная база данных;
- распределённая система логирования.

### 22.3. Запрет на упрощения, нарушающие архитектуру

Нельзя ради скорости:

- объединять бизнес-логику всех модулей в одном сервисе;
- разрешать прямые обращения к чужим таблицам;
- обходить публичные контракты;
- передавать полный доступ к данным через общий объект;
- смешивать первичные данные и производные представления;
- отключать серверную проверку полномочий.

Упрощать инфраструктуру можно. Упрощать границы ответственности нельзя.

## 23. Возможность дальнейшего масштабирования

Архитектура должна допускать постепенное выделение отдельных модулей в самостоятельные сервисы.

Например, в будущем могут быть выделены:

- Notifications;
- Analytics;
- Memory;
- Services & Integrations.

Однако это не означает, что их нужно сразу разрабатывать как отдельные приложения.

Для будущего выделения необходимо:

1. иметь стабильные контракты;
2. не допускать прямого доступа к внутренним данным;
3. использовать явные идентификаторы и форматы сообщений;
4. обеспечить независимое владение данными;
5. предусмотреть обработку сетевых ошибок;
6. поддерживать повторные операции;
7. обеспечить трассировку межмодульных процессов.

При таком подходе переход от внутрипроцессного взаимодействия к сетевому не должен требовать переписывания бизнес-логики всех модулей.

## 24. Архитектурные антипаттерны

Следующие решения считаются нарушением архитектуры.

| Антипаттерн | Почему запрещён |
|---|---|
| God Object | Сосредоточение всей бизнес-логики в одном компоненте |
| Shared Business Logic | Общая бизнес-логика без определённого владельца |
| Direct Database Access | Обход публичных интерфейсов модулей |
| Circular Dependencies | Циклические зависимости |
| Event Everything | Использование событий для всех типов взаимодействия |
| Memory as Main Database | Подмена первичных данных системой памяти |
| UI Authorization | Проверка прав только на стороне интерфейса |
| Hidden Coupling | Зависимость от внутренних деталей другого модуля |
| Uncontrolled Retry | Повторное выполнение без защиты от дублирования |
| Shared Mutable State | Неконтролируемое изменение общих данных |

## 25. Критерии архитектурной готовности

Архитектура взаимодействия считается готовой к использованию в разработке, если выполнены следующие условия.

### Независимость модулей

- [ ] Определено владение данными.
- [ ] Определены публичные интерфейсы.
- [ ] Запрещён прямой доступ к внутренним компонентам других модулей.
- [ ] Исключены циклические зависимости.
- [ ] Бизнес-логика остаётся внутри владельца предметной области.

### Взаимодействие

- [ ] Определено назначение Command Bus.
- [ ] Определено назначение Query Bus.
- [ ] Определено назначение Event Bus.
- [ ] Определены правила Process Manager.
- [ ] Определены правила публикации событий.

### Безопасность

- [ ] Определён Access Context.
- [ ] Все критические операции требуют серверной проверки полномочий.
- [ ] Обеспечена изоляция проектов.
- [ ] Определены границы доступа к Memory.
- [ ] Предусмотрена защита от передачи лишних данных.

### Надёжность

- [ ] Предусмотрен Outbox.
- [ ] Определены правила идемпотентности.
- [ ] Предусмотрена обработка ошибок.
- [ ] Предусмотрена трассировка.
- [ ] Определена обработка повторных событий.

### Масштабирование

- [ ] Архитектура не привязана к одному способу физического размещения модулей.
- [ ] Контракты допускают независимое развитие.
- [ ] Возможность будущего выделения сервисов не требует перестройки бизнес-логики.

## 27. Связанные документы

Core Interaction Architecture является базовым документом для следующих спецификаций:

| Документ | Назначение |
|---|---|
| Module Contract Specification V1.0 | Форматы контрактов, правила публикации и совместимости |
| Event System Specification V1.0 | События, Outbox, доставка, повторная обработка |
| Memory System Architecture V1.0 | Память, хранение знаний, контекст и ИИ-агенты |
| Security Architecture | Безопасность, идентификация, полномочия, изоляция |
| Development Standards | Правила реализации архитектуры в коде |

Все последующие документы должны соответствовать принципам этой архитектуры.

Если в последующих спецификациях обнаруживается противоречие, его необходимо разрешить до начала реализации.

## 28. Итоговое архитектурное правило

Архитектура Raymondovich.ru строится на независимых функциональных модулях, каждый из которых владеет собственной бизнес-логикой и первичными данными.

Модули не обращаются напрямую к внутренней реализации друг друга.

Взаимодействие осуществляется через Core Interaction System с использованием публичных контрактов, команд, запросов и событий.

Длительные процессы координируются Process Manager. Полномочия проверяются серверной стороной через единый контекст доступа. Memory предоставляет знания и контекст, но не подменяет первичные источники данных.

На первом этапе используется модульный монолит. Архитектура должна позволять масштабировать отдельные модули независимо без необходимости перестраивать всю платформу.

**Основной принцип: независимость модулей при централизованных правилах взаимодействия.**
