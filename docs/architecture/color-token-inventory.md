# Инвентаризация цветовой системы и токенов Raymondovich

> Версия: 0.1  
> Статус: Аудит — завершён, целевая модель — на согласовании  
> Дата: 2026-11-11  
> Область: `source/design-system/`, с отдельными замечаниями по авторизованному интерфейсу

## 1. Цель и границы

Документ фиксирует фактическое состояние цветовой системы до её нормализации. Анализ выполнен по исходным CSS, HTML и JavaScript в ветке `main`.

Проверены:
- `source/design-system/tokens/tokens.css`;
- `source/design-system/themes/themes.css`;
- `source/design-system/foundations/foundations.css`;
- `source/design-system/components/components.css`;
- все CSS-файлы в `source/design-system/patterns/`;
- подключение CSS в `index.html`;
- `source/presentation/public/scripts/theme.js`.

В этой работе не менялись CSS, JavaScript, HTML, маршруты, бизнес-логика, данные, БД, RLS, интеграции и секреты. Это статическая инвентаризация: фактический рендеринг, вычисленные цвета браузера, iPhone Safari и Telegram Mini App не проверялись.

## 2. Текущее устройство

### 2.1. Подключение слоёв

В `index.html` стили подключаются в следующем порядке:

1. `tokens/tokens.css`;
2. `foundations/foundations.css`;
3. `themes/themes.css`;
4. `components/components.css`;
5. паттерны интерфейса.

Это означает, что базовые значения объявляются в токенах, светлая тема переопределяет часть значений после foundations, а компоненты и паттерны потребляют итоговые CSS custom properties. Сам порядок подключения в целом логичен.

### 2.2. Базовый режим

`tokens.css` задаёт на `:root`:
- `color-scheme: dark`;
- базовые цвета тёмной темы;
- семантические токены Owner, Ideas и Workspace;
- фирменные градиенты;
- типографические и геометрические переменные;
- safe-area и Telegram fallback-переменные;
- токены оболочки приложения и профиля.

По факту базовый слой одновременно выполняет две роли: содержит общие дизайн-примитивы и служит полной палитрой тёмной темы. Это работает, но смешивает Foundation и Theme Mapping.

### 2.3. Светлая тема

`themes.css` содержит переопределения под селектором `:root[data-theme="light"]`. В файле обнаружено 145 определений переменных, соответствующих переменным базового файла `tokens.css`.

Светлая тема уже не является простой инверсией: у неё отдельно настроены фоны, поверхности, текст, разделители, Owner, Ideas, Workspace, градиенты, оболочка и профиль. Это хорошая основа для равноправного развития двух тем.

Однако часть цветовых переменных остаётся общей с тёмной темой или не имеет отдельного light mapping. Это нужно проверить и исправить до признания цветовой системы завершённой.

## 3. Объём и структура токенов

В `tokens.css` обнаружено 179 определений CSS custom properties. В `themes.css` — 145 определений. Дублирующихся имён внутри самого `tokens.css` при статическом разборе не обнаружено.

Текущие семейства:

| Семейство | Назначение | Наблюдение |
|---|---|---|
| `--color-*` | Фоны, текст, линии, статусы и акценты | Смешаны общие семантические и модульные токены |
| `--gradient-*` | Фирменные и компонентные градиенты | Часть градиентов жёстко привязана к тёмной палитре |
| `--shadow-*` | Тени и подсветки | Часть значений имеет светлую тему, часть остаётся общей |
| `--ws-*` | Workspace / Projects / Ideas | Большое семейство, местами повторяет общую семантику |
| `--color-owner-*` | Owner Control Center | Имеет собственное отображение для обеих тем |
| `--color-ideas-*` | Ideas | Имеет собственное отображение для обеих тем |
| `--color-app-shell-*` | Оболочка авторизованного интерфейса | Имеет light mapping |
| `--color-profile-*` | Профиль | Имеет light mapping |
| `--font-*`, `--space-*`, `--radius-*` | Типографика и геометрия | Не являются цветовыми токенами |
| `--safe-*`, `--telegram-*`, `--pin-*` | Платформенные и специальные значения | Требуют отдельной классификации |

Наличие 145 переопределений не означает, что все цветовые значения корректно тематизированы: часть из оставшихся 34 переменных — структурные и платформенные, но среди них есть и цветовые значения, которые требуют отдельного решения.

## 4. Подтверждённые пробелы тематизации

### 4.1. Глобальный акцент

В базовом файле заданы:
- `--color-accent: #ff762f`;
- `--color-accent-bright: #ff9a5b`;
- `--gradient-accent` с оранжевыми оттенками.

В `themes.css` для них нет отдельного light mapping. Поэтому светлая тема наследует яркие значения тёмной темы.

Расчёт контрастности по формуле WCAG для непрозрачных цветов:
- `#ff762f` на белом фоне: около **2.66:1**;
- `#ff762f` на `#f3f4f6`: около **2.42:1**;
- `#d65b1f` на белом фоне: около **3.91:1**;
- `#b94c19` на белом фоне: около **5.11:1**.

Следствие: глобальный оранжевый `#ff762f` не подходит для мелкого текста и значимых контуров на светлых поверхностях, если требуется WCAG 2.2 AA. В Ideas для светлой темы уже используется более тёмный акцент `#d65b1f`, а для отдельных элементов — `#b94c19`. Это показывает, что в продукте уже есть более подходящие light-варианты, но они не распространены на общую семантику.

Контраст рассчитан только для указанных непрозрачных пар foreground/background. Для прозрачных цветов, градиентов, blur и реального фона необходим отдельный расчёт по фактическому композитному цвету.

### 4.2. Контрастный текст кнопки

В `components.css` у `.button.primary` текст имеет жёстко заданный цвет `#17100b`, вместо отдельного семантического токена текста на primary-поверхности. Аналогичное назначение есть у `--color-ideas-accent-contrast` и `--ws-button-text`.

Нужно оставить один однозначный контракт: токен foreground для primary action должен быть связан с конкретной темой и конкретным фоном кнопки. Цвет нельзя выбирать независимо от градиента кнопки.

### 4.3. Workspace-токены

В `tokens.css` семейство `--ws-*` содержит множество отдельных значений, в том числе:
- `--ws-card-focused`;
- `--ws-card-compact`;
- `--ws-group-surface`;
- `--ws-group-line`;
- `--ws-progress-track`;
- `--ws-card-line`;
- `--ws-card-text`;
- `--ws-card-muted`;
- `--ws-project-*`;
- `--ws-empty-*`.

Для светлой темы большинство этих значений переопределено, что правильно. Но по смыслу часть токенов описывает не семантические роли, а конкретные поверхности или состояния конкретного рабочего пространства. В будущем их следует оставить на компонентном уровне, а общие роли связать с Semantic tokens. Механически удалять или объединять их нельзя: это может изменить различия Projects, Ideas и Owner Control Center.

### 4.4. Специальные и платформенные токены

Не имеют самостоятельного light mapping:
- `--telegram-color-*-fallback`;
- `--pin-background`, `--pin-text`, `--pin-title`, `--pin-accent`, `--pin-submit-text`;
- часть градиентов Ideas;
- некоторые общие акцентные значения.

Telegram fallback сейчас явно содержит тёмные значения. Это может быть корректно для fallback в тёмном Telegram-контексте, но не должно автоматически считаться универсальной палитрой Mini App. Нужно отдельно определить источник истины для темы в Telegram: выбор пользователя, системная тема или Telegram theme parameters, а также приоритеты этих источников.

PIN Lock имеет отдельные фиксированные тёмные цвета непосредственно в CSS, поэтому сейчас его оформление не следует общей теме полностью. Нужно принять отдельное продуктовое решение: PIN Lock всегда остаётся фирменным тёмным экраном или адаптируется к выбранной теме. Самостоятельно менять это поведение нельзя.

## 5. Цвета вне токенов

Статический анализ обнаружил цветовые литералы непосредственно в CSS паттернах и компонентах. Основные подтверждённые места:

| Файл | Примеры | Риск |
|---|---|---|
| `foundations/foundations.css` | Цвет выделения текста задан rgba-литералом | Выделение не управляется тематической семантикой |
| `components/components.css` | Цвет текста primary-кнопки задан hex; scrim имеет фиксированный чёрный цвет | Нет единого тематического контракта для этих ролей |
| `patterns/authentication.css` | Цвета текста, границ, полей, focus, error и success заданы литералами и fallback-переменными старого формата | Авторизация частично обходит текущую палитру и не имеет полноценного light mapping |
| `patterns/pin-lock.css` | Фон, границы, текст, поля, состояния и кнопки содержат фиксированные тёмные значения | PIN Lock фактически имеет собственную фиксированную тему |
| `patterns/projects.css` | Два локальных rgba-значения | Небольшое локальное дублирование оформления |
| `patterns/ideas.css` | Локальный rgba-фон | Небольшое локальное дублирование оформления |
| `patterns/public-layout.css` | Локальный rgba-цвет атмосферы | Публичная часть частично обходит токены |

Особенно важно исправить не только hex/rgba. В `authentication.css` используются fallback-переменные вида `--text-muted`, `--border-color`, `--surface-elevated`, `--text-primary`, `--surface-input`, `--accent`. Они не совпадают с текущим основным контрактом `--color-*`. Пока не доказано, что эти старые переменные определены где-либо ещё; при отсутствии определений срабатывают fallback-значения из самого файла.

## 6. Текущая логика переключения темы

`theme.js`:
1. читает `raymondovich-theme` из localStorage;
2. если сохранённого значения нет, использует `prefers-color-scheme`;
3. применяет `data-theme="light"` или `data-theme="dark"` к `:root`;
4. переключает тему по нажатию на элемент с `data-theme-toggle`;
5. сохраняет выбор в localStorage.

Плюсы:
- выбор пользователя сохраняется;
- начальная тема учитывает системную настройку;
- CSS получает один корневой атрибут для отображения темы.

Ограничения:
- логика не содержит явной интеграции с Telegram theme parameters;
- не найден отдельный режим «следовать системе» после того, как пользователь вручную сохранил тему;
- метатег `theme-color` в HTML имеет фиксированное тёмное значение и не обновляется при переключении темы;
- начальное применение темы выполняется внешним модулем, а не inline-скриптом до первой отрисовки; возможное краткое появление базовой темы до выполнения модуля требует браузерной проверки.

Эти пункты зафиксированы как вопросы и риски, а не как доказанные визуальные дефекты.

## 7. Целевая модель токенов

Предлагается не переписывать текущие переменные одним большим изменением, а постепенно привести их к следующей модели:

### Уровень 1 — Foundation

Независимые от назначения примитивы:
- нейтральная шкала;
- фирменная оранжевая шкала;
- статусные цветовые шкалы;
- прозрачность;
- базовые градиенты и параметры материалов;
- геометрия, типографика и интервалы.

Foundation не должен напрямую использоваться в прикладных компонентах, кроме обоснованных декоративных случаев.

### Уровень 2 — Semantic

Назначение цвета независимо от конкретного hex:
- `--color-background`;
- `--color-surface`, `--color-surface-raised`;
- `--color-text-primary`, `--color-text-secondary`, `--color-text-tertiary`;
- `--color-border`, `--color-divider`;
- `--color-accent`, `--color-accent-foreground`, `--color-accent-subtle`;
- `--color-success`, `--color-warning`, `--color-danger`;
- `--color-focus-ring`, `--color-selection`;
- семантические тени и материалы.

Имена здесь предварительные, это целевая схема, а не утверждённый API токенов.

### Уровень 3 — Component

Только значения, которые действительно уникальны для компонента:
- app shell / navigation;
- profile;
- Owner Control Center;
- Ideas;
- Projects;
- PIN Lock;
- authentication;
- Liquid Glass surfaces.

Компонентные токены должны ссылаться на Semantic, если у них нет обоснованной уникальной потребности.

### Уровень 4 — Theme Mapping

Отдельные полные карты:
- `:root[data-theme="light"]`;
- `:root[data-theme="dark"]`.

Рекомендуется сделать явными оба режима в одном theme layer. Тёмная тема не должна существовать только как побочный эффект базовых значений Foundation. Для каждой темы отдельно задаются все обязательные семантические роли, включая акцент, foreground акцента, статусы, focus, selection, поверхности и материалы.

Существующие имена `--color-bg`, `--color-text`, `--ws-*` и другие нельзя переименовывать в рамках инвентаризации. Миграция должна быть постепенной, с совместимыми alias-токенами и проверкой всех потребителей.

## 8. Требования к двум равноправным темам

Для каждой темы отдельно необходимо определить и проверить:
- основной фон и уровни поверхностей;
- основной, вторичный и вспомогательный текст;
- границы и разделители;
- основной и вторичный акцент;
- текст на акцентной поверхности;
- success, warning, danger и info;
- hover, pressed, focus-visible, disabled, loading;
- selected, expanded, empty и error;
- тени и elevation;
- прозрачные поверхности и blur;
- контраст на реальном фоне.

Светлая и тёмная темы должны пройти одинаковый набор проверок. Минимальная цель контрастности текста — WCAG 2.2 AA: 4.5:1 для обычного текста и 3:1 для крупного текста; для значимых графических объектов и границ компонентов применяется соответствующее требование 3:1. Прозрачные и градиентные поверхности проверяются по итоговому композитному цвету, а не только по исходным значениям.

## 9. Рекомендуемый порядок нормализации

1. Утвердить семантическую карту цветовых ролей и контракт нейминга.
2. Зафиксировать отдельные полные light/dark mappings, не меняя визуальный результат.
3. Исправить глобальные акценты и foreground для primary action с проверкой контраста.
4. Перевести authentication и PIN Lock на согласованный тематический контракт после решения о поведении PIN Lock.
5. Перевести оставшиеся цветовые литералы в CSS на семантические или компонентные токены.
6. Разделить общие semantic tokens и локальные `--ws-*` component tokens без потери текущих различий.
7. Проверить все авторизованные экраны в обеих темах, затем публичную часть и Telegram Mini App.
8. Проверить контраст WCAG 2.2 AA, reduced motion, отсутствие вспышки неправильной темы и обновление meta theme-color.

Каждый шаг должен быть отдельным проверяемым срезом. Не выполнять массовое переименование переменных до карты их использования.

## 10. Решения, требующие подтверждения владельца

До реализации необходимо утвердить:
1. **Акцент светлой темы:** использовать более тёмный оранжевый для текста, иконок и контуров, сохранив более яркий оранжевый для декоративных заливок и градиентов?
2. **PIN Lock:** всегда тёмный фирменный экран или полностью следует выбранной теме?
3. **Telegram:** при первом запуске Mini App следовать Telegram theme parameters, системной теме или сохранённому выбору пользователя? Какой источник имеет приоритет при конфликте?
4. **Тема по умолчанию:** сохраняем текущую логику «сохранённый выбор → системная тема → dark fallback»?

## 11. Ограничения аудита

- Анализ основан на статическом чтении репозитория `main`.
- Реальные вычисленные цвета, прозрачность поверх контента, градиенты и blur не измерялись в браузере.
- Контрастные отношения рассчитаны только для отдельных непрозрачных цветовых пар, указанных в документе.
- Не проверялись iPhone Safari, Telegram Mini App, Android и desktop rendering.
- Не выполнялись build, lint, автоматические тесты и браузерные тесты.
- CSS, JS, HTML и поведение приложения не изменялись.
