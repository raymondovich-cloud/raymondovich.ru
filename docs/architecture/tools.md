# Архитектура раздела «Инструменты»

**Дата:** 09.10.2026  
**Статус:** Базовая схема БД и первая версия UI реализованы; функциональная и браузерная проверка продолжается.

## 1. Назначение

Раздел «Инструменты» — закрытый реестр сервисов и технических ресурсов, используемых во всей экосистеме RAYMONDOVICH. Он должен показывать, какие инструменты используются, с какими продуктами они связаны и какую роль выполняют.

Раздел является частью административного блока Raymondovich.ru и в перспективе — одним из источников данных для AI Business Analyst.

## 2. Термины и границы

Необходимо различать три сущности:

- **Инструмент / сервис** — внешняя платформа или поставщик возможностей: ChatGPT, GitHub, REG.RU, Supabase.
- **Ресурс** — конкретный объект внутри сервиса или технической инфраструктуры: репозиторий, домен, база данных, сервер, проект в облачной панели, API-интеграция.
- **Проект** — продукт или внутренний проект экосистемы Raymondovich.

Пример: GitHub — инструмент; репозиторий raymondovich.ru — ресурс; Raymondovich.ru — проект. Это разные сущности, даже если названия похожи.

## 3. Пользовательские сценарии

1. В административном блоке открыть «Инструменты» и увидеть реестр сервисов.
2. Открыть сервис и увидеть назначение, статус, ссылку, связанные проекты и зарегистрированные ресурсы.
3. Открыть конкретный ресурс и увидеть сервис-владелец, связанный проект, роль, статус и дату последней проверки.
4. Перейти от инструмента к проекту и обратно.
5. Добавить новый сервис или ресурс без изменения архитектуры других разделов.
6. Находить ресурсы без подтверждённой связи с проектом и связи, требующие проверки.

## 4. Концептуальная модель данных

### 4.1. Tool — инструмент/сервис

Предлагаемые поля:

- id — стабильный идентификатор.
- name — отображаемое название.
- slug — уникальный технический идентификатор.
- category — категория: AI, разработка, домены/DNS, база данных, хостинг/серверы, аналитика, платежи или другая.
- description — назначение инструмента в экосистеме.
- official_url — официальный сайт или панель управления.
- status — active, testing, paused, retired.
- owner_id — владелец записи в рамках существующей модели авторизации.
- created_at, updated_at — даты создания и обновления.
- last_verified_at — дата последней проверки актуальности сведений.

### 4.2. Tool Resource — конкретный ресурс

Предлагаемые поля:

- id — стабильный идентификатор.
- tool_id — ссылка на сервис, которому принадлежит ресурс.
- name — название ресурса.
- resource_type — repository, domain, database, server, api, deployment, dns_zone или other.
- external_id — необязательный идентификатор во внешней системе, если его безопасно хранить.
- resource_url — ссылка на ресурс без секретов и временных токенов.
- environment — production, staging, development или не задано.
- status — active, testing, paused, retired, unknown.
- description — назначение ресурса.
- owner_id — владелец записи.
- last_verified_at, created_at, updated_at — контроль актуальности и изменений.

Ресурс не обязан быть привязан к одному проекту: инфраструктурный ресурс может обслуживать несколько продуктов.

### 4.3. Project ↔ Tool — связь проекта с инструментом

Связь многие-ко-многим. Предлагаемые атрибуты:

- project_id — ссылка на существующий проект.
- tool_id — ссылка на инструмент.
- relationship_type — manual_use, technical_integration, infrastructure_dependency или other.
- purpose — зачем инструмент используется в проекте.
- status — planned, active, paused, retired, needs_verification.
- evidence_note — краткое основание связи или ссылка на подтверждающую документацию.
- last_verified_at — дата проверки связи.

Ограничение уникальности должно не допускать дублирования одной и той же связи с одинаковым типом.

### 4.4. Project ↔ Resource — связь ресурса с проектом

Отдельная связь многие-ко-многим нужна, чтобы указать, какие конкретно репозитории, домены, базы данных или серверы относятся к проекту. Она может включать роль ресурса, статус связи, основание и дату проверки.

Примеры:
- сервис GitHub → ресурс-репозиторий → проект AI Sistem;
- сервис REG.RU → ресурс-домен → проект Raymondovich.ru;
- сервис Supabase → ресурс-база данных → административный блок Raymondovich.ru.

Эти примеры должны быть занесены в реестр как подтверждённые только после проверки фактической конфигурации. Не следует автоматически создавать связи лишь на основании названия проекта.

## 5. Правила достоверности данных

- Явно различать подтверждённые, запланированные и требующие проверки связи.
- Не считать запись в реестре доказательством доступности сервиса, корректности DNS или работоспособности интеграции.
- Хранить дату последней проверки; не представлять устаревшие данные как актуальные.
- Для автоматических проверок в будущем фиксировать источник, время проверки и результат отдельно от ручного описания.
- Не создавать фиктивные ресурсы и связи ради заполнения интерфейса.

## 6. Единый доступ к данным и будущий AI Business Analyst

Раздел должен предоставлять данные через общий application-контракт/сервис доступа к административным данным, а не через прямые запросы AI к таблицам.

Предусмотреть операции чтения реестра инструментов, ресурсов и связей, фильтрацию по проекту/категории/статусу и получение контекста для аналитических запросов. Контракт не должен зависеть от конкретного UI.

На первом этапе AI Business Analyst получает доступ только на чтение. Серверная авторизация обязательна. Клиентский интерфейс и AI не должны обходить политики доступа или получать привилегированные ключи.

## 7. Безопасность

- Использовать существующий Supabase как предпочтительное хранилище, если дальнейшая проверка схемы подтвердит совместимость.
- До изменения базы проверить текущие таблицы проектов, типы идентификаторов, RLS и модель ролей.
- Применять least privilege и RLS ко всем новым таблицам; не полагаться только на скрытие UI.
- Не хранить пароли, API-ключи, access/refresh tokens, секреты деплоя и другие учётные данные в открытом виде в реестре.
- Для секретов при необходимости использовать отдельное защищённое хранилище и контролируемый серверный доступ.
- Ссылки на панели управления не должны содержать секреты, сессионные данные или временные токены.
- AI Business Analyst не получает автоматического доступа к аккаунтам внешних сервисов из-за наличия записи об инструменте.

## 8. Интеграция с существующей архитектурой

Соблюдать текущие слои Raymondovich:

- domain — правила и типы предметной области инструментов, ресурсов и связей;
- application — сценарии чтения/управления реестром и контракт доступа;
- infrastructure — Supabase-адаптеры и будущие интеграции с внешними сервисами;
- presentation — страница списка, карточка инструмента, карточка ресурса и переходы между связанными сущностями;
- memory — только если требуется для состояния приложения; не использовать как замену постоянному хранилищу;
- design — визуальные компоненты без бизнес-логики.

Не добавлять всю функциональность в один файл и не связывать UI напрямую с таблицами Supabase.

## 9. План реализации

1. Сопоставить эту концепцию с фактической схемой projects и моделью авторизации Supabase.
2. Уточнить окончательные поля и внешние ключи, избегая дублирования уже существующих сущностей.
3. Подготовить миграцию базы данных и RLS-политики, но применить их после отдельной проверки.
4. Реализовать application-контракты и адаптер хранилища.
5. Реализовать UI реестра, страницы инструмента и страницы ресурса.
6. Добавить подтверждённые сервисы и связи, помечая непроверенные сведения.
7. Проверить права доступа, CRUD-сценарии, пустые состояния и мобильную адаптацию.
8. После стабилизации использовать тот же контролируемый read-only-контракт для будущего AI Business Analyst.

## 10. Что не входит в текущий этап

- Реальное подключение к API ChatGPT, GitHub, REG.RU или Supabase из реестра.
- Сбор и хранение секретов.
- Автоматический мониторинг серверов, доменов и DNS.
- Изменения схемы или данных Supabase.
- Реализация AI Business Analyst.

Текущий результат — документированная концепция и модель для дальнейшего согласования технических деталей.
