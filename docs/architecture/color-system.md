# Raymondovich — Color System Foundation

**Версия:** 0.1  
**Дата:** 2026-11-06  
**Статус:** архитектурная спецификация; конкретные цветовые значения требуют отдельного визуального согласования.

## 1. Назначение

Color System задаёт единый способ описания и применения цветов во всех четырёх пользовательских пространствах Raymondovich.ru. Система должна обеспечивать узнаваемость бренда, доступность, тематическую согласованность и предсказуемое поведение компонентов.

Color System входит в Design System Core. Она не принадлежит отдельному бизнес-модулю.

## 2. Режимы темы

Поддерживаются три пользовательских режима:

- `light` — принудительная светлая тема.
- `dark` — принудительная тёмная тема.
- `system` — тема определяется настройкой операционной системы через системную цветовую схему.

Правила:
1. Выбор пользователя `light` или `dark` имеет приоритет над системным предпочтением.
2. В режиме `system` приложение отслеживает изменение системной цветовой схемы и обновляет тему без перезагрузки, если это допускает выбранная runtime-архитектура.
3. Значение `system` — пользовательская настройка режима, а не третий независимый набор цветов. Фактически применяется палитра `light` или `dark`.
4. Компоненты не должны определять тему самостоятельно или напрямую читать системную настройку; разрешение темы централизуется на уровне приложения.
5. Переключение темы не должно сбрасывать пользовательский контекст или менять бизнес-данные.

## 3. Архитектура цветовых токенов

Необходимо разделять как минимум три уровня:

### 3.1 Primitive tokens

Базовые значения палитры без привязки к назначению:
- шкала нейтральных оттенков;
- фирменная оранжевая шкала;
- дополнительные палитры, если они будут обоснованы реальными сценариями.

Primitive tokens не используются компонентами напрямую, если для значения существует семантический токен.

### 3.2 Semantic tokens

Токены, описывающие назначение цвета:
- `surface.canvas` — основной фон приложения;
- `surface.primary` — основная поверхность;
- `surface.secondary` — вторичная поверхность;
- `surface.elevated` — приподнятая поверхность;
- `text.primary` — основной текст;
- `text.secondary` — вторичный текст;
- `text.muted` — вспомогательный текст;
- `border.subtle` — ненавязчивая граница;
- `border.strong` — выраженная граница;
- `action.primary` — основное действие;
- `action.primary-hover` — состояние наведения;
- `action.primary-active` — активное состояние;
- `focus.ring` — видимый индикатор клавиатурного фокуса;
- `status.success`, `status.warning`, `status.danger`, `status.info` — семантические статусы.

Для каждой темы semantic tokens получают соответствующие значения. Имена токенов остаются одинаковыми.

### 3.3 Component tokens

Компонентные токены вводятся только там, где компоненту действительно требуется собственная настройка. Они должны ссылаться на semantic tokens, а не создавать параллельную независимую палитру.

## 4. Фирменный оранжевый и градиенты

Оранжевый утверждён как фирменный акцент Raymondovich.

Принципы:
- оранжевая шкала должна содержать значения для разных уровней контраста и интенсивности;
- фирменный акцент не заменяет семантические цвета статусов;
- градиенты строятся из утверждённых цветовых токенов, а не задаются произвольными значениями в компонентах;
- для градиентного текста, фонов и интерактивных элементов отдельно проверяется контраст;
- градиент не должен быть единственным способом передать состояние или смысл.

Конкретные оттенки, HEX/RGB/HSL значения, точки остановки и направления градиентов пока не утверждены.

## 5. Требования к темам

### Light
- светлая базовая поверхность;
- достаточный контраст текста и границ;
- оранжевый акцент сохраняет узнаваемость без чрезмерной визуальной тяжести;
- тени и границы не должны создавать избыточный визуальный шум.

### Dark
- тёмная базовая поверхность;
- текст и интерактивные элементы сохраняют читаемость;
- избегать использования чистого чёрного и чистого белого повсеместно без проверки визуального комфорта;
- оранжевый акцент и градиенты не должны чрезмерно светиться или конкурировать с содержимым.

### System
- использует полный набор semantic tokens выбранной системой темы;
- не содержит собственной отдельной палитры;
- корректно реагирует на изменение системного предпочтения.

## 6. Доступность и проверка

Для всех сочетаний цветов необходимо проверять:
- контраст обычного текста;
- контраст крупного текста;
- контраст значимых графических элементов и границ контролов;
- видимость focus indicator;
- различимость состояний без опоры только на цвет;
- читаемость градиентного текста на фактическом фоне.

Целевые критерии контрастности должны соответствовать WCAG 2.2 AA, если для конкретного элемента не действует более строгое требование.

Проверки выполняются для обеих фактических палитр — Light и Dark. Режим System проверяется через обе ветви системного предпочтения.

## 7. Правила реализации

- Единственный источник значений — Design System Core.
- Компоненты используют semantic tokens.
- Бизнес-модули не объявляют собственные глобальные палитры.
- Тема задаётся централизованно на корневом уровне приложения.
- Выбранный режим темы и фактически разрешённая тема — разные понятия; их нельзя смешивать в одном флаге.
- Конкретный формат хранения токенов и способ подключения CSS custom properties определяются отдельным ADR.
- Не добавлять runtime-код до утверждения CSS-архитектуры и технологического стека.

## 8. Что остаётся открытым

1. Конкретные значения нейтральной и оранжевой шкал.
2. Значения semantic tokens для Light и Dark.
3. Фирменные градиентные наборы и правила их применения.
4. Формат токенов и способ экспорта в CSS.
5. Способ хранения пользовательского выбора темы.

## 9. Критерии готовности

Color System готова к реализации, когда:
- палитры Light и Dark утверждены визуально;
- semantic tokens имеют значения для обеих тем;
- контраст проверен по WCAG 2.2 AA;
- градиенты проверены на читаемость и не дублируют семантику статусов;
- выбран формат токенов и способ подключения через ADR.
