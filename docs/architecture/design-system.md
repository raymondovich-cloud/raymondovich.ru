# Raymondovich.ru — Design System

**Версия:** 1.0  
**Дата:** 2026-11-06  
**Статус:** архитектурная спецификация; реализация интерфейса и подключение к runtime требуют отдельных ADR.

## 1. Назначение

Design System — общая визуальная и компонентная основа Raymondovich.ru. Она обеспечивает единые правила оформления, повторное использование компонентов и предсказуемое поведение интерфейсов всех пользовательских пространств.

Design System состоит из двух связанных, но архитектурно разделённых частей:

1. **Design System Core** — исходная система токенов, foundations, компонентов, паттернов и правил.
2. **Design System Workspace** — закрытый интерфейс внутри Owner Control Center для просмотра, проверки и документирования Core.

Workspace не является отдельным пользовательским пространством и не должен становиться независимой копией дизайн-системы.

## 2. Границы и размещение

### Design System Core

Расположение: `source/design/`

Предлагаемая структура:

```text
source/design/
├── tokens/          # цветовые, типографические, пространственные и прочие токены
├── foundations/     # базовые визуальные правила
├── components/      # переиспользуемые UI-компоненты
├── patterns/        # композиции компонентов и типовые сценарии
├── layouts/         # общие правила построения интерфейсов
└── README.md
```

Core — shared capability платформы. Он не принадлежит Public, Owner, Partner или External пространству и не содержит бизнес-логики этих модулей.

### Design System Workspace

Workspace относится к Owner Control Center и доступен только пользователю с подтверждёнными полномочиями Owner.

Его логическое назначение:

- каталог токенов и foundations;
- каталог компонентов;
- демонстрация вариантов и интерактивных состояний;
- проверка адаптивного поведения;
- документация правил использования;
- контроль согласованности интерфейсов.

Workspace использует те же определения Core, которые применяются приложением. Дублирование токенов или компонентов специально для Workspace запрещено.

## 3. Состав Design System Core

### Tokens
- цвета и семантические цветовые роли;
- типографическая шкала;
- spacing scale;
- размеры и ограничения контейнеров;
- радиусы;
- границы;
- тени и слои;
- motion и timing (канонические CSS custom properties в `source/design/tokens/motion.css`);
- breakpoints.

Токены должны иметь семантические имена. Компоненты не должны без необходимости содержать произвольные значения, если для них уже существует токен.

### Foundations
- цветовая модель и контраст;
- типографика;
- сетка и отступы;
- responsive-поведение;
- доступность и focus;
- правила анимации и reduced motion.

### Components
Базовые независимые элементы интерфейса: кнопки, поля ввода, переключатели, бейджи, карточки, диалоги, уведомления и другие элементы по мере появления реальной потребности.

Каждый компонент описывает назначение, API, варианты, состояния, ограничения и правила доступности.

### Patterns
Повторяемые композиции компонентов: формы, панели фильтрации, списки, пустые состояния, подтверждение опасных действий и другие сценарии.

### Layouts
Общие правила контейнеров, колонок, навигационных областей и адаптивных композиций. Бизнес-специфичные страницы остаются в своих модулях.

Подробные принципы, токены и критерии движения зафиксированы в [Motion System](./motion-system.md). Первый реализованный паттерн — управляемое знакомство с экосистемой через орбитальную композицию: `source/design/patterns/orbital-introduction.css`.

## 4. Технические правила

- Стили хранятся в отдельных CSS-файлах; CSS-in-JS не используется.
- Визуальные значения централизуются в токенах.
- Компоненты не должны зависеть от бизнес-модулей.
- Бизнес-модули могут использовать публичный API Design System, но не импортируют внутренние файлы компонентов друг друга.
- Компоненты не должны напрямую обращаться к Supabase, сети или бизнес-данным.
- Foundations и компоненты должны учитывать клавиатурную навигацию, видимый focus и семантическую разметку.
- Адаптивность проверяется как минимум для узкого мобильного, планшетного и широкого desktop viewport.
- Визуальные изменения должны сопровождаться проверкой состояний: default, hover (где применимо), focus, active, disabled, loading и error (где применимо).
- Конкретный формат токенов, CSS-архитектура, сборка и тестовые инструменты фиксируются ADR до внедрения.

## 5. Принципы Workspace и безопасность

- Workspace размещается в Owner Control Center, а не в публичной навигации.
- Доступ ограничивается ролью и серверными permissions Owner.
- Скрытие пункта меню не является контролем доступа.
- Публичные, партнёрские и внешние пользователи не получают доступ к Workspace.
- На первом этапе Workspace — инструмент просмотра и проверки, а не редактор production-токенов.
- Изменение исходных токенов и компонентов проходит через обычный процесс разработки, review и тестирования.
- Если в будущем появится визуальное редактирование, оно должно создавать контролируемое предложение изменений, а не незаметно менять production-интерфейс.

## 6. Критерии готовности

Design System считается внедрённой в конкретной части платформы, когда:

1. Компонент или токен имеет единственное каноническое определение.
2. Компонент документирован и имеет проверенные состояния.
3. Компонент не содержит бизнес-логики и инфраструктурных зависимостей.
4. Workspace отображает фактическую реализацию Core, а не отдельные макеты-копии.
5. Доступ к Workspace проверяется сервером.
6. Изменения не нарушают визуальную согласованность существующих пространств.

## 7. Этапы реализации

1. Утвердить визуальные foundations и базовые токены.
2. Принять ADR по CSS-структуре и способу подключения Core.
3. Реализовать минимальный набор компонентов.
4. Подключить Core к оболочкам четырёх пространств.
5. Создать закрытый Design System Workspace внутри OCC.
6. Добавить визуальные и accessibility-проверки.
7. Расширять библиотеку по мере появления подтверждённых потребностей.

## 8. Что не входит в текущий этап

Эта спецификация не выбирает UI framework, bundler или тестовый стек; не создаёт runtime-компоненты; не меняет публичный сайт, маршруты, авторизацию или production deployment. Эти решения принимаются отдельно.
