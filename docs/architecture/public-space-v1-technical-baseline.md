# Public Space V1.0 — техническая основа

> **Проект:** Raymondovich.ru  
> **Документ:** Техническая основа первой версии Public Space  
> **Версия:** 1.0  
> **Статус:** Утверждённое техническое решение владельца  
> **Дата:** 2026-11-07  
> **Область действия:** только Public Space V1.0

---

## 1. Назначение

Документ фиксирует минимально необходимую техническую основу первой публичной версии Raymondovich.ru: технологический подход, структуру каталогов и границы реализации.

Public Space V1.0 — адаптивный публичный сайт-обложка с навигацией, презентацией экосистемы и страницами-заглушками. Это не реализация всей платформы Raymondovich.ru.

Документ подчиняется AGENT.md, продуктовой концепции и утверждённой архитектуре взаимодействия модулей. При противоречии агент обязан остановиться и запросить решение владельца.

## 2. Технологический подход

Для Public Space V1.0 утверждается следующий минимальный стек:

- **HTML5** — семантическая структура страниц.
- **CSS3** — вся визуальная система и оформление.
- **Vanilla JavaScript (ES modules)** — только необходимое поведение интерфейса.
- **Без UI-фреймворка** — React, Vue, Angular и аналогичные фреймворки в V1.0 не используются.
- **Без CSS-фреймворка и CSS-in-JS** — Bootstrap, Tailwind и аналогичные решения не подключаются.
- **Без backend и базы данных для публичной оболочки V1.0** — серверные функции, регистрация, личные кабинеты, платежи и интеграции находятся вне текущего scope.

Причина выбора: первая версия имеет ограниченный набор публичных сценариев. Статические HTML-страницы и небольшие ES-модули обеспечивают минимальную сложность, быструю загрузку и простую публикацию. Это решение не утверждает стек будущих закрытых пространств или всей платформы.

### 2.1. Модель страниц

V1.0 реализуется как статический многостраничный сайт. Каждая публичная страница имеет собственный HTML-документ и использует общие ресурсы Design System и общие модули поведения.

Навигация между страницами выполняется обычными ссылками. Клиентский роутер не вводится.

Страницы-заглушки должны явно сообщать, что раздел находится в разработке. Нельзя создавать впечатление, что несуществующая функция уже работает.

## 3. Структура каталогов

Ниже фиксируется структура для реализации Public Space V1.0. Она не является предписанием для будущих серверных модулей или закрытых пользовательских пространств.

```text
/
├── index.html
├── source/
│   ├── design-system/
│   │   ├── tokens/
│   │   ├── foundations/
│   │   ├── themes/
│   │   ├── components/
│   │   └── patterns/
│   └── presentation/
│       └── public/
│           ├── pages/
│           ├── navigation/
│           └── scripts/
├── assets/
│   ├── images/
│   ├── icons/
│   └── fonts/
├── docs/
│   ├── architecture/
│   ├── development.rules/
│   └── product/
└── CNAME
```

### 3.1. Ответственность каталогов

| Путь | Ответственность |
|---|---|
| `index.html` | Точка входа главной публичной страницы |
| `source/design-system/tokens/` | Цветовые, типографические, размерные и другие дизайн-токены |
| `source/design-system/foundations/` | Базовые CSS-правила: reset, базовая типографика, доступность и общие основы |
| `source/design-system/themes/` | CSS-реализация тем, включая светлую и тёмную |
| `source/design-system/components/` | Переиспользуемые визуальные компоненты |
| `source/design-system/patterns/` | Композиции компонентов и повторяемые интерфейсные паттерны |
| `source/presentation/public/pages/` | HTML-документы публичных страниц и заглушек, кроме корневого `index.html` |
| `source/presentation/public/navigation/` | Поведение навигации и мобильного меню |
| `source/presentation/public/scripts/` | Иные небольшие сценарии поведения публичного интерфейса |
| `assets/images/` | Растровые и векторные изображения |
| `assets/icons/` | Иконки, если они не реализованы как CSS-компоненты или inline SVG по отдельному правилу |
| `assets/fonts/` | Локальные файлы шрифтов при наличии лицензии и необходимости |

Каталоги создаются по мере появления реальных файлов. Пустые каталоги и абстрактные заготовки без потребности не добавляются.

### 3.2. Организация CSS

Все CSS-файлы принадлежат исключительно `source/design-system/`. Допускается подключать несколько CSS-файлов из HTML, но хранить или писать CSS в других местах запрещено.

Предлагаемое разделение CSS по ответственности:

- tokens — CSS custom properties и базовые значения;
- foundations — reset и глобальные основы;
- themes — значения и правила тем;
- components — отдельные компоненты;
- patterns — композиции и повторяемые макеты.

Точные имена CSS-файлов определяются при подготовке технической спецификации и не должны дублировать ответственность.

**Запрещено:**
- inline-атрибуты `style`;
- блоки `<style>` в HTML;
- CSS внутри JavaScript;
- CSS-in-JS;
- визуальные значения, разбросанные по HTML/JS вместо Design System.

HTML использует семантические элементы, классы и необходимые атрибуты состояния. JavaScript меняет состояние интерфейса через классы, атрибуты и свойства DOM, но не генерирует CSS.

## 4. Правила JavaScript

JavaScript используется только для поведения, которое нельзя разумно обеспечить обычными HTML-ссылками и CSS.

Для V1.0 допустимы:
- открытие и закрытие мобильной боковой панели;
- переключение активного пункта навигации, если это не определяется самой страницей;
- переключение светлой/тёмной темы;
- сохранение выбранной темы в локальном хранилище браузера;
- доступное управление с клавиатуры и корректное состояние ARIA.

Не допускаются:
- клиентская бизнес-логика будущих закрытых пространств;
- фиктивная авторизация или фиктивное состояние сессии;
- хранение секретов;
- подмена серверной проверки прав клиентскими условиями;
- тяжёлые библиотеки ради простых действий интерфейса.

Сценарии должны деградировать безопасно: без JavaScript страницы остаются читаемыми, а обычная навигация продолжает работать. Если переключатель темы недоступен без JavaScript, базовая тема должна оставаться корректной.

## 5. Design System — единый источник визуального оформления

Design System — единственное место хранения визуальных правил Public Space.

Она определяет:
- цветовые токены и градиенты;
- типографическую шкалу;
- размеры, отступы и сетки;
- радиусы, границы и тени;
- состояния интерактивных элементов;
- компоненты Header, Sidebar, Footer, кнопок, ссылок и элементов навигации;
- паттерны главной страницы и заглушек;
- светлую и тёмную темы;
- адаптивные правила.

Компоненты и страницы не должны вводить собственные несогласованные значения оформления. Если требуется новое визуальное значение, оно сначала добавляется в Design System и затем используется интерфейсом.

## 6. Адаптивность и доступность

Обязательные целевые среды:
- Desktop;
- планшеты;
- iPhone Safari.

Требования:
- отсутствие горизонтальной прокрутки на поддерживаемых ширинах;
- мобильная навигация не перекрывает контент без возможности закрытия;
- интерактивные элементы доступны с клавиатуры;
- видимый фокус;
- корректные семантические заголовки и landmarks;
- достаточная контрастность в обеих темах;
- уважение системной настройки уменьшения анимации;
- корректная работа при увеличении масштаба страницы.

Конкретные контрольные размеры экранов и матрица тестирования фиксируются в тестовой спецификации Public Space.

## 7. Границы V1.0

В Public Space V1.0 входят:
- Header;
- Sidebar;
- центральная презентационная область главной страницы;
- блок «Три формата развития проектов» с утверждёнными текстами;
- блок перехода к сотрудничеству;
- Footer;
- страницы-заглушки для пунктов меню;
- переключение светлой и тёмной темы;
- адаптивная навигация.

В V1.0 не входят:
- полноценная регистрация и авторизация;
- пользовательские кабинеты;
- Owner Control Center;
- Partner Workspace;
- External Project Workspace;
- управление проектами и участниками;
- динамический каталог;
- отправка и обработка заявок на сервере;
- платежи;
- Supabase и иная база данных;
- внешние API-интеграции.

Наличие пункта меню не означает наличие соответствующей функциональности. Заглушки должны быть честными и не имитировать работающие процессы.

## 8. Правила реализации

1. Перед реализацией проверить фактическое состояние репозитория и существующие ресурсы.
2. Не перезаписывать и не удалять существующие файлы без анализа их назначения и согласованного плана.
3. Сначала реализовывать один вертикальный срез: структура → стили Design System → поведение → проверка.
4. Не создавать неиспользуемые библиотеки, абстракции и каталоги.
5. Не подключать несуществующие изображения, шрифты, ссылки и внешние ресурсы.
6. Тексты направлений OWN PROJECTS, PARTNER PROJECTS и EXTERNAL PROJECTS брать из утверждённого источника; не реконструировать по памяти.
7. Все страницы должны использовать общие ресурсы Design System.
8. Проверять работу на Desktop и в iPhone Safari до признания задачи завершённой.
9. Изменения сначала проверяются в изолированной ветке/среде. Публикация в production выполняется только по правилам AGENT.md и с необходимым разрешением владельца.

## 9. Критерии готовности технической основы

Техническая основа считается зафиксированной, если:
- выбран HTML5, CSS3 и Vanilla JavaScript ES modules без UI/CSS-фреймворков;
- зафиксирована статическая многостраничная модель;
- определены границы Design System и Presentation;
- CSS централизован в Design System;
- определены границы V1.0 и исключённые функции;
- будущие закрытые пространства не реализуются преждевременно;
- документ согласован владельцем.
