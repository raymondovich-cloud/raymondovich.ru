# Multi-Platform Architecture

> **Проект:** Raymondovich.ru  
> **Документ:** Архитектура Web, Telegram Mini App и iOS  
> **Версия:** 1.0  
> **Статус:** На утверждении  
> **Дата:** 2026-11-10  
> **Область действия:** общие клиентские платформы и серверные контракты

---

## 1. Цель и исходные ограничения

Цель — сохранить один продукт и единый источник бизнес-правил, постепенно добавляя клиенты Web, Telegram Mini App и iOS без переписывания предметной логики и без нарушения действующего Web.

Фактическая база на дату редакции:
- единственная точка входа — корневой `index.html`;
- SPA на Vanilla JS ES modules с hash-маршрутами;
- стили находятся в `source/design-system/`;
- статические файлы публикуются через GitHub Pages, в корне есть `CNAME` со значением `raymondovich.ru`;
- используется Supabase Auth, Postgres/RLS и Edge Function `pin-auth`;
- Supabase JS загружается с esm.sh по диапазону `@2`, а URL и publishable key находятся в текущем клиентском модуле;
- текущий auth redirect — `https://raymondovich.ru/#authorization`;
- PIN уже реализован через серверную функцию и заявлен как общий для платформ.

Это документ проектирования, а не разрешение немедленно менять публичные контракты, авторизацию, инфраструктуру или код. Этап 1 и далее требуют отдельного явного утверждения владельца.

## 2. Стратегия внедрения и триггеры

### Этап A — Web как основной клиент

Продолжать разработку основной версии на текущем стеке. Существующие маршруты, Auth, PIN, RLS, Ideas, Projects и Design System остаются источником совместимости.

**Триггер перехода:** основные сценарии Web завершены и проверены; есть стабильная структура модулей и серверных контрактов. Не начинать платформенные адаптеры вместо завершения основного сайта.

### Этап B — PWA без обязательных платных сервисов

Добавить manifest, иконки, метаданные установки и инструкцию добавления на экран «Домой». На iOS установка выполняется пользователем через Safari → Share → Add to Home Screen; поддержка установки не требует App Store.

Service Worker не является обязательным условием самой установки PWA. Его внедрение отложено до отдельного ADR: до него не кэшировать ничего и не регистрировать SW.

**Триггер:** Web стабилен на мобильном Safari, есть согласованные иконки и проверен standalone-режим.

### Этап C — Telegram Mini App

Создать бота через официальный BotFather, привязать Web App URL и настроить кнопки/меню. Telegram Mini App остаётся клиентом существующего сайта, а не отдельной копией бизнес-логики.

Понадобятся: ранняя нормализация launch-параметров hash, платформенный bridge, динамическая загрузка официального Telegram WebApp SDK только в Telegram, серверная проверка initData и безопасная процедура привязки аккаунта.

**Триггер:** Web/PWA совместимы с платформенным слоем; подтверждены Telegram bot ownership, домен и серверный auth flow. Создание бота и настройка URL — отдельная операционная задача владельца.

### Этап D — iOS

Сначала использовать PWA как проверку спроса и качества мобильного сценария. Нативное приложение рассматривать после появления бюджета и подтверждённой потребности в функциях, которые PWA не обеспечивает достаточно хорошо.

| Вариант | Преимущества | Ограничения и стоимость |
|---|---|---|
| 1. PWA | Нет отдельного приложения и программы Apple Developer; один Web-код; установка с экрана «Домой» | Ограничения браузерных API и фоновой работы; не распространяется через App Store как обычное приложение |
| 2. Оболочка с локальным bundle (например, Capacitor) | В приложение упакован web bundle; доступ к нативным API через плагины; меньше зависимости от доступности сайта при запуске | Нужны сборка, подпись, обновление bundle и тестирование плагинов; требуется нативная ценность, иначе риск отказа по Guideline 4.2 |
| 3. Оболочка с удалённым URL | Быстрый старт и единый web deployment | Зависимость от сети и сайта; слабая нативная ценность; высокий риск выглядеть как repackaged website по Guideline 4.2; удалённый код/контент требует соответствия правилам Apple |
| 4. Полностью нативное Swift-приложение | Лучший доступ к iOS API, нативная производительность и UX | Самая высокая стоимость; второй клиентский интерфейс и поддержка; нужна строгая синхронизация контрактов |

**Рекомендация по умолчанию:** вариант 2 — оболочка с локальным bundle, только когда появится бюджет и появится достаточная нативная функциональность. Это не окончательное утверждение технологии/библиотеки.

Для распространения через App Store и TestFlight требуется членство Apple Developer Program. Официальная страница Apple указывает годовую плату 99 USD (или локальную цену, если доступна). Бесплатный Apple Account позволяет пользоваться Xcode и устанавливать приложения на собственные устройства с ограничениями; он не даёт распространение через App Store или TestFlight. Актуальные условия и доступность регистрации в регионе необходимо повторно проверить непосредственно перед началом iOS-этапа.

Guideline 4.2 требует, чтобы приложение предлагало функции, контент и UI, выходящие за рамки переупакованного сайта. Одна WebView-оболочка без устойчивой полезности и нативной ценности — риск отказа. До iOS-этапа определить минимум нативных возможностей (например, системная навигация, безопасное хранение токена, share sheet, haptics, уведомления — только если они реально нужны продукту).

Подготовка к варианту 2 заранее:
- не связывать предметную логику с DOM, browser history и конкретным SDK;
- изолировать навигацию и внешние действия за платформенным bridge;
- относительные и абсолютные пути инвентаризировать; будущий bundle должен обслуживаться из корня WebView либо пути должны быть согласованно адаптированы;
- выделить конфигурацию публичных URL/ключей без переноса секретов в bundle;
- определить auth callback для native и отдельный безопасный storage adapter;
- учитывать safe-area, клавиатуру, lifecycle и возврат из background;
- подготовить build script без зависимостей только после отдельного согласования;
- не создавать iOS adapter, пока не выбран вариант оболочки.

## 3. Единый контракт и принцип «логика на сервере»

Клиентский JS отвечает за отображение, локальное состояние представления и оркестрацию сценариев. Он не является доверенной границей безопасности.

Новые бизнес-операции, влияющие на данные, права, роли, финансы, проекты, PIN или партнёрские отношения, должны предоставляться серверными контрактами — Postgres RPC или Supabase Edge Functions — с проверками RLS и полномочий. Исключение возможно только для явно read-only запросов, которые уже разрешены политиками и соответствуют утверждённым границам модулей.

Любой клиент (Web, Telegram, iOS, будущий Swift) вызывает один и тот же контракт. Не дублировать бизнес-правила в разных UI-клиентах. Внутренние таблицы не становятся публичным API только потому, что клиент умеет обращаться к PostgREST.

Существующие RLS, RPC `convert_idea_to_project` и Edge Function `pin-auth` — правильная основа, но это не подтверждает, что все текущие операции уже вынесены на сервер. Обнаруженный прямой Supabase-доступ в presentation-коде требует отдельного аудита и постепенного переноса только после утверждения.

## 4. Telegram Mini App: запуск и аутентификация

### 4.1. Launch-параметры и SDK

Telegram может передавать launch-параметры в hash. Текущий `routeFromLocation() = location.hash` воспринимает весь hash как маршрут. Это критический риск: например, `#tgWebAppData=...` станет неизвестным маршрутом.

До подключения роутера нужен ранний bootstrap, который только на Telegram-платформе:
1. обнаруживает launch-параметры в hash/query;
2. сохраняет исходные значения в памяти или sessionStorage для последующей передачи SDK;
3. удаляет Telegram-параметры из адресной строки через `history.replaceState`;
4. сохраняет существующий app-route либо преобразует `tgWebAppStartParam` только по явной allowlist-таблице;
5. неизвестный startParam игнорирует, не превращая в произвольный маршрут.

Пример разрешённого сопоставления: `projects → #authorization/projects`. Таблица маршрутов должна утверждаться вместе с реальными deep-link сценариями. Поддельный hash-тест — только проверка устойчивости роутера, не доказательство подлинности Telegram launch data.

Официальная документация Telegram предписывает загружать `https://telegram.org/js/telegram-web-app.js` и проверять `Telegram.WebApp.initData` на сервере. SDK должен подключаться динамически и только при подтверждённой платформе Telegram; в обычном Web не должно быть дополнительного запроса к telegram.org. Зависимость от внешнего скрипта оценивается по AGENT.md §16: назначение, официальный источник, стабильность/совместимость, безопасность, данные, способ отключения и поведение при недоступности. Версию SDK/параметр URL документировать; не загружать сторонние зеркала.

### 4.2. Проверка initData на сервере

Браузер передаёт исходную строку `initData` серверной Supabase Edge Function. Сервер:
- проверяет подпись по официальному алгоритму Telegram с использованием bot token, хранящегося только в server-side secrets;
- проверяет обязательные поля и формат;
- проверяет `auth_date` по утверждённому короткому окну свежести;
- применяет защиту от повторного использования там, где операция требует одноразовости;
- не принимает `initDataUnsafe` или поля из клиентского JSON как доказательство личности;
- не выдаёт роль admin на основании Telegram ID, username, имени, группы, канала или startParam.

Bot token, service_role и другие секреты запрещено помещать в репозиторий, HTML, JS bundle, URL или клиентские логи.

### 4.3. Привязка Telegram к существующему Supabase user

Предлагаемый сценарий: уже авторизованный пользователь Web инициирует привязку. Сервер создаёт одноразовый случайный код/ссылку с ограниченным сроком действия и связывает её с текущим Supabase user из проверенной сессии. Пользователь открывает Mini App по этой ссылке; сервер проверяет Telegram initData, атомарно потребляет одноразовый код и связывает Telegram identity с ранее подтверждённым user ID. Повторное использование, истечение срока, привязка к другому пользователю и конкурентное потребление должны завершаться отказом.

Нельзя принимать user ID из тела запроса как источник истины. Нельзя позволять Telegram-данным назначать роли. При конфликте привязки требуется ручной процесс восстановления через подтверждённую веб-учётную запись.

### 4.4. Выдача сессии: варианты и ограничения

| Вариант | Плюсы | Риски/ограничения |
|---|---|---|
| A. Telegram identity только связывается с аккаунтом; пользователь входит существующим способом Supabase | Минимальная поверхность риска; не требуется выпускать новую сессию | Менее плавный UX; повторный вход может требовать email/пароль |
| B. Одноразовый server-side exchange в Supabase Auth session | Лучший UX, единый Supabase user/session | Нужен поддерживаемый Supabase Auth flow, проверенный на staging; нельзя самостоятельно подписывать JWT в Edge Function или отдавать секретный ключ клиенту |
| C. Собственная Telegram-сессия поверх Supabase | Независимость от Auth flow | Два источника сессий, сложная ротация, отзыв, RLS integration и аудит; не рекомендовано |

**Предлагаемая позиция:** сначала A как безопасный fallback. B исследовать отдельно и принимать только после прототипа на изолированном staging и проверки официального поддерживаемого механизма. Не использовать service_role как клиентскую сессию. Не считать Telegram identity автоматически авторизованной в Supabase.

## 5. Сессии, хранилища и PIN

| Платформа | Сессия | Настройки/предпочтения | Ограничения |
|---|---|---|---|
| Web | Текущий Supabase Auth storage (localStorage по умолчанию), без смены ключа/формата в рамках платформенного этапа | localStorage; временное состояние — sessionStorage | Сохранить действующие ключи и сессии. XSS остаётся риском для токенов в JS-доступном storage |
| PWA | Тот же origin и тот же Supabase Auth storage, что у Web | localStorage | Не создавать отдельное хранилище только из-за standalone; проверить реальное поведение Safari |
| Telegram | Supabase session в webview storage после безопасного входа; CloudStorage — только для несекретных предпочтений | Telegram CloudStorage или локальное хранилище | CloudStorage привязан к боту, не заменяет Auth и не должен хранить access/refresh tokens или PIN; доступность API зависит от версии клиента |
| iOS local bundle | После выбора оболочки — отдельный storage adapter Supabase; предпочтительно Keychain-backed secure storage для токенов | Capacitor Preferences/локальные настройки только для несекретных значений | Preferences не следует считать защищённым хранилищем секретов; плагин и его лицензия/безопасность требуют отдельной оценки |

PIN остаётся серверно проверяемым общим механизмом. PIN-код никогда не хранить в localStorage, CloudStorage, Preferences, URL, history.state или логах. Клиентское состояние «разблокировано» — только UX-флаг и не заменяет серверную авторизацию. Для каждой платформы проверить очистку/изоляцию хранилища, выход из аккаунта, повторный вход и блокировку после background. Не менять существующие ключи PIN storage или семантику без отдельного согласования.

| Push | Не включать сейчас | Web Push для установленной Home Screen web app на iOS 16.4+; требует SW и серверной отправки | Bot API может отправлять сообщения пользователю после разрешения/инициации диалога; применяются ограничения Telegram | APNs/native push — отложено; платные/операционные требования оценить отдельно |

Для Telegram Bot API нет отдельной платы за само использование API, но действуют лимиты Telegram и стоимость/квоты серверного исполнения. Web Push не «бесплатен автоматически»: стандарт не требует платного push-провайдера, однако нужны service worker, подписки, VAPID и серверная отправка. На этом этапе push не реализуется. Native push/APNs, дополнительные плагины и инфраструктура — отложено до подтверждённой потребности и бюджета.

## 7. Бесплатные тарифы и бюджетные ограничения

### Supabase Free — данные официальной документации на 2026-11-10

- Free plan включает до двух активных проектов в организации; неактивные проекты могут автоматически приостанавливаться.
- Free project может быть приостановлен при недостаточной активности в течение семи дней; критерий зависит от активности БД. Данные и настройки сохраняются, восстановление выполняется через Dashboard.
- Текущие опубликованные квоты: 500 MB database на проект, 50,000 MAU, 1 GB Storage, 5 GB uncached egress + 5 GB cached egress, 500,000 Edge Function invocations. Перепроверять перед планированием нагрузки: тарифы меняются.
- Edge Functions: Free wall-clock duration 150 секунд, CPU time 2 секунды на запрос; число функций — до 100 на проект согласно опубликованной таблице лимитов.
- Встроенный Supabase Auth SMTP — только для тестов: письма только на адреса участников команды проекта, лимит 2 письма в час, без SLA. Для регистрации внешних пользователей и надёжного восстановления пароля потребуется отдельный SMTP-провайдер; если он платный, включать только после появления бюджета и отдельного согласования.
- Free plan не предоставляет downloadable database backups по production checklist. Нужен отдельный план экспорта/резервного копирования; не считать бесплатный тариф полноценной backup-стратегией.

**Условия перехода на платный план:** проект становится критичным для реальных пользователей и недопустима автоматическая пауза; фактическое потребление приближается к квотам; нужны надёжные резервные копии/SLA/поддержка; нужен SMTP с доставкой на произвольные адреса; функции/трафик/хранилище превышают бесплатные квоты. До появления средств — сокращать нагрузку и функциональность, не включать платные услуги по умолчанию.

### GitHub Pages / Apple / Telegram

- Текущая статика размещена на GitHub Pages. Платные лимиты/особенности плана и ограничения private repository для конкретного аккаунта здесь не подтверждены — требуют проверки по официальной документации перед масштабированием. Не менять способ публикации в рамках этого документа.
- App Store и TestFlight требуют Apple Developer Program membership; официальная публичная цена — 99 USD/год, локальные условия проверять перед регистрацией.
- BotFather и Telegram Mini Apps не требуют платной подписки за создание бота; Telegram API limits и доступность функций зависят от версии клиента и актуальной документации.

| ID | Риск / вопрос | Последствие | Предлагаемая мера / решение |

### Решения, требующие владельца

1. Утвердить стратегию этапов Web → PWA → Telegram Mini App → iOS и рекомендацию iOS local bundle как целевой вариант по умолчанию.
2. Утвердить принцип новых бизнес-операций через RPC/Edge Functions под RLS как общий межплатформенный контракт.
3. Утвердить Telegram auth design: server-side initData validation, привязка только через авторизованную Web-сессию и отсутствие admin-role от Telegram; на первом этапе использовать безопасный fallback A, а session exchange B исследовать отдельно.
4. Утвердить платформенный bridge и раннюю нормализацию Telegram launch hash как границу Этапа 1.
5. Утвердить модель хранения: Supabase Auth storage на Web/PWA, CloudStorage только для несекретных Telegram preferences, Keychain для iOS токенов при выборе оболочки.
6. Утвердить матрицу платформенных возможностей и отложенные push/native plugins.
7. Подтвердить, что текущий Supabase free project допускает паузы и отсутствие production SMTP приемлемо на текущем этапе.
8. Принять решение по противоречиям technical baseline: обновить его до 1.3, ограничив правило «без backend/Supabase» только исходным scope Public Space V1.0 и заменив критерий «статическая многостраничная модель» на «SPA с единственным index.html и hash-маршрутами». Не исправлять документ без утверждения.

## 9. Противоречия документации и фактической реализации

В `public-space-v1-technical-baseline.md` v1.2 §2 одновременно:
- утверждается «без backend и базы данных» для публичной оболочки V1.0;
- §2.1 описывает SPA с единым `index.html` и hash-маршрутами;
- §9 всё ещё требует «статическую многостраничную модель».

Фактический репозиторий уже содержит Supabase Auth, Postgres/RLS-зависимые сценарии, Edge Function `pin-auth`, закрытые экраны Ideas/Projects и SPA-роутер. Это не следует исправлять молча: baseline был ограничен Public Space V1.0, но его текущая формулировка и фактическое расширение scope расходятся.

**Предложение для владельца:** выпустить baseline v1.3, где:
- чётко отделить публичную статическую презентационную часть от уже существующих закрытых пространств и Supabase-инфраструктуры;
- зафиксировать SPA/hash routing как единственную модель клиентской оболочки;
- уточнить, что «без backend» было исходным ограничением Public Space V1.0, а не утверждением об отсутствии backend во всём репозитории;
- обновить критерий готовности §9 и историю версий.
До утверждения v1.2 остаётся неизменённым.
