# Безопасность административного блока Raymondovich

**Дата:** 09.10.2026  
**Статус:** Базовые требования и результаты первичного аудита. Это не сертификат безопасности и не замена полноценному тестированию.

## 1. Цель и модель угроз

Административный блок — приватная панель управления экосистемой. Административный доступ должен принадлежать только владельцу. Утечка URL или открытие HTML-файла не должны предоставлять доступ к данным или операциям.

Защищаем: проектные сведения, внутренние стратегии и идеи, карту инфраструктуры, метаданные сервисов, будущие интеграционные настройки и любые персональные данные.

Основные угрозы: неавторизованный аккаунт; подделка роли на клиенте; прямые запросы к Supabase API в обход интерфейса; межпользовательский доступ через ошибочную RLS-политику; утечка секретов из репозитория/логов; XSS и небезопасный рендеринг; компрометация сессии; ошибочная конфигурация внешнего сервиса.

## 2. Обязательные правила

1. Доступ по принципу deny-by-default: без валидной сессии нет доступа; без серверно назначенной роли `app_metadata.role = admin` нет административного доступа.
2. Проверка роли только в интерфейсе недостаточна. Все операции с данными защищаются RLS и, когда требуется, серверной функцией с проверкой JWT и роли.
3. Пользовательские метаданные (`user_metadata`) не являются источником привилегий. Роль берётся только из `app_metadata`, назначаемой доверенным административным контуром.
4. Нельзя помещать пароли, service-role ключи, приватные API-ключи, refresh-токены, recovery-коды и секреты интеграций в HTML, JavaScript клиентского приложения, Git, таблицы реестра, URL или журналы.
5. Публичный Supabase publishable key допустим только при строгих RLS и минимальных grants. Он не является секретом, но и не заменяет авторизацию.
6. Секреты интеграций при появлении хранятся в серверном secret store / Edge Function secrets. В БД реестра хранятся только ссылка на секрет (идентификатор/имя), владелец, назначение и статус — не само значение.
7. Все новые таблицы: RLS включён в той же миграции; явные политики для каждой операции; минимальные права ролей; индексы для полей политик и внешних ключей.
8. Все связи между проектами, инструментами и ресурсами проверяются на принадлежность текущему владельцу; клиент не может назначить себе owner_id или роль.
9. Опасные операции журналируются без содержимого секретов. Ошибки для пользователя не должны раскрывать SQL, JWT, внутренние конфигурации или stack trace.
10. Изменения безопасности — через версионируемые миграции, с проверкой результата после применения.

## 3. Шифрование и секреты

- Использовать HTTPS/TLS для передачи данных.
- Полагаться на шифрование хранилища/баз данных на стороне провайдера для данных в покое и отдельно проверять настройки резервного копирования и хранения.
- Не создавать собственную криптографию и не хранить ключ шифрования рядом с зашифрованным значением.
- Если в будущем возникнет обоснованная необходимость хранить секреты, предпочесть внешнее хранилище секретов. Шифрование полей БД имеет смысл только при чёткой модели управления ключами, ротации, резервного восстановления и серверного расшифрования.
- Пароли пользователей обрабатывает Supabase Auth; приложение не хранит их самостоятельно.
- Для администратора рекомендуется включить MFA (предпочтительно authenticator/passkey, если поддерживается текущей конфигурацией), проверить восстановление доступа и хранить recovery-коды вне репозитория.

## 4. Первичный аудит 09.10.2026

### Подтверждено

- Supabase project `yajybgdorhxebbigwjgi` (`raymondovich`) активен.
- В `public` обнаружены `user_profiles`, `projects`, `project_milestones`, `project_tasks`, `project_history`; RLS включён на всех пяти таблицах.
- Политики таблиц проектов проверяют роль из JWT `app_metadata` и владельца через `auth.uid()`; политики этапов и задач проверяют владение связанным проектом.
- Клиентский код использует publishable key, а не service-role key.
- В `source/application/auth/authentication.js` роль читается из `session.user.app_metadata.role`; регистрация не присваивает административную роль.
- В `app.html` и `source/presentation/app/app-page.js` есть различие ADMIN/USER. Серверная защита данных обеспечивается RLS, а не этим визуальным различием.

### Найденные вопросы и риски

- Supabase Security Advisor сообщает, что защита от скомпрометированных паролей отключена. Требуется включить настройку в Supabase Auth.
- В Auth обнаружены две учётные записи: одна с ролью admin и подтверждённой почтой, вторая без роли и с неподтверждённой почтой. Это подтверждает, что регистрация не закрыта полностью. Роль второй записи не admin; однако необходимо принять решение, должна ли регистрация оставаться включённой для будущих пользовательских продуктов или должна быть выключена на период разработки.
- На момент первичного аудита у роли `anon` обнаружены избыточные grants на `user_profiles`. В этой сессии они отозваны миграцией; authenticated оставлен доступ только SELECT/INSERT/UPDATE для существующего профиля.
- Security Advisor не сообщил дополнительных security lint findings в полученном ответе, но это не доказывает отсутствие уязвимостей.
- Есть performance-предупреждения о повторном вычислении auth-функций в RLS-политиках. Это оптимизация, а не самостоятельное доказательство обхода доступа.
- Полный аудит всех страниц, XSS, заголовков безопасности, конфигурации Auth, MFA, восстановления доступа, резервных копий и внешних интеграций ещё не завершён.

## 5. План усиления

1. Проверить все административные маршруты и общую точку авторизации; неизвестная роль должна получать отказ, а не пользовательский доступ к админ-функциям.
2. Проверить RLS, grants, функции `SECURITY DEFINER`, права на схемы и все будущие таблицы.
3. Включить защиту от скомпрометированных паролей и настроить разумные ограничения Auth/частоты запросов.
4. Включить MFA для администратора и проверить сценарии восстановления.
5. Применить least privilege к `anon`, `authenticated` и серверным ролям без нарушения действующей авторизации.
6. Проверить все динамические вставки HTML; предпочитать `textContent` и безопасные DOM API.
7. Добавить CSP и другие подходящие HTTP security headers на уровне хостинга после проверки совместимости модулей и CDN.
8. После каждой миграции выполнить проверки доступа как admin, authenticated user без admin-роли и anon; проверить чтение, вставку, изменение, удаление и межвладельческие связи.
9. Для будущего AI Business Analyst создать read-only application-контракт с минимальным набором данных; не передавать секреты и не давать прямой доступ к базе.
10. Поддерживать журнал проверок и план реагирования на компрометацию: отзыв сессий/ключей, ротация секретов, проверка логов и восстановление.

## 6. Что не считается защитой

- Скрытая ссылка на страницу.
- Проверка роли только в JavaScript.
- Публичный ключ Supabase как единственная защита.
- Обфускация или минификация кода.
- Хранение зашифрованного секрета рядом с ключом расшифровки.
- Запись связи в реестре как доказательство того, что внешняя интеграция действительно работает.

## 7. Критерий готовности

Безопасность административного блока принимается только после проверок на уровне Auth, RLS/grants, серверных операций, пользовательского интерфейса и конфигурации хостинга. До этого разделы считаются находящимися в разработке, даже если интерфейс визуально доступен только администратору.
