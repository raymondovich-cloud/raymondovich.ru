## Hash-навигация рабочего пространства
- Рабочее пространство остаётся одним SPA с единой HTML-оболочкой `app.html`; отдельные HTML-страницы для разделов не создаются.
- Добавлены адресуемые hash-маршруты: `app.html#projects`, `#ideas`, `#team`, `#tools`, `#profile` и `#profile/settings`.
- При прямом открытии ссылки отображается соответствующий раздел; навигация обновляет hash без полной перезагрузки документа.
- Поддерживаются история браузера, кнопки «Назад/Вперёд» и восстановление активного раздела через `hashchange`.
- Заголовок вкладки синхронизируется с текущим разделом.


## Domain-модули рабочего пространства
- Подтверждено разделение ответственности: единая SPA-оболочка и hash-маршрутизация не объединяют доменную логику разделов.
- Каждый раздел рабочего пространства связан со своим модулем в `source/domain/`: `projects`, `ideas`, `team`, `tools`, `profile`.
- Создан каталог `source/domain/team/` как доменный модуль раздела «Команда».
- Интерфейс и навигация остаются в presentation; сценарии использования и координация — в application; интеграции и хранение — в infrastructure. Domain отвечает за предметные сущности и бизнес-правила.
- Перенос корневой точки входа SPA и связывание разделов с их модулями — отдельный следующий этап; одной только сменой URL доменная архитектура не считается реализованной.


## Корневая точка входа рабочего пространства
- Корневой `index.html` теперь содержит публичную главную и единый shell рабочего пространства; режим выбирается по допустимому hash-маршруту.
- Поддерживаются `/#projects`, `/#ideas`, `/#team`, `/#tools`, `/#profile` и `/#profile/settings`; каждый маршрут остаётся внутри одной SPA-оболочки.
- Workspace-модуль загружается динамически только при входе на допустимый маршрут. Публичная главная остаётся режимом по адресу `/` без hash.
- Авторизация сохраняет запрошенный маршрут в sessionStorage и возвращает пользователя в него после входа или подтверждения Email; fallback — `/#projects`.
- `app.html` сохранён как legacy-адрес и перенаправляет на `/#projects`.
- Важно: каталоги `source/domain/projects`, `ideas`, `profile`, `tools` и `team` на момент проверки содержат только `.gitkeep`. Поэтому маршруты уже адресуют соответствующие разделы оболочки, но доменная бизнес-логика ещё не реализована и не может считаться подключённой. Её интеграция требует отдельных доменных контрактов и use cases, а не фиктивных импортов пустых каталогов.
- Визуальная система не менялась. Реальную проверку в iOS Safari не заявляем до пользовательского теста.


## Контракты Domain и маршрутизация через Application
- Добавлен общий контракт `source/contracts/workspace-section.js`: проверяет идентификатор домена, базовый маршрут, список маршрутов и отсутствие дубликатов.
- Каждый раздел объявляет владение своими маршрутами в собственном Domain-модуле: `projects/workspace-section.js`, `ideas/workspace-section.js`, `team/workspace-section.js`, `tools/workspace-section.js`, `profile/workspace-section.js`.
- Создан Application use case `source/application/workspace/resolve-workspace-route.js`: собирает определения доменов, проверяет уникальность маршрутов и возвращает владельца маршрута и подмаршрут.
- Root router и Workspace Presentation используют один Application resolver; перечень маршрутов больше не дублируется в двух presentation-модулях.
- Presentation сохраняет ответственность за названия, отображение, навигационные кнопки и визуальное поведение. Domain не импортирует Presentation, Supabase или браузерные API.
- Это пока контракт владения разделами и маршрутизацией, а не полный набор бизнес-сценариев Projects/Ideas/Team/Tools/Profile. Для реализации CRUD, участников, прав, подключений сервисов и настроек нужны отдельные предметные требования и use cases; фиктивные бизнес-правила не добавлялись.


## Единая HTML-точка входа

- Корень репозитория очищен: единственные HTML-файлы верхнего уровня больше не создаются; в корне остаются `index.html` и `CNAME` (служебные каталоги и файлы конфигурации сохраняются).
- Авторизация, регистрация, подтверждение Email и восстановление пароля перенесены в единый SPA shell в `index.html`.
- Сценарии авторизации маршрутизируются через query-параметр `auth`: `/?auth=login`, `/?auth=register`, `/?auth=callback`, `/?auth=recovery`. Это сохраняет совместимость с Supabase redirect flow, в котором могут присутствовать query-параметры PKCE или hash-токены.
- После успешного входа и обновления пароля пользователь направляется в `/#projects`; защищённые workspace routes при отсутствии сессии направляют на `/?auth=login`.
- Удалены legacy entry pages `app.html`, `auth.html`, `auth-callback.html`, `update-password.html`.
- Старый HTML UI-прототип перемещён из корня в `docs/archive/prototypes/`; он не подключается к приложению.
- Supabase Auth Dashboard Redirect URLs и фактические email-ссылки требуют отдельной проверки вручную. End-to-end проверка регистрации, подтверждения Email и восстановления пароля не заявляется как выполненная.


# 2026-11-13 — Profile settings

## Настройки профиля
- В разделе «Профиль → Настройки» добавлены iOS-style переключатель тёмной/светлой темы и блок пользовательских данных.
- ФИО и дата рождения редактируются отдельными формами через Edge Function `profile-update`; сервер проверяет JWT и изменяет только запись текущего пользователя через закрытые RPC-функции. RPC доступны только роли `service_role`.
- Логин показывается как неизменяемое поле.
- Для смены пароля и Email пользователь повторно подтверждает текущий пароль; сами изменения выполняются через Supabase Auth. Новый Email требует подтверждения по письму.
- Не добавлялись новые поля БД, таблицы, роли или прямые права клиенту на схему `private`.

## Проверки и ограничения
- Edge Function `profile-update` развернута с обязательной JWT-проверкой.
- Требуется end-to-end тестирование в браузере: загрузка профиля, обновление ФИО/даты, смена пароля, подтверждение нового Email. Отправка реального письма и фактическое изменение Email не считаются проверенными до такого теста.
- Визуальная проверка на реальном iPhone/Safari не выполнялась.

- Profile feature logic separated by layers: domain validation in `source/domain/profile/profile-data.js`, application use cases in `source/application/profile/profile-settings.js`, and Supabase/Auth operations in `source/infrastructure/supabase/profile-settings-gateway.js`. Presentation composes the gateway with the use cases.


## Исправление переключателя темы и диагностика загрузки профиля
- Исправлена геометрия переключателя: трек теперь является блочным позиционируемым элементом, бегунок центрируется по вертикали и перемещается в пределах корпуса, как у системного iOS switch.
- По журналам Supabase установлено, что запрос GET к Edge Function `profile-update` проходит аутентификацию, но RPC `profile_settings_get` не находит запись в `private.user_profiles`. Для текущей учётной записи запись отсутствует; поэтому функция возвращает 500.
- Триггер создания приватного профиля уже существует, но он выполняется только при создании новой Auth-учётной записи. Текущая учётная запись создана до появления/активации этого механизма, а доступные Auth metadata не содержат полного набора полей профиля. Автоматически придумывать логин или дату рождения нельзя.
- Для полного восстановления профиля требуется безопасный сценарий первичного заполнения отсутствующих данных; существующие роли, Auth и Intake не менялись.


## Упрощение настройки оформления
- В строке настройки темы оставлена только одна подпись и переключатель.
- В тёмном режиме подпись — «Тёмная тема»; после переключения на светлый режим она меняется на «Светлая тема».
- Удалено дополнительное пояснение под названием настройки. Логика сохранения темы и ключ localStorage не менялись.


## Возврат переключателя к утверждённому компоненту Design System

- Используется утверждённый компонент `.ds-switch` из `source/design-system/components/components.css`, соответствующий Showcase 0.4.
- Удалены локальные переопределения `.ds-switch` из workspace-паттерна, чтобы внешний вид полностью задавался общим компонентом.
- Состояние переключателя синхронизируется через `aria-checked`; подпись строки переключается между «Тёмная тема» и «Светлая тема».
- Геометрия и визуальные параметры общего компонента не изменялись.


## Верхний блок профиля
- В разделе «Профиль» добавлена карточка пользователя: круглый аватар с инициалами из ФИО, имя и фамилия, логин и бейдж глобальной роли.
- Роль читается только из доверенного `app_metadata.role` Supabase Auth: `admin` отображается как «Администратор», `user` — как «Пользователь». Неизвестное или отсутствующее значение не интерпретируется как обычная роль и отображается нейтрально.
- Данные ФИО и логина загружаются через существующий профильный use case. Схема БД, Auth, RLS и Design System Baseline 1.0 не менялись.
- Добавлены только правила компоновки карточки; аватар использует утверждённые Design System tokens, бейдж — общий компонент `.ds-badge`.

Возврат использует историю переходов внутри рабочего пространства с fallback на родительский маршрут. Удалена локальная кнопка возврата из экрана настроек профиля.

## Исправление возврата из настроек профиля
- Для вложенного маршрута `profile/settings` верхняя стрелка теперь всегда возвращает непосредственно в корневой раздел `profile`, не полагаясь на внутренний стек переходов.
- Стек истории очищается после возврата; сброс флага подавления истории гарантирован через `finally`.
- Остальные вложенные маршруты сохраняют общий механизм возврата к предыдущему маршруту с fallback на родительский.
- Дополнительно изменён механизм возврата именно из `profile/settings`: переход на `#profile` выполняется через `window.location.hash`, чтобы событие `hashchange` одновременно обработало маршрут в workspace и корневом router. Это устраняет зависимость от ручного вызова `renderRoute()` при `history.replaceState()`.
