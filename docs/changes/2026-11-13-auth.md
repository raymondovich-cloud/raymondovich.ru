# 2026-11-13 — Authentication foundation

## Спецификация
- Регистрация: ФИО, дата рождения, уникальный логин, Email, пароль.
- Вход: Email + пароль или логин + пароль.
- После создания учётной записи сервер назначает роль USER; клиент не передаёт и не меняет роль.
- Подтверждение Email, восстановление пароля, смена пароля, завершение сессии.
- Magic Link и сторонние OAuth-провайдеры не добавлялись.

## Реализация
- Добавлена приватная таблица профилей в схеме private; доступ через Data API для anon/authenticated закрыт, RLS включён.
- Добавлен триггер назначения USER для новых регистраций. Существующие роли не изменялись.
- Профильные поля копируются из signup metadata в private.user_profiles; raw_user_meta_data очищается после создания профиля.
- Добавлена Edge Function username-sign-in: логин разрешается в Email на сервере через RPC, доступную только service_role, затем используется стандартная проверка пароля Supabase Auth. Email не возвращается клиенту.
- Добавлена серверная блокировка регистрации через private.auth_settings.registration_enabled; она защищает не только UI, но и прямые вызовы Supabase Auth API.
- Для разработки владелец разрешил временно включить регистрацию: private.auth_settings.registration_enabled = true. Это тестовый режим, а не публичный запуск.
- В auth.html включена кнопка переключения на регистрацию; форма регистрации доступна для тестирования с несколькими аккаунтами.
- Добавлены страницы входа/регистрации, callback подтверждения Email, восстановления пароля и минимальной защищённой страницы аккаунта.
- Frontend использует PKCE и публичный publishable key; секретный ключ не добавляется в репозиторий.
- UI использует утверждённую Design System Baseline 1.0.

## Ограничения перед публичным запуском
- Текущий Supabase project расположен в eu-central-1 (Франкфурт). В тестовом режиме использовать только тестовые данные и отдельные тестовые Email; не регистрировать реальные персональные данные третьих лиц.
- Перед публичным запуском перенести хранение персональных данных на инфраструктуру в РФ, проверить требования законодательства и повторно оценить схему хранения.
- Публичную регистрацию нельзя считать готовой к релизу до отдельной проверки и решения владельца.
- Не проверены фактическая доставка писем, настройки подтверждения Email, SMTP и разрешённые Redirect URLs в Supabase Auth.
- Не выполнен end-to-end тест с новым Email-аккаунтом.
- Supabase Auth URL/SMTP настройки недоступны через текущие инструменты управления; требуется ручная проверка в Dashboard.
- Вход по логину использует публичную Edge Function с одинаковым ответом для неизвестного логина и неверного пароля; Supabase Auth применяет собственные лимиты попыток пароля. Дополнительный rate limit на username endpoint следует добавить до масштабирования.
- Leaked password protection ранее была отмечена Security Advisor как выключенная; включить до публичного запуска.

## Первое пользовательское пространство
- Страница app.html заменена на минимальную оболочку рабочего пространства, доступную только после Supabase Auth session check.
- Нижняя навигация из пяти разделов слева направо: Проекты, Идеи, Команда, Инструменты, Профиль.
- Все пять разделов пока являются заглушками; переключение работает на клиенте без запросов к БД.
- Добавлен отдельный workspace pattern в Design System; продуктовая логика остаётся в presentation layer.
- Выход из аккаунта доступен в верхней панели.

## Совместимость с iOS Safari
- Для ссылок, кнопок и интерактивных ролей добавлен `touch-action: manipulation`: это отключает двойное касание для приближения на интерактивных элементах, сохраняя стандартное масштабирование жестом двумя пальцами.
- Проверка на физическом iPhone после публикации ещё требуется.
