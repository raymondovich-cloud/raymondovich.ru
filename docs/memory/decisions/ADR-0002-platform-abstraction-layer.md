# ADR-0002 — Платформенный слой и единый серверный контракт

> **Проект:** Raymondovich.ru  
> **Документ:** Architecture Decision Record  
> **Версия:** 1.1  
> **Статус:** Утверждено  
> **Дата:** 2026-11-10

## Контекст

Текущая SPA использует hash-навигацию, browser storage, browser dialogs, внешние ссылки и CSS viewport assumptions. Telegram и iOS имеют собственные системные API. Нельзя дублировать бизнес-логику и менять поведение Web при подготовке других клиентов.

## Рассмотренные варианты

1. Разветвлять поведение по платформам во всех компонентах.
2. Ввести один платформенный фасад с адаптерами, сохранив существующие модули навигации и бизнес-сценарии.
3. Переписать клиент на новый фреймворк/сборщик до интеграции платформ.

## Предложенный выбор

Вариант 2. Предусмотреть фасад `window.RaymondovichPlatform` с минимальным API для определения платформы, внешних ссылок, auth redirect, standalone, haptics, share и синхронизации back button. Web-адаптер повторяет текущее поведение; Telegram/native адаптеры загружаются только на своей платформе. Навигационный контроллер остаётся единственным владельцем истории.

Новые бизнес-операции реализуются на сервере через RPC/Edge Functions под RLS. Клиентские платформы используют единый контракт. Не вводить package.json, сборщик, фреймворк или сторонние зависимости без отдельного согласования.

## Последствия

- Изменения Web должны быть нейтральными: те же маршруты, storage keys, Supabase config, redirect URL и пользовательский UX.
- Платформенные API изолированы от модулей и Design System.
- Ранний Telegram hash bootstrap обязателен до navigation.js.
- Telegram SDK загружается динамически с официального telegram.org только в Telegram.
- iOS adapter не создаётся до выбора способа оболочки.
- CSS и визуальные правила остаются только в `source/design-system/`; JS не назначает inline styles.
- Точная версия supabase-js и vendor strategy остаются отдельным риском, не исправлять на этом этапе.

## Решение владельца

2026-11-10 владелец утвердил фасад `window.RaymondovichPlatform`, минимальные платформенные адаптеры, единый серверный контракт новых бизнес-операций и сохранение существующего навигационного контроллера. Существующие прямые обращения к Supabase не переписываются в Этапе 1; их перенос требует отдельного аудита и приоритизации.
