# Ideas — функциональная спецификация

> **Проект:** Raymondovich.ru  
> **Модуль:** Ideas  
> **Версия:** 1.0  
> **Статус:** Базовая модель согласована владельцем  
> **Дата:** 2026-11-08  
> **Область:** Owner Control Center

---

## 1. Назначение

Ideas — закрытый модуль Owner Control Center для фиксации, оценки, отбора и развития идей экосистемы Raymondovich.

Идея является самостоятельной управляемой сущностью. Она может оставаться в реестре идей, быть отложена в архив или пройти процесс преобразования в проект. Создание идеи само по себе не создаёт проект и не меняет его коммерческий или юридический статус.

## 2. Доступ

- В первой версии модуль доступен только владельцу с действующей ролью `admin` в доверенных claims Supabase Auth.
- Проверка роли в интерфейсе используется только для отображения. Она не является границей безопасности.
- Серверный доступ к данным ограничивается отдельной проверкой роли владельца и RLS.
- `user_metadata` не используется для принятия решений об авторизации.
- Партнёры, ученики и обычные пользователи не получают доступ к идеям в первой версии.

## 3. Жизненный цикл

Используются следующие фиксированные статусы:

| Код | Отображаемое название | Значение |
|---|---|---|
| `new` | Новая | Идея только зафиксирована |
| `under_review` | На рассмотрении | Владелец оценивает идею |
| `selected` | Отобрана | Принято решение развивать идею |
| `in_development` | В разработке | Идея активно прорабатывается |
| `converted` | Преобразована в проект | Идея связана с созданным проектом |
| `archived` | Архив | Идея отложена или отклонена |

Статус хранится как стабильный машинный код. Отображаемые подписи задаются в прикладном слое, а не используются как идентификаторы.

Статус `converted` допустим только при наличии подтверждённой связи с существующим проектом. Нельзя имитировать преобразование изменением одного статуса. До появления рабочего Projects-модуля действие преобразования не должно создавать фиктивный проект.

## 4. Категории

- Категории создаются, переименовываются, сортируются и архивируются владельцем.
- Категория имеет стабильный идентификатор; идеи ссылаются на неё по ID.
- Удаление категории с привязанными идеями не должно приводить к потере или скрытому изменению идей. В первой версии применяется архивирование категории.
- Название категории уникально без учёта регистра в пределах списка владельца.
- Начальный список категорий не зашивается в интерфейс и не создаётся автоматически как фиктивные данные.

## 5. Данные идеи

Первая версия предусматривает следующие поля:

| Поле | Обязательность | Назначение |
|---|---|---|
| Название | Обязательно | Краткое название идеи |
| Описание | Необязательно | Суть и детали задумки |
| Категория | Необязательно | Ссылка на настраиваемую категорию |
| Цель | Необязательно | Какую задачу решает идея |
| Аудитория | Необязательно | Для кого предназначена |
| Потенциальная ценность | Необязательно | Ожидаемая польза или результат |
| Приоритет | Обязательно | `low`, `normal`, `high`, `critical` |
| Статус | Обязательно | Фиксированный жизненный цикл из раздела 3 |
| Заметки | Необязательно | Рабочие заметки владельца |
| Ссылки | Необязательно | Внешние материалы и источники |
| Дата создания / изменения | Системные | Временные метки |
| Архивная дата | Системная | Фиксация архивирования |

Приоритет и статус — разные измерения: приоритет отражает важность, статус — этап жизненного цикла.

## 6. Основные сценарии первой версии

1. Открыть реестр идей.
2. Создать идею.
3. Просмотреть полную карточку идеи.
4. Изменить данные идеи.
5. Изменить статус и приоритет.
6. Искать по названию и описанию.
7. Фильтровать по статусу, категории и приоритету.
8. Сортировать по дате изменения и приоритету.
9. Создавать и редактировать категории.
10. Архивировать и возвращать идею из архива.
11. Просматривать историю существенных изменений.

Удаление идеи не является обычным пользовательским действием первой версии. Архивирование сохраняет данные и историю.

## 7. Преобразование идеи в проект

Преобразование — отдельная операция, а не простое редактирование статуса.

Операция становится доступной после подключения Projects-модуля и должна:
- проверить право владельца;
- создать проект через штатный механизм Projects;
- сохранить ссылку на созданный проект в исходной идее;
- зафиксировать событие преобразования;
- не удалять и не переписывать исходное содержание идеи;
- быть защищена от повторного создания проекта при повторном запросе.

Если создание проекта завершилось ошибкой, идея остаётся в прежнем состоянии. Частично созданные данные не должны оставаться без согласованной процедуры компенсации.

## 8. История изменений

Для существенных действий фиксируются:
- создание идеи;
- изменение содержательных полей;
- изменение категории, статуса и приоритета;
- архивирование и восстановление;
- преобразование в проект.

Запись истории должна содержать идентификатор идеи, тип события, время, идентификатор действовавшего пользователя и минимально необходимое описание изменения. Секреты и избыточные персональные данные в журнал не записываются.

## 9. Предварительная модель хранения

Логическая модель первой версии:
- `ideas` — основная запись идеи;
- `idea_categories` — управляемые владельцем категории;
- `idea_activity` — история существенных действий;
- ссылки могут храниться отдельными записями, если это оправдано реализацией формы и валидацией.

Физическая схема, индексы, ограничения, права SQL и миграция фиксируются отдельно после проверки текущей схемы Supabase и определения staging-среды. Нельзя выполнять первую DDL-миграцию непосредственно в production без проверки на staging.

## 10. Безопасность и целостность

- RLS включён на всех таблицах модуля.
- Владелец определяется только по доверенному `app_metadata.role = 'admin'` в JWT или через более строгую серверную проверку, согласованную с текущей архитектурой.
- Клиент не может назначить себе роль, владельца записи или идентификатор другого пользователя.
- Любая операция изменения проверяет авторизацию на серверной стороне.
- Для новой таблицы отдельно проверяются Data API grants: создание таблицы в `public` само по себе не означает, что она автоматически доступна через Data API.
- Никакие service-role или secret keys не передаются в браузер.
- После миграции выполняются тесты разрешённого и запрещённого доступа и проверка Supabase Security Advisors.

## 11. Границы первой версии

В первую версию не входят:
- совместная работа над идеями;
- доступ партнёров и учеников;
- публичные идеи и пользовательские предложения;
- голосование и комментарии;
- автоматическая оценка идеи ИИ;
- автоматическое создание задач;
- полноценное преобразование в проект до готовности Projects-модуля;
- файловое хранилище вложений, если оно не требуется утверждённому пользовательскому сценарию.

## 12. Критерии готовности

Модуль первой версии готов, когда владелец может безопасно создать, просмотреть, найти, отфильтровать, изменить, категоризировать, приоритизировать и архивировать идею; категории настраиваются без изменения кода; доступ других ролей запрещён на серверном уровне; история изменений сохраняется; интерфейс корректно работает на мобильном Safari и не вызывает автоматический zoom форм.
