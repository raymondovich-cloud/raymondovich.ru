# Ideas — функциональная спецификация

> **Проект:** Raymondovich.ru  
> **Модуль:** Ideas  
> **Версия:** 1.2  
> **Статус:** Базовая модель согласована владельцем; существующая БД обследована  
> **Дата:** 2026-11-08  
> **Область:** Owner Control Center

---

## 1. Назначение

Ideas — закрытый модуль Owner Control Center для фиксации, оценки, отбора и развития идей экосистемы Raymondovich.

Идея является самостоятельной управляемой сущностью. Она может оставаться в реестре идей, быть отложена в архив или пройти процесс преобразования в проект. Создание идеи само по себе не создаёт проект и не меняет его коммерческий или юридический статус.

## 2. Доступ

- В первой версии модуль доступен только владельцу с действующей ролью `admin` в доверенных claims Supabase Auth.
- Проверка роли в интерфейсе используется только для отображения. Она не является границей безопасности.
- Серверный доступ к данным ограничивается проверкой роли владельца и RLS.
- `user_metadata` не используется для принятия решений об авторизации.
- Партнёры, ученики и обычные пользователи не получают доступ к идеям в первой версии.

## 3. Жизненный цикл

Утверждённые владельцем статусы:

| Код модели | Отображаемое название | Значение |
|---|---|---|
| `new` | Новая | Идея только зафиксирована |
| `review` | На рассмотрении | Владелец оценивает идею |
| `selected` | Отобрана | Принято решение развивать идею |
| `in_development` | В разработке | Идея активно прорабатывается |
| `converted` | Преобразована в проект | Идея связана с созданным проектом |
| `archived` | Архив | Идея отложена или отклонена |

Код `review` сохранён совместимым с существующей базой данных. Отображаемые подписи задаются в прикладном слое. В существующей БД также обнаружен старый код `launched`; его нельзя массово переименовывать или удалять без отдельной проверки зависимостей. В интерфейсе он не должен подменять новый статус `converted`.

Статус `converted` допустим только при наличии подтверждённой связи с существующим проектом. В текущей схеме проектов для этого уже предусмотрено поле `projects.source_idea_id`. Преобразование должно создавать проект через штатный механизм Projects и сохранять эту связь. Одного изменения статуса недостаточно.

## 4. Категории

- Категории создаются, переименовываются, сортируются и архивируются владельцем.
- Категория имеет стабильный идентификатор; идеи ссылаются на неё по ID.
- Удаление категории с привязанными идеями не должно приводить к потере или скрытому изменению идей. Применяется архивирование категории.
- Название категории уникально без учёта регистра в пределах владельца.
- Начальный список категорий не зашивается в интерфейс и не создаётся автоматически как фиктивные данные.

## 5. Данные идеи

В существующей таблице `public.ideas` уже имеются поля:

- `id`, `owner_id`, `name`, `description`;
- `status`, `priority`;
- `goal`, `concept`, `additional_info`;
- `estimated_cost`, `expected_revenue`, `business_model`;
- `launched_at`, `created_at`, `updated_at`.

Эти поля и данные должны быть сохранены. Новая реализация адаптируется к действующей схеме; запрещено создавать вторую параллельную таблицу идей или перезаписывать существующие записи.

| Поле интерфейса | Текущее поле БД / план |
|---|---|
| Название | `name` |
| Описание | `description` |
| Цель | `goal` |
| Концепция | `concept` |
| Заметки / дополнительная информация | `additional_info` |
| Предполагаемая модель бизнеса | `business_model` |
| Оценка затрат | `estimated_cost` |
| Ожидаемая выручка | `expected_revenue` |
| Приоритет | `priority` |
| Статус | `status` |
| Категория | Добавить nullable `category_id` после проверки staging |
| Целевая аудитория | Отдельное поле добавлять только если форма подтверждает необходимость; не дублировать `additional_info` |
| Потенциальная ценность | На первом этапе отображать как часть концепции/ожидаемого результата; отдельное поле не добавлять без отдельного обоснования |
| Дата создания / изменения | `created_at`, `updated_at` |

Приоритеты существующей БД: `low`, `normal`, `high`, `critical`. Они сохраняются. Приоритет и статус — разные измерения.

## 6. Основные сценарии первой версии

1. Открыть реестр идей.
2. Создать идею.
3. Просмотреть полную карточку идеи.
4. Изменить данные идеи.
5. Изменить статус и приоритет.
6. Искать по названию и описанию.
7. Фильтровать по статусу, категории и приоритету.
8. Сортировать по дате изменения и приоритету.
9. Создавать, переименовывать, сортировать и архивировать категории.
10. Архивировать и возвращать идею из архива.
11. Просматривать историю существенных изменений.

Удаление идеи не является обычным пользовательским действием первой версии. Архивирование сохраняет данные и историю.

## 7. Преобразование идеи в проект

В таблице `public.projects` уже существует `source_idea_id`, ссылающееся на идею. Это используемая точка связи, которую необходимо проверить на ограничения и индексы до реализации операции.

Преобразование:
- проверяет право владельца;
- создаёт проект через штатный механизм Projects;
- сохраняет `projects.source_idea_id = ideas.id`;
- переводит идею в `converted` только после успешного создания проекта;
- фиксирует событие преобразования;
- не удаляет и не переписывает исходное содержание идеи;
- защищено от повторного создания проекта для той же идеи.

До готовности интерфейса и серверной операции Projects кнопка преобразования не должна создавать фиктивный проект или менять статус.

## 8. История изменений

Для существенных действий фиксируются:
- создание идеи;
- изменение содержательных полей;
- изменение категории, статуса и приоритета;
- архивирование и восстановление;
- преобразование в проект.

Запись истории содержит идентификатор идеи, тип события, время, идентификатор действовавшего пользователя и минимально необходимое описание изменения. Секреты и избыточные персональные данные в журнал не записываются.

## 9. Предварительная модель хранения и аудит существующей БД

Логическая модель:
- `ideas` — существующая основная таблица; не дублировать;
- `idea_categories` — новая таблица настраиваемых категорий;
- `idea_activity` — новая таблица истории существенных действий.

До миграции обследована действующая БД Supabase, на которую указывает клиент сайта (`yajybgdorhxebbigwjgi`):

- таблица `public.ideas` уже существует;
- в ней обнаружено 8 записей, все со статусом `new`;
- таблица содержит поля планирования, затрат, ожидаемой выручки и бизнес-модели;
- RLS включён; действующая политика ограничивает строки ролью `admin` из `app_metadata` и совпадением `auth.uid() = owner_id`;
- таблица `public.projects` уже содержит `source_idea_id`;
- отдельной таблицы категорий и истории идей в текущем списке таблиц нет.

Это означает, что Ideas уже имеет часть серверной основы. Следующая реализация должна расширять её без потери данных и без создания параллельной модели.

Физическая схема, индексы, ограничения, права SQL и миграция фиксируются после проверки текущих ограничений, триггеров и связей на staging. Нельзя выполнять DDL-изменения непосредственно в production без проверки на staging.

## 10. Безопасность и целостность

- RLS включён на всех таблицах модуля.
- Владелец определяется только по доверенному `app_metadata.role = 'admin'` в JWT или через более строгую серверную проверку.
- Клиент не может назначить себе роль, владельца записи или идентификатор другого пользователя.
- Любая операция изменения проверяет авторизацию на серверной стороне.
- Для новых таблиц отдельно проверяются Data API grants: создание таблицы в `public` само по себе не означает, что она автоматически доступна через Data API.
- Никакие service-role или secret keys не передаются в браузер.
- После миграции выполняются тесты разрешённого и запрещённого доступа и проверка Supabase Security Advisors.

## 11. Границы первой версии

В первую версию не входят:
- совместная работа над идеями;
- доступ партнёров и учеников;
- публичные идеи и пользовательские предложения;
- голосование и комментарии;
- автоматическая оценка идеи ИИ;
- автоматическое создание задач;
- файловое хранилище вложений.

## 12. Критерии готовности

Модуль первой версии готов, когда владелец может безопасно создать, просмотреть, найти, отфильтровать, изменить, категоризировать, приоритизировать и архивировать идею; категории настраиваются без изменения кода; доступ других ролей запрещён на серверном уровне; история изменений сохраняется; преобразование создаёт ровно один связанный проект через Projects; интерфейс корректно работает на мобильном Safari и не вызывает автоматический zoom форм.

## 13. Избранное и «В фокусе»

Избранное — персональная связь пользователя с идеей; оно не заменяет и не изменяет статус идеи.

- В деталях идеи размещается переключатель-звезда.
- Добавленная в избранное идея дополнительно появляется в представлении «Идеи → В фокусе» и в «Профиль → Избранное».
- Добавление/удаление звезды не меняет категорию, приоритет, статус, архивность или связь с проектом.
- Идея остаётся в своём основном разделе и не перемещается из него.
- При soft delete запись избранного сохраняется, но идея скрывается из активных представлений. Восстановление возвращает её с прежней отметкой.
- При окончательном удалении идеи запись избранного удаляется через FK `ON DELETE CASCADE`.
- Применяются общие контракты и правила хранения из `docs/product/favorites-module-specification.md`.
- Текущая граница доступа Ideas остаётся admin-only; избранное не выдаёт дополнительных полномочий.
