# Favorites — функциональная и техническая спецификация

> **Проект:** Raymondovich.ru  
> **Модуль:** Favorites  
> **Версия:** 1.0  
> **Статус:** Согласовано владельцем для реализации  
> **Дата:** 2026-11-12  
> **Путь:** `docs/product/favorites-module-specification.md`

## 1. Назначение

Favorites — единый механизм персонального избранного для сущностей Projects и Ideas. Он предоставляет один источник данных для трёх представлений:
- Projects → «В фокусе»;
- Ideas → «В фокусе»;
- Profile → «Избранное».

Favorites не владеет проектами или идеями, не меняет их жизненный цикл и не дублирует их данные.

## 2. Утверждённое поведение

### 2.1 Проекты

- Новый проект появляется в основном реестре «Проекты → В работе» согласно существующей логике Projects.
- В Project Overview рядом с существующей зелёной плашкой статуса размещается компактная звезда.
- Нажатие на неактивную звезду добавляет текущий проект в избранное.
- Проект дополнительно появляется в «Проекты → В фокусе» и «Профиль → Избранное».
- Проект продолжает отображаться в «В работе». Избранное не является альтернативным статусом и не перемещает проект из основного реестра.
- Нажатие на активную звезду удаляет связь избранного и синхронно убирает проект из обоих представлений.

### 2.2 Идеи

- В деталях идеи размещается аналогичный переключатель-звезда.
- Добавленная идея дополнительно появляется в «Идеи → В фокусе» и «Профиль → Избранное».
- Идея продолжает отображаться в своём основном разделе.
- Избранное не меняет статус, категорию, приоритет, архивность и связь идеи с проектом.
- Удаление звезды убирает идею из «В фокусе» и «Профиль → Избранное».

### 2.3 Общее представление профиля

- Profile показывает проекты и идеи в одном списке.
- Для каждой записи видны название и тип объекта («Проект» или «Идея»).
- Выбор записи открывает её существующий экран/маршрут.
- Profile не создаёт собственную копию списка и не хранит независимый флаг избранного.

## 3. Модель данных

Используется отдельная таблица `public.user_favorites`.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `user_id` | uuid | Пользователь, добавивший объект |
| `project_id` | uuid, nullable | Ссылка на `public.projects.id` |
| `idea_id` | uuid, nullable | Ссылка на `public.ideas.id` |
| `created_at` | timestamptz | Время добавления |

Ограничения целостности:
- Ровно одно из `project_id` и `idea_id` должно быть заполнено.
- `user_id` ссылается на `auth.users.id` с `ON DELETE CASCADE`.
- `project_id` ссылается на `projects.id` с `ON DELETE CASCADE`.
- `idea_id` ссылается на `ideas.id` с `ON DELETE CASCADE`.
- Частичные уникальные индексы запрещают повторно добавлять один и тот же объект одним пользователем.
- Для списков создаются индексы по `user_id` и соответствующему внешнему ключу.

Не использовать полиморфную пару `entity_type/entity_id`: она не обеспечивает обычный FK на обе целевые таблицы.

## 4. Жизненный цикл и корзина

### 4.1 Добавление и удаление из избранного

- Добавление и удаление выполняются отдельными application use cases.
- Операции идемпотентны: повторное добавление не создаёт дубликат; повторное удаление не приводит к ошибке состояния.
- После успешной операции инвалидируются/обновляются in-memory snapshots Projects, Ideas и Favorites текущего пользователя.
- При ошибке сохранённое состояние не подменяется локальным оптимистичным предположением; UI возвращает звезду в подтверждённое сервером состояние и показывает понятную ошибку.

### 4.2 Soft delete и восстановление

- Перемещение проекта или идеи в корзину не удаляет запись из `user_favorites`.
- Пока у объекта заполнено `deleted_at`, он исключается из активных списков «В фокусе» и «Профиль → Избранное».
- При восстановлении `deleted_at` очищается; прежняя запись избранного автоматически снова участвует в представлениях.
- Не требуется отдельная операция «восстановить избранное»: сохранённая связь является источником истины.
- Это правило не меняет существующие статусы и поля архивации Ideas.

### 4.3 Окончательное удаление

- Окончательное удаление проекта или идеи выполняется только через существующий сценарий корзины.
- FK `ON DELETE CASCADE` удаляет связанные записи избранного вместе с объектом.
- Favorites не препятствует окончательному удалению и не оставляет осиротевшие связи.

## 5. Доступ и RLS

Текущие Projects и Ideas имеют admin-only границу. Первая версия Favorites наследует её и не расширяет доступ партнёрам, ученикам или другим ролям.

Требования:
- RLS включён на `public.user_favorites`.
- Пользователь читает и изменяет только строки, где `user_id = auth.uid()`.
- Вставка разрешена только при подтверждённой роли `app_metadata.role = 'admin'`, совпадении `user_id = auth.uid()` и существовании целевого активного объекта, принадлежащего этому пользователю.
- Проект проверяется через `projects.owner_id = auth.uid()` и `projects.deleted_at IS NULL`.
- Идея проверяется через `ideas.owner_id = auth.uid()` и `ideas.deleted_at IS NULL`.
- Удаление связи разрешено только её владельцу.
- Клиентская проверка роли и скрытие кнопки не заменяют RLS.
- Сервисный ключ в браузере не используется.
- Табличные grants ограничиваются необходимыми операциями для `authenticated`; доступ anon отсутствует.

Будущая поддержка партнёров требует отдельного решения о доступе к объектам и проектной membership-модели. Само наличие записи избранного не предоставляет доступ к объекту.

## 6. Application Layer и контракты

Создаётся отдельный модуль `source/application/favorites/`.

Публичные use cases:
- `getFavorites()` — вернуть избранные доступные активные проекты и идеи текущего пользователя;
- `isFavorite({ projectId })` / `isFavorite({ ideaId })` — проверить состояние для объекта;
- `addProjectToFavorites(projectId)`;
- `removeProjectFromFavorites(projectId)`;
- `addIdeaToFavorites(ideaId)`;
- `removeIdeaFromFavorites(ideaId)`.

Контракт не принимает произвольный `user_id` от UI: пользователь определяется доверенной Supabase Auth session. Для переключения допускается единый use case с типизированным объектом, если он не ослабляет проверку входных данных.

Infrastructure реализует Supabase repository. Presentation вызывает application contract и не обращается напрямую к таблице.

## 7. Представления и синхронизация

- «В фокусе» Projects получает только проекты из Favorites.
- «В фокусе» Ideas получает только идеи из Favorites.
- Profile получает оба типа объектов из одного вызова `getFavorites()`.
- Все три представления используют одну и ту же серверную связь; отдельные флаги и дублирующие таблицы запрещены.
- Snapshot изолируется по user ID и действует только в текущей вкладке браузера, согласно архитектуре существующих реестров.
- Успешное изменение избранного обновляет или инвалидирует соответствующие snapshots.
- Переходы между представлениями не должны создавать независимую историю навигации.

## 8. UI и Design System

- Звезда в Project Overview размещается рядом с существующей плашкой статуса, без изменения семантики статуса.
- Звезда в Idea Detail использует тот же визуальный компонент и состояния.
- Обязательны состояния «не избрано», «избрано», «загрузка/недоступно» и «ошибка».
- Кнопка имеет доступное имя, `aria-pressed`, видимый focus state и достаточную область нажатия для touch.
- Визуальное оформление, размеры, цвета, hover/focus/active/disabled состояния размещаются только в `source/design-system/`.
- JavaScript переключает классы и ARIA/data-атрибуты; inline CSS и `element.style` запрещены.
- Компонент должен корректно работать в iPhone Safari и Telegram Mini App, включая safe-area и touch interaction.

## 9. Критерии приёмки

1. Созданный проект появляется в «В работе».
2. Добавление звезды показывает его также в «В фокусе» и Profile Favorites.
3. Проект остаётся в «В работе».
4. Удаление звезды убирает его из обоих представлений без удаления проекта.
5. Аналогичные сценарии работают для идей.
6. В профиле одновременно отображаются проекты и идеи с правильным типом.
7. Два пользователя не видят и не изменяют избранное друг друга.
8. Нельзя добавить в избранное чужой или недоступный объект прямым запросом.
9. Soft delete скрывает объект из активных представлений, сохраняя связь.
10. Восстановление возвращает объект в прежнее избранное без дополнительного действия.
11. Hard delete удаляет связь каскадно.
12. Ошибки Supabase не оставляют UI в ложном состоянии.
13. Не нарушены корзина, статусы, архивирование, преобразование идеи в проект и существующая навигация.
14. Все стили находятся в Design System.

## 10. План реализации

Вертикальные этапы:
1. SQL migration, RLS, grants и проверка целостности на staging.
2. Favorites application contract и Supabase repository с тестами.
3. Переключатель-звезда и подразделы «В фокусе» в Projects/Ideas.
4. Profile Favorites, синхронизация snapshots и полная регрессионная проверка.

Production DDL и публикация не входят в эту ветку без отдельного разрешения владельца.
