# Projects — функциональная спецификация

> **Проект:** Raymondovich.ru  
> **Модуль:** Projects  
> **Версия:** 1.2  
> **Статус:** Согласовано владельцем для реализации первой вертикали  
> **Дата:** 2026-11-10  
> **Область:** Owner Control Center; дальнейшее расширение Partner Workspace

---

## 1. Назначение

Projects — модуль управления проектами экосистемы. Он предоставляет владельцу реестр проектов и отдельное рабочее пространство каждого проекта.

Проект может быть:
- создан непосредственно в Projects;
- создан атомарным преобразованием идеи через Ideas.

Оба пути создают одну сущность в `public.projects`. Проект, созданный из идеи, сохраняет `source_idea_id`; прямой проект имеет `source_idea_id = null`.

## 2. Утверждённая навигация

Каждый проект открывается в отдельном Project Workspace. Внутри него четыре функциональных модуля открываются на самостоятельных экранах:

1. Services — подключённые сервисы и инфраструктурные ресурсы.
2. Accounting — доходы, расходы и финансовый результат.
3. Analytics — динамика пользователей, активность и партнёрская атрибуция.
4. Marketing — площадки продвижения, аккаунты, публикации и статистика.

Навигация: Projects Registry → Project Overview → отдельный экран выбранного модуля. Возврат из модуля ведёт к обзору того же проекта. Общая навигация браузера должна сохранять корректную историю.

## 3. Карточка проекта в реестре

Карточка компактная и содержит:
- название;
- статус;
- приоритет;
- источник: создан напрямую или из идеи;
- дату последнего изменения.

Поиск работает по названию и описанию. Фильтрация по статусу и приоритету — отдельное расширение реестра.

## 4. Обзор проекта

Визуальная композиция соответствует утверждённому референсу:
- верхняя карточка проекта со статусом;
- название;
- три финансово-операционных показателя: пользователи, доход, расход;
- сетка 2×2 из карточек Services, Accounting, Analytics и Marketing;
- краткая сводка и переход в каждый модуль.

Нельзя показывать выдуманные числа или примерные значения как фактические. Пока источник данных не реализован, отображать «—», «Нет данных» или честный статус ручного ввода. Демонстрационные данные допустимы только в явно обозначенном preview-режиме, не в реальном кабинете.

### Правила показателей шапки

- `users` и `income` имеют состояние `not_configured` и отображаются как «—», пока Analytics и Accounting не предоставляют реальные показатели.
- `expense` сначала использует фактическое значение публичного контракта Accounting, если он его вернул.
- Пока Accounting не настроен, при наличии подключённых связей Services `expense` показывает сумму `monthly_cost` по каждой валюте отдельно. Значение маркируется `period: "month"`, `source: "services_recurring"`, `basis: "manual_estimate"` и сопровождается подписью «в мес · по сервисам».
- Подключённые бесплатные связи отображаются как «0 ₽/мес» (или ноль в их валюте). При отсутствии подключённых связей расход отображается как «—». При нескольких валютах суммы перечисляются через « · » без конвертации и сложения.
- При ошибке чтения Services значение расхода не подменяется нулём. Ручные оценки не являются фактическими бухгалтерскими операциями.
- Текст пояснения: «Расход показывает ежемесячные платежи по сервисам проекта (ручной ввод); фактический учёт появится в „Бухгалтерии“».

## 5. Границы модулей

### 5.1 Services
Владеет связями проекта с сервисами и ресурсами. В существующей БД уже есть:
- `ecosystem_tools` — каталог сервисов;
- `tool_resources` — конкретные ресурсы/аккаунты/домены/инфраструктурные объекты;
- `project_tool_relations` — связи проекта с сервисами;
- `project_resource_relations` — связи проекта с ресурсами.

Services не хранит пароли, API keys, recovery codes или иные секреты. Допустимы только безопасные ссылки на секрет-хранилище и метаданные доступа.

### 5.2 Accounting
Отдельный владелец финансовых операций. Планируемые сущности:
- финансовая операция: доход или расход;
- категория и статья;
- сумма и валюта;
- дата операции и отчётный период;
- проект;
- контрагент/описание при необходимости;
- источник данных: ручной ввод или интеграция;
- подтверждённость/статус операции;
- вложение/документ — отдельный будущий этап.

Нельзя смешивать выручку, поступившие деньги, расходы, обязательства, комиссии и выплаты партнёрам. Формулы чистого результата и распределения доходов должны быть явно определены до включения расчётов.

### 5.3 Analytics
Отдельный владелец аналитических наблюдений и агрегатов:
- пользователи и прирост;
- активность/онлайн по часам, дням, неделям и месяцам;
- источники переходов;
- партнёрские ссылки и атрибуция;
- период, часовой пояс, метод измерения и происхождение данных.

Аналитика не меняет первичные финансовые операции и не подменяет данные маркетинговых платформ. Источник и метод подсчёта каждого показателя должны быть видны.

### 5.4 Marketing
Отдельный владелец каналов продвижения:
- платформа;
- аккаунт/канал;
- ссылка;
- статус подключения;
- идентификатор внешнего аккаунта;
- публикации/кампании;
- источник статистики и время последней синхронизации.

Автоматическая выгрузка статистики подключается поэтапно через официальные API и только после проверки разрешений платформы, ограничений, стоимости и условий использования. Нельзя обещать автоматическую синхронизацию там, где API её не предоставляет.

## 6. Межмодульное взаимодействие

Модули не импортируют внутренние реализации друг друга и не обращаются напрямую к чужим таблицам.

Разрешённые механизмы:
- публичные контракты модулей;
- Application Layer / Process Manager как посредник;
- события с минимальным необходимым payload.

Project Overview получает сводки через прикладной фасад/контракт каждого модуля. В первой вертикали допустим единый фасад Projects Overview, который вызывает только публичные интерфейсы модулей. Фасад не содержит бизнес-логику бухгалтерии, аналитики, маркетинга или сервисов.

## 7. Доступ и безопасность

Первая версия доступна только владельцу с доверенным `app_metadata.role = 'admin'`. UI-проверка роли не является защитой. Каждая таблица в exposed schema обязана иметь RLS; политики ограничивают пользователя через `auth.uid()` и проверенный app_metadata claim.

Партнёрский доступ не включается до отдельной модели membership/permissions. Нельзя считать, что наличие роли partner автоматически даёт доступ ко всем проектам.

Нельзя хранить в обычных таблицах или выводить в браузер:
- API keys и access tokens;
- пароли и коды восстановления;
- банковские реквизиты, если они не нужны для конкретной операции;
- приватные ключи и секреты интеграций.

## 8. Этапы реализации

### Этап 1 — Projects Registry + Overview
- список и поиск проектов;
- создание проекта напрямую;
- открытие Project Overview;
- переходы в четыре отдельные страницы-модуля;
- отображение реальных данных, уже существующих в БД;
- честные empty states для ещё не реализованных источников;
- интеграция с текущим сценарием Ideas → Projects.

### Этап 2 — Services
- каталог сервисов и связей;
- ресурсы и сроки продления;
- напоминания;
- затем API-интеграции.

### Этап 3 — Accounting
- ручной ввод доходов и расходов;
- отчётные периоды;
- сводный финансовый результат;
- проверка формул и валют.

### Этап 4 — Analytics
- ручные показатели и snapshots;
- графики и сравнение периодов;
- партнёрские ссылки и атрибуция.

### Этап 5 — Marketing
- ручной реестр площадок и аккаунтов;
- публикации и кампании;
- затем официальные API-интеграции по одной.

## 9. Критерии готовности первой вертикали

- Владелец видит реальные проекты из существующей БД.
- Можно создать проект напрямую, не создавая фиктивную идею.
- Идея преобразуется в проект существующей атомарной RPC-операцией.
- Из карточки открывается обзор проекта.
- Четыре модуля открываются на отдельных экранах и возвращаются к правильному проекту.
- Отсутствующие данные не заменяются демонстрационными числами.
- На мобильном Safari интерфейс не ломает ширину и навигацию.
- Существующие данные и таблицы Ideas не повреждены.
- Все стили находятся только в Design System.

## 10. Известные ограничения текущей БД

Read-only обследование Supabase проекта `yajybgdorhxebbigwjgi` от 2026-11-09 подтвердило наличие таблиц `projects`, `project_tool_relations`, `project_resource_relations`, `ecosystem_tools`, `tool_resources`, `project_history`, `project_milestones` и `project_tasks`. В `projects` уже есть одна запись и RLS включён.

В обследованной схеме не обнаружены отдельные таблицы финансовых операций, маркетинговых каналов и аналитических snapshots. Их создание требует отдельных спецификаций, миграций, RLS, явных Data API grants и проверки на staging. Production DDL не выполнять в рамках первой UI-вертикали.

## 11. Удаление проектов и корзина

Удаление проекта выполняется в два этапа. Автоматическая очистка корзины и срок хранения не задаются.

### 11.1 Перемещение в корзину

- В Project Overview доступно действие «Переместить в корзину».
- Перед действием показывается подтверждение с названием проекта.
- Операция является soft delete: `projects.deleted_at` получает timestamp.
- Проект с `deleted_at IS NOT NULL` не отображается в основном реестре и не учитывается в активной сводке.
- Данные проекта и его связи при перемещении не удаляются.

### 11.2 Корзина и восстановление

- В реестре Projects доступен отдельный экран «Корзина».
- Элемент корзины показывает название проекта и дату перемещения.
- Доступны действия «Восстановить» и «Удалить навсегда».
- Восстановление разрешено только для проекта, находящегося в корзине; `deleted_at` очищается, а проект возвращается в реестр с прежним ID и связями.
- Корзина не очищается автоматически.

### 11.3 Окончательное удаление

- Окончательное удаление доступно только из корзины и требует отдельного подтверждения с названием проекта.
- На уровне RLS операция `DELETE` разрешена владельцу с `app_metadata.role = 'admin'` только если `deleted_at IS NOT NULL`.
- Удаление проекта каскадно удаляет принадлежащие ему `project_history`, `project_milestones`, `project_tasks`, `project_tool_relations` и `project_resource_relations` согласно фактическим FK `ON DELETE CASCADE`.
- Общие записи `ecosystem_tools` и `tool_resources` не удаляются вместе с проектом: удаляются только отношения проекта.
- Исходная идея не удаляется. `projects.source_idea_id` ссылается на `ideas.id` через `ON DELETE SET NULL`; удаление проекта не запускает удаление идеи.
- Любые будущие таблицы, добавляющие FK к проекту, должны быть включены в анализ перед включением окончательного удаления.

### 11.4 Граница доступа

Первая версия остаётся admin-only. UI не считается границей безопасности: ограничения окончательного удаления обеспечиваются RLS. Партнёрский доступ к корзине не включён.

## Открытые решения

1. **Сосуществование Services и Accounting.** Когда Accounting начнёт возвращать фактические операции, определить для владельца правило отображения и периодизации регулярных платежей Services: показывать отдельно, исключать из фактических расходов, связывать с операциями или применять иной утверждённый подход. До решения запрещено автоматически складывать эти источники или считать Services бухгалтерской операцией.
