# AGENT.md

**Project:** raymondovich.ru  
**Document version:** 1.1  
**Status:** Active

Этот документ устанавливает обязательные правила работы с репозиторием raymondovich.ru. Правила распространяются на всех разработчиков, AI-агентов и модели, работающие с проектом.

## 1. Naming convention — имена файлов и папок

1. Все новые папки и файлы должны иметь имена, записанные строчными буквами (lowercase).
2. Если имя состоит из нескольких слов, слова разделяются дефисом (`-`). Пробелы в именах запрещены.
3. Не использовать заглавные буквы и пробелы в новых именах.
4. Перед созданием файла или папки агент обязан проверить соответствие имени этим правилам.
5. Если существующая структура не соответствует правилам, агент не должен переименовывать её самовольно: переименование выполняется отдельной согласованной задачей с проверкой всех импортов, ссылок и конфигураций.

Примеры:

| Правильно | Неправильно |
|---|---|
| `design-system` | `Design System` |
| `user-profile` | `User Profile` |
| `agent.md` | `Agent.md` |
| `auth-service.js` | `Auth Service.js` |

## 2. File versioning — версии файлов

1. Каждый новый изменяемый файл должен получить начальную версию `1.0`.
2. Каждое последующее изменение содержимого файла требует увеличения его версии.
3. Формат версии: `major.minor` — например, `1.0`, `1.1`, `1.2`, `2.0`.
4. Перед изменением агент обязан определить текущую версию файла.
5. Версия должна храниться в самом файле в подходящем для его формата виде: в заголовке, комментарии или поддерживаемом поле метаданных.
6. Если формат не поддерживает комментарии или метаданные, версия фиксируется в сопровождающем manifest-файле или документации. Нельзя добавлять в такой файл недопустимый синтаксис ради версии.
7. Изменение версии должно происходить в том же коммите, что и изменение содержимого.
8. Нельзя сбрасывать, пропускать назад или произвольно менять версию.
9. Изменение только версии без содержательного изменения также должно иметь понятное обоснование.

## 3. Design system — единый визуальный слой

Весь визуальный слой приложения размещается исключительно в:

`source/design-system/`

Это обязательная архитектурная граница.

В `source/design-system/` должны находиться:

- UI-компоненты и их визуальная реализация;
- CSS и другие файлы стилей;
- дизайн-токены;
- цветовые палитры и темы;
- типографика;
- размеры, сетки и отступы;
- визуальные состояния компонентов;
- анимации и motion-правила;
- адаптивные правила;
- общие визуальные паттерны.

Запрещено:

1. Размещать CSS, визуальные стили или визуальные токены в доменных, прикладных, инфраструктурных и иных модулях за пределами `source/design-system/`.
2. Создавать локальные или дублирующие дизайн-системы внутри отдельных модулей.
3. Задавать визуальные параметры независимо от общих токенов и правил Design System.
4. Дублировать реализацию общих UI-компонентов в разных частях проекта.
5. Обходить Design System через inline-стили, локальные CSS-файлы или стили, встроенные в HTML/JavaScript.

Остальные слои могут содержать семантическую разметку и логику представления, необходимую для работы конкретного сценария, но не должны самостоятельно определять визуальное оформление. Они используют компоненты и стили из Design System.

## 4. Domain ownership and cross-domain boundaries — владение доменами

Верхний уровень предметной области Raymondovich состоит ровно из пяти глобальных доменов, соответствующих основным разделам продукта:

| Глобальный раздел | Обязательный каталог |
|---|---|
| Профиль | `source/domain/profile/` |
| Идеи | `source/domain/ideas/` |
| Команда | `source/domain/team/` |
| Инструменты | `source/domain/tools/` |
| Проекты | `source/domain/projects/` |

Эти каталоги являются корневыми bounded contexts (предметными областями) соответствующих разделов.

Обязательные правила:

1. Каждая сущность, бизнес-правило, инвариант и предметная логика, принадлежащие одному из пяти глобальных разделов, размещаются в каталоге этого домена внутри `source/domain/`.
2. Любое дальнейшее развитие конкретного раздела расширяет его собственный доменный каталог. Нельзя создавать параллельный домен этого же раздела в другом месте репозитория.
3. Подкатегории и внутренние направления размещаются внутри соответствующего глобального домена. Например, категории инструментов располагаются внутри `source/domain/tools/`, а не становятся равноправными глобальными доменами.
4. Доменный каталог владеет своими сущностями и бизнес-правилами. Другие домены не копируют их и не изменяют их внутреннее состояние в обход предусмотренных контрактов.
5. Общие технические типы сами по себе не являются основанием для переноса предметной логики в общий каталог. Общий код допускается только при наличии реальной общей ответственности и явного контракта.

### Междоменные связи — отдельный слой экосистемы

Связи между двумя и более глобальными доменами не принадлежат ни одному из них. Для таких связей предусмотрен отдельный архитектурный слой вне `source/domain/`:

`source/ecosystem/`

Этот слой отвечает за междоменные отношения и правила взаимодействия между глобальными разделами Raymondovich.

Правила слоя:

1. Модели связей, идентификаторы связуемых объектов, правила установления/разрыва междоменных отношений и координация нескольких доменов размещаются в `source/ecosystem/`, а не внутри одного из пяти доменов.
2. Слой экосистемы может ссылаться на публичные доменные контракты и идентификаторы, но не должен присваивать себе владение сущностями или бизнес-правилами отдельных доменов.
3. Слой экосистемы не должен дублировать доменную логику, напрямую менять внутреннее состояние доменов или обходить их публичные контракты.
4. Слой не является местом для произвольного общего кода. В него попадает только логика, которая по смыслу действительно связывает несколько глобальных доменов.
5. Интеграция междоменных связей с базой данных, API и интерфейсом выполняется через соответствующие application, infrastructure и presentation механизмы. Сам слой экосистемы не должен содержать UI, CSS, прямые обращения к Supabase или browser API.
6. Если междоменные связи ещё не реализуются, каталог `source/ecosystem/` не требуется создавать заранее. Но при первом внедрении таких связей они должны начинаться именно в этом слое.

### Исключения и существующая структура

1. Архитектурное исключение допускается только тогда, когда ответственность по своей природе не принадлежит одному из пяти доменов или относится к отдельному техническому/платформенному слою.
2. Исключение должно быть обосновано в документации до реализации: указать ответственность, причину размещения вне домена и границы взаимодействия.
3. Нельзя использовать исключения как способ обхода доменного владения или для создания неограниченного общего каталога.
4. Уже существующие каталоги, не входящие в пять глобальных доменов (например, `source/domain/control-center/`), не перемещаются и не удаляются автоматически. Их назначение и дальнейшее размещение рассматриваются отдельной архитектурной задачей. Новые предметные сущности пяти глобальных разделов в такие каталоги не добавляются.

### Обязательная проверка перед разработкой

Перед созданием или изменением доменной логики агент обязан определить, какому из пяти глобальных доменов принадлежит ответственность. Если она охватывает несколько доменов, агент обязан рассмотреть слой `source/ecosystem/`. При неоднозначности или необходимости исключения агент должен остановиться и согласовать архитектурное решение с владельцем до изменения кода.

## 5. Обязательное соблюдение

1. Агент обязан прочитать этот документ до начала работы с репозиторием.
2. Правила применяются ко всем новым файлам, папкам, модулям и изменениям.
3. Агент обязан проверить соблюдение правил до завершения задачи.
4. Если требования задачи конфликтуют с этим документом, агент обязан сообщить о конфликте до внесения изменений.
5. Агент не вправе самостоятельно отменять или ослаблять эти правила.
6. Изменение настоящего регламента допускается только по явному решению владельца проекта.

## 6. Проверка перед завершением задачи

Перед передачей результата агент обязан проверить:

- [ ] Новые имена файлов и папок соответствуют Naming Convention.
- [ ] Версии всех изменённых файлов увеличены.
- [ ] Визуальные стили и токены не вынесены за пределы `source/design-system/`.
- [ ] Новые UI-компоненты используют общую Design System.
- [ ] Предметная логика размещена в одном из пяти соответствующих доменных каталогов.
- [ ] Междоменные связи размещены в отдельном слое экосистемы, а не внутри одного домена.
- [ ] Любое архитектурное исключение обосновано и согласовано до реализации.
- [ ] Изменения не нарушают существующие архитектурные границы.
